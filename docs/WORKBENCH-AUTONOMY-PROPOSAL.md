# Seep 全工作台执行与人机协作优化方案

日期：2026-11-01。状态：**待评审的设计草稿，尚未实施**。

本文根据本轮用户需求、当前源码检查与上游研究提出方案，覆盖九大域、跨域项目和日常开发。它不代表新增能力已完成，也不构成运行目标、安装组件或修改系统的执行许可。本文不是第二份需求或进度总纲；获准实施后，决定并入 `REQUIREMENTS.md`，实施状态与验证结果仍记入 `docs/CURRENT-STATE.md`。

本次只新增本文，保留工作区原有未提交改动，不修改运行配置、不部署、不启动目标软件。

## 1. 要解决的实际问题

用户通过 PIWeb、PI 或其他通用智能体提供目标后，Agent 应能够在已有任务范围内自主完成必要的理解、资料查询、工具发现、实现、运行、观察、验证和接续。用户不必反复代替 Agent 选择技术路线、启动工具、双击、切页面、截图、运行测试或执行普通命令。

适用任务包括九个现有领域中的专业工作、多个领域协作，以及普通应用开发、缺陷修复、前后端联调、测试、构建、依赖维护和工具配置。日常开发继续使用宿主的通用编码能力，不增加第十域，不强制进入逆向判型或实验模式。

运行与界面能力覆盖 Windows 桌面程序、Android 模拟器中的 APK、实验虚拟机内的程序，以及后续按实际设备验证的 Android 真机。登录页、功能页、菜单、文件对话框和异常弹窗都属于需要时可用的操作范围，不要求每个任务都使用 GUI。

对带壳、反调试或环境检测的目标，要能够比较正常运行与不同观测方式下的行为，并选择有证据支持的路线。不能承诺任意目标、任意保护都能自动完成，也不能把“软件打不开”直接认定为风控。

成功的产品体验是：用户说明目标和环境后，Agent 自己完成已经授权且具备能力的技术动作；遇到真正缺少的用户输入、超出范围的影响或工具无法处理的问题，才提出具体请求。

### 1.1 总体结构

```text
PI / PIWeb / 其他智能体宿主
  → 通用任务理解、已有范围复用、工具选择、执行与验证
      ├─ 日常开发：直接使用宿主编码、构建、测试能力
      ├─ 九大域任务：按需加载主域和辅助域专业能力
      └─ 跨域项目：共用目标、资产、版本、运行和证据
  → 文件 / CLI / MCP / 浏览器 / 桌面 / 设备 / 实验环境
  → 核对任务结果、必要清理、按任务复杂度保存接续信息
```

这是既有能力的职责划分，不要求新增常驻总控服务。公共执行原则适用于所有任务；具体领域方法按需加载。不能让逆向场景的壳判型、运行回执、M0 分级、固定报告格式和实验词汇成为普通开发的前置条件。

## 2. 已查明的事实与尚未验证的部分

| 项目 | 当前证据 | 对方案的影响 |
|---|---|---|
| 默认人工启动 | `Tool/prompts/AGENTS.md` 首选用户双击；`Tool/scripts/launch-gui.ps1` 默认 `Mode=user`，输出让用户操作并等待反馈 | 这是直接增加人工介入的行为来源，需要整理 |
| 启动提示与实际许可不一致 | `cmd-guard.ts` 对普通启动为 warn，但提示仍推荐用户双击 | 放行后仍可能把模型引向人工 |
| GUI 硬拦截已关闭 | 当前规则 `blockGui=false`；纯判定检查允许普通启动、鼠标位置控制和截图文件读取 | 不能再把问题笼统归为“所有权限都被封死” |
| 首答与运行回执不再独立阻断 | `answer-gate.ts` 的相应判定返回不阻断 | 提示词中残留的强制回执要求需要与代码统一 |
| 执行地点区分不足 | 命令文本 `ssh test-vm "Restart-Service TestFixture"` 仍命中系统服务规则；该字符串未被实际执行 | 必须区分宿主、实验客户机与真实设备，不能只按关键词放宽 |
| 文档冲突 | 凭据“用户自己操作”与“可读可用”并存；`AUTONOMY.md` 中部分系统操作口径与当前边界冲突 | 应同时消除偏严、偏松的旧表述 |
| 启动判断过强 | 启动脚本主要按父进程名给出风险，却推导出“零参数、无创建标志、等同双击”；按进程名寻找实例 | 需要改为实际启动证据与可靠的实例身份 |
| PI 已具备部分基础 | 本机 PI 代码支持图像工具结果；安装配置包含 `pi-playwright`、`pi-web-access` | 复用宿主与模型能力，避免另造智能体 |
| 桌面完整闭环尚未验收 | 浏览器操作与图片读取已确认到代码、安装层；不能据此推导 Windows 桌面全流程可用 | 必须新增真实窗口、输入和结果验证 |
| 现有项目入口是只读执行面 | `project_workflow.py` 明确为 `workflow-entry-only`，不负责启动目标、GUI 或任意运行操作 | 不能直接扩大其只读白名单并冒充已接通运行能力 |
| 公共规则夹带专业流程 | 全局提示词包含逆向判型、固定阶段、补丁术语和“同形状失败两次即停”；边界锚也包含该停止表述 | 需核对日常开发是否被套用专业流程；静态文字是风险证据，实际误用仍需场景验证 |
| shell 守卫不是全工具边界 | `cmd-guard.ts` 的工具钩子只处理 `bash` / `powershell`，其他工具直接返回 | 不能宣称文件、MCP、浏览器和 GUI 动作已受同一执行保护 |

本轮已比较相关扩展部署副本与源码；受管提示词去掉部署标记后内容一致。这仅证明磁盘内容一致，不证明正在运行的 PIWeb 已重载。当前会话的工具可见性、图像传递与桌面动作仍需单独验证。

## 4. 设计原则

1. **授权沿用任务范围。** 已有明确授权不因每次启动、截图、点击或调用分析工具重复请求。范围扩大、影响改变或用户撤回时才重新判断。
2. **能力、许可、环境分别判断。** 工具没注册、模型不能收图、窗口锁屏、访问被拒和目标检测退出是不同问题，不能统一显示“需要你操作”。
3. **根据动作目的选择通道。** 静态分析优先结构化接口；真实界面行为需要 GUI；调试状态使用调试器接口。MCP 是接口形式，不代表动作天然更安全或更难检测。
4. **按实际影响判断边界。** 命令、API 和 GUI 执行同一动作时使用同一边界。不能通过点击系统设置绕过命令限制，也不能把禁止动作直接转交用户执行来声称任务已完成。
5. **保护日常宿主。** 已知可能安装驱动、改变全局网络或服务的目标，不仅因为“启动动作看起来普通”就自动运行。优先使用已明确的实验环境。
6. **不固定所有目标的技术路线。** 正常启动、调试启动和启动后附加按问题选择；早期启动逻辑可能需要直接调试，真实用户行为基线则需要正常运行。
7. **保留现有项目体系。** 不新增第十领域、不重造 Manager、账本或完整 Agent 平台。专业路线由现有主辅域与 `unpack-loop` 承担。
8. **先证明可用，再扩大范围。** 图片可显示不等于模型收到；进程存在不等于功能可用；一次成功不等于支持所有版本和环境。
9. **公共原则与领域方法分层。** 公共层只管任务范围、用户材料、系统影响、凭据去向和结果真实性。专业阶段、判据与停止条件只适用于对应领域；日常开发保留宿主本来能完成的动作。
10. **按任务规模使用流程。** 小修复可以直接阅读、修改和验证；长期、多版本、多设备或需要交付证据的项目使用现有持久状态。不为一行修复强制创建完整案件、时间预算和四档上限。

### 4.1 九大域与日常开发的适配要求

以下按当前 `Tool/skill/*/pack.json` 的实际 ID 列出，表示拟验收的职责，不表示已经全部接通。通用准入不依赖“属于哪个域”，领域负责专业判断和验收。

| 任务范围 | Agent 在已有范围内应自主完成 | 保留的关键边界 | 必须有的结果验证 |
|---|---|---|---|
| 通用软件 `softseep` | 文件识别、静动态分析、程序操作、工作副本修改、版本比较 | 原件、运行环境、目标实例与系统影响 | 目标行为、相邻功能及适用版本；不以补丁写入证明功能通过 |
| Android `apkseep` | 包分析、构建签名、测试设备上的安装启动、界面与日志观察 | 设备选择、账号、数据清除和系统变更 | 实际安装包、正确设备和完整功能路径 |
| 网站与接口 `web-pentest` | 代码/接口检查、范围内请求、浏览器流程和测试验证 | 端点、账号、速率、测试数据及外部影响 | 请求与响应、权限对照、必要业务后置条件 |
| 固件与 IoT `firmware-iot` | 解包、结构分析、约定仿真环境和协议实验 | 真机刷写、供电、设备与网络影响 | 架构/布局、提取内容、仿真行为或设备实测分别说明 |
| 私有协议与插件 `protocol-plugin` | 文件/流量解析、编解码、测试端点交互、插件构建联调 | 真实业务消息、服务端状态和重放副作用 | 分帧、状态转换、输入输出与当前版本相符 |
| Pwn 与密码学 `pwn-crypto` | 本地分析、求解、测试 harness、已明确靶场的实验 | 目标地址与本地/远端影响、资源上限 | 独立样例、真实触发和可复现结果；失败与未知分开 |
| 取证 `forensics-mobile` | 镜像/日志/数据库分析、提取、时间线和交叉核对 | 原始证据、隐私、提取对设备的改变 | 来源、指纹、工具参数与结论链；不把推测当原始事实 |
| 恶意样本 `malware-analysis` | 静态研判、已批准隔离环境内的运行与采集 | 未知代码、外连、持久化、共享资源和宿主隔离 | 已观察行为、未触发分支与运行覆盖范围 |
| 供应链 `supply-chain-security` | 依赖/制品审查、SBOM、来源核对、测试构建 | 安装脚本、制品执行、签名凭据和发布权限 | 依赖身份、可复现检查、构建结果；安装脚本不因包管理器调用而自动变低影响 |
| 日常开发与维护 | 读改代码、范围内依赖操作、本地测试、构建、启动开发服务、浏览器/桌面验证和文档 | 已有用户改动、生产系统、发布/发送、不可恢复数据和系统设置 | 与变更相称的测试、构建或功能验证，不强制逆向报告 |

跨域例子：Android 应用与私有协议联调、桌面软件与供应链审查、固件与密码算法分析，使用一个项目中的主辅资产和相应专业验收，不要求用户分别发起多轮任务或重复授权。

### 4.2 日常开发不能被实验规则误伤

- 已要求修改代码时，相关工作副本读写、合理测试、构建和本地验证自主完成；安装或更新依赖按来源、安装脚本与影响判断，不能所有安装都问，也不能全部无条件执行。
- 工作区可再生缓存和本次产生的中间产物可按明确路径清理；用户原始资料、未知文件和已有未提交改动保留。
- 启动本地开发服务、测试数据库或容器需要核对端口、卷、数据与暴露范围；使用容器不等于隔离成立，更不自动授予宿主服务或网络管理权限。
- 构建与部署分开。本地构建、测试不应要求上线许可；发布、生产部署、外部发送和真实业务变更按当前明确授权处理。
- 数据库迁移先明确作用于可丢弃测试数据、开发数据还是生产数据；同一条命令在不同目标上的处理可以不同。
- 一次测试失败应先定位再修正；“两次失败”限制相同无证据重试，不限制合理的编译修复、测试迭代和新假设验证。
- 普通开发不默认套用 `scope=local-authorized-sandbox` 作为环境事实。若保留该标记，应仅表达已注明的产品默认元数据，不能替代真实工作区、设备和环境范围。

## 5. 用户体验与最小工作流程

流程不是每个任务必须走完的固定关卡。简单开发任务可直接修改与验证，静态任务可直接结束于分析结果；需要长期状态、运行或外部交互时按需使用下列环节。

```text
用户自然语言与材料
  → 理解预期结果，复用工作区、项目和已有任务范围
  → 日常开发直接使用宿主能力；专业任务按需加载主辅域
  → 核对本次需要的最小能力与动作影响
  → 阅读 / 实现 / 分析 / 运行 / 交互，按需组合
  → 核对结果，失败时先诊断与重规划
  → 交付、清理本次资源；必要时保存项目证据和接续信息
```

对用户只表达目标进展、已证事实、具体阻碍和必要决策。项目 ID、设备适配器、窗口句柄、阶段枚举、工具选择和账本字段由 Agent 处理。

### 5.1 允许自主执行的动作

在当前目标和环境已有授权、实际影响相符的前提下：读改任务相关代码、查资料、调用已接通工具、创建工作副本、依赖检查、测试构建、本地联调、启动或重启本次目标、截图、窗口导航、点击、输入、切换功能页、采集约定日志、运行受控实验、登记证据和验证结果。

“点击”不能一概视为低影响：提交交易、删除真实数据、安装系统组件、发送外部消息等仍按其实际后果处理。测试账号、测试数据和允许的网络交互范围应沿用项目中已有约定。

### 5.2 需要用户介入的情况

- 用户尚未提供、且 Agent 无法从已有项目材料得到的必要信息或实体设备。
- 首次建立确实缺失的任务范围，或扩大到新目标、敏感环境、不可恢复动作。
- 需要实体按键、设备解锁、本人验证等当前工具不能完成的动作。
- 宿主或目标实际拒绝访问，且不存在已授权、能力等价的可用路线。

请求必须写清：缺什么、实际报错或证据、为何现有工具无法处理、最少需要用户做什么、完成后从哪里继续。多个缺口合并询问；等待时可继续独立的已授权工作。

### 5.3 失败后的责任

同一假设下的重复失败触发 Agent 自己重新判断，不自动结束整个任务或要求用户接手。区分：动作未发出、动作返回失败、状态未变化、目标退出、权限拒绝、工具断连和证据不足。

已经可能产生副作用的操作，不因超时或断连直接重放；先检查实际状态。明确不可替代缺口后才进入等待状态。

## 6. 在现有架构内接入能力

### 6.1 三类能力分工

这里的三类是运行与交互专项的内部划分。普通代码读写、测试、构建、依赖检查、文件与离线数据处理继续使用宿主及现有领域工具，不需要绕道桌面控制服务。

| 能力 | 负责的动作 | 复用或落点 |
|---|---|---|
| 目标运行 | 正确入口、参数、目录、生命周期、已有实例、正常启动与调试启动 | 重整 `launch-gui.ps1` 的职责；分析工具自身仍使用 `tool-run.ps1` |
| 界面控制 | 图像与控件、窗口、键鼠、触控、等待、结果检查 | 评估现成桌面/移动 MCP 或库，接入现有工具发现、配置和效果声明 |
| 专业分析 | 反编译、断点、事件、内存、转储、网络观察和比较 | 继续复用 IDA、x64dbg、Frida、现有领域技能和 `unpack-loop` |

工具优先级必须附带“是否回答同一问题”的条件。有 CLI 能读文件，不能推导它能替代程序交互；存在 GUI 也不要求用鼠标操作本可稳定调用的调试器 API。

### 6.2 接口语义草案

下表描述所需语义，不预先冻结工具名或新建一套协议。实施前先比对选定 provider 的实际 schema，优先适配已有接口。

| 接口职责 | 至少需要提供的事实 |
|---|---|
| 发现与就绪 | provider 与版本、运行位置、当前会话、图像/控件/输入能力、权限、限制、实际探针结果 |
| 启动/选择实例 | 目标资产、实际路径与版本、入口、参数、目录、PID 与启动时间、是否复用已有实例、启动方式 |
| 获取观察 | 环境与窗口/设备身份、观察时间、分辨率与缩放、画面或控件、观察版本号、截断/遮挡/安全画面限制 |
| 执行动作 | 目标窗口或设备、动作类型、参数、依据的观察、结果与错误；不回显秘密值 |
| 等待与检查 | 可观察条件、超时、实际状态、是否仍在运行、是否达到业务后置条件 |
| 清理与接续 | 本次拥有的进程/连接、已释放资源、仍运行的目标、未完成清理及恢复步骤 |

动作“已发出”“被接口接受”“界面发生变化”“目标功能通过”是不同结果，不统一写成 success。

### 6.3 与现有状态和证据衔接

- 项目、版本、run、资产与结论继续使用现有 `project_state`、`manager_state`、`case_state` 和报告接口。
- `project_workflow` 的既有只读动作保持其原契约。运行能力通过明确声明效果的适配路径接入；不能只修改其只读白名单或全局允许 foreign-code 来获得执行权。
- 先核对现有状态模型是否已有环境、实例与观察引用字段；缺少时做向后兼容的最小扩展，不另建一套项目数据库。
- 原始输出、动作记录、关键截图和业务检查结果回到同一 run；状态快照不能冒充持续运行证明。
- 日常小变更使用现有会话与工作区即可。持续性开发项目可以复用既有资产、版本、run 和交接记录，不强制映射成逆向领域，也不为了通用开发重造项目框架。是否登记状态取决于恢复和交付需要，而非所有工具调用的前置要求。
- 直接调用外部 MCP 不会自动经过 `project_workflow`。每个通道必须声明哪些检查由 provider、宿主扩展或本项目承担，不能宣称当前存在全局执行闸。
- 运行记录保存可恢复的目标身份和下一步，连接句柄本身不跨进程复用；恢复时重新核对 PID 启动时间、设备标识和目标版本。

## 7. 权限与执行环境的整理

### 7.1 先区分运行位置

| 位置 | 默认处理原则 |
|---|---|
| 日常 Windows 宿主 | 保留全局网络、驱动、服务、引导、信任根和破坏性磁盘操作保护 |
| 已明确的实验虚拟机 | 在该客户机已批准的范围内执行；可回滚不等于无限授权，不扩大到宿主、共享目录或生产网络 |
| Android 模拟器/真机 | 动作绑定设备 serial、用户配置与目标包；设备系统改动和清数据需对应范围 |
| 其他远端环境 | 核对端点与环境身份，继承该环境已有边界；远程命令不能因名称包含 vm 就自动放行 |

不要仅从 SSH 命令中的主机名推断“安全虚拟机”。应由已核对的连接与环境身份提供执行位置，使用结构化参数传递目标动作。未知位置保留明确诊断，不能静默套用宿主规则或全部放行。

### 7.2 清理相互矛盾的规则

实施时一次核对以下消费者，避免只改一处又被另一处旧提示覆盖：

- `REQUIREMENTS.md` 的人机配合和凭据表述。
- `Tool/prompts/AGENTS.md` 的默认人工启动、固定通道顺序、运行回执、30 秒不确定即问。
- `Tool/docs/AUTONOMY.md`、`EXECUTION.md`、`EXTEND.md` 与相关使用手册。
- `cmd-guard.ts` 的启动告警及其返回给模型的建议。
- `cmd-guard.rules.json`、`answer-contract.json`、`user-inputs.json`、`blockers.json` 的实际消费者。
- `tool-runtimes.json` 中“GUI 必须人工盯住”等与桌面控制目标不一致的说明。
- 相关领域技能、部署模板与实际 AgentRoot 中的受管副本。

删除“所有工具都必须先加回执”“任何目标必须用户双击”等概括要求；保留任务范围、明确拒绝、真实系统副作用与必要输入。没有依据不增加新的首次确认表。

凭据沿用现有凭据仓，用引用传入输入工具，执行结果不回显秘密。截图、控件值、工具返回、错误和日志均需检查凭据泄露出口；不能只处理报告正文。尚未支持安全传递的 provider 不自动获得凭据输入能力。

### 7.3 保留守卫，修正守卫的职责

守卫负责真实副作用边界、超时与执行诊断，不负责替主模型选择所有技术路线。普通启动警告应说明观察事实和适用条件，不再默认推荐用户代劳。

前端点击删除数据与命令删除数据的后果相同；所有新增 GUI/设备通道都需要效果声明与明确的边界消费者。不能因为它不经过 shell 就跳过检查。

### 7.4 先完成全工作台规则影响清查

不能只改 `launch-gui.ps1`。实施第一阶段要沿真实加载与调用链核对：

| 层 | 清查内容 | 必须交付的事实 |
|---|---|---|
| 公共提示词 | 系统装配、边界锚、全局 AGENTS、请求期补充、项目级指令 | 哪些每个任务都加载、哪些只在专业任务需要；重复、冲突与专业规则外溢位置 |
| 宿主与扩展 | PI/PIWeb 当前版本、已加载工具、超时、重试、停止、用户询问、外部 MCP | 当前实际生效的设置和限制来源，不能把第三方宿主拒绝归因 Seep |
| 工具与效果 | 文件、shell、MCP、浏览器、GUI、设备与远端通道 | 每类动作能影响哪里、谁检查边界、谁拥有资源、失败怎么恢复 |
| 九域方法 | 父技能、子技能、配方、知识库中的准入与人工步骤 | 哪些是必要专业条件，哪些是无依据的全局禁令或过时经验 |
| 日常开发 | 代码修改、依赖、测试、构建、本地服务、数据与制品 | 哪些正常动作被不必要的实验规则阻断或推给用户 |
| 部署与接续 | 源码、受管副本、实际装配、旧进程、项目恢复 | 区分文件已部署、模块已加载和真实任务已验证 |

清查结果在现有需求/状态记录中按具体问题登记：来源、触发条件、实际结果、期望行为、消费者、修正方式和回归场景。不要生成一套需要用户长期维护的规则管理平台。

公共层只保留确实跨任务成立的原则。可变技术偏好交由 Agent 结合任务判断；专业步骤放回对应领域按需读取；能可靠检查的真实副作用由明确的执行边界承担。第三方宿主的权限政策不由修改 Seep 提示词覆盖。

## 8. Windows 启动与桌面闭环

### 8.1 启动器需要修正的行为

- 自动方式成为已有任务范围内的默认，人工方式仅作为显式选择或已确认缺口的后备。
- 支持正确的程序入口、快捷方式或启动器；允许目标确实需要的参数和工作目录，不强制所有程序零参数。
- 只记录实际取得的父进程、命令行、令牌等信息；未测到的创建标志不推断。Explorer 父进程不能作为不可检测证明。
- 用完整映像路径、启动时间、会话和 PID 识别实例；处理同名程序、多实例、单实例转发、启动器退出及子进程接管。
- shell 打开成功与目标进程就绪分开；进程就绪与主窗口、业务页面可用分开。
- 不同步等待交互程序自然退出作为启动成功条件；helper 可后台运行，目标 GUI 应在需要交互的会话中可见。

### 8.2 界面控制至少覆盖

窗口发现与选择、截图、按控件或坐标定位、单击/双击/右键、按键与组合键、Unicode/中文输入、滚动、拖动、菜单、文件对话框、弹窗与错误读取。

标准控件可优先用 UIA；自绘、Qt、游戏画面等根据真实暴露能力使用视觉或其他已验证后端。纯文本模型可使用结构化控件；没有图像输入的模型不能被标记为完成自绘界面视觉验证。

### 8.3 稳定性要求

- DPI、多显示器、缩放和窗口坐标必须映射一致；窗口移动或页面变化后旧定位失效。
- 关键动作前检查目标与观察是否仍匹配；页面变化后重新观察，避免按过期画面点击。
- 多 Agent 共享一个交互桌面时，界面动作必须串行归属，避免抢焦点；独立静态分析仍可并发。
- 锁屏、断开的远程桌面、UAC 安全桌面和不同完整性级别应返回具体限制，不循环盲点。
- 关闭和清理只作用于本次拥有的实例；不得按程序名批量杀掉用户已有进程。

## 9. Android、模拟器与虚拟机适配

### 9.1 Android 模拟器

优先验证用户实际使用的模拟器和现有 ADB 环境。基础能力包括：选择设备、识别包、按范围安装、启动/停止、前台 Activity、截图/控件树、点击/滑动/长按、输入、返回/主页、授权弹窗和日志。

明确使用的是 ADB/UIAutomator、设备内服务、模拟器控制台还是宿主窗口控制；不同后端的观测和输入特征不能混写。清除数据、卸载、重装、修改系统配置分别声明效果。

### 9.2 Android 真机

在模拟器路径稳定后单独验证。复用适配器语义，不继承模拟器的通过结论。USB 调试、设备授权、Root、系统版本、屏幕保护与输入法限制逐项保留事实。

遇到模拟器环境拒绝，先确认正常人工操作是否同样失败；可选择已授权真机，不把重试点击当环境适配。手机鼠标输入不等于手指触屏；HID、外部图像采集和物理触控设备只作为后续有具体需求的可选通道。

### 9.3 虚拟机

控制端可以位于宿主，执行目标位于客户机。明确区分客户机内调试 MCP、虚拟机控制台键鼠、浏览器远程控制台和远端命令。

从浏览器控制台看到了客户机画面，不代表能读取客户机内部 DOM。应核对键鼠是否传入、画面缩放、焦点、设备映射和实际业务结果。

需要快照时验证其属于正确虚拟机且恢复可用；不能只保存“已快照”字段。恢复可能影响已安装软件、文件、会话和网络状态，需按既有实验范围处理。

## 10. 带壳与反分析目标的合理流程

目标控制与专业逆向分别验收。UI 能点击不等于调试可附加，调试接口可用不等于目标功能页可操作。

| 问题 | 应取得的证据 | 处理方向 |
|---|---|---|
| 正常启动也失败 | 入口、依赖、错误窗口、日志、退出信息、环境 | 先排查运行条件，不直接归因自动化检测 |
| 正常可用，软件输入失败 | 人工基线与控制输入对照、焦点/权限/页面状态 | 验证输入通道，不先改目标代码 |
| 接调试器或观测工具后退出 | 接入前后差异与可重复信号 | 由现有专业技能选择更合适的观测方法 |
| 只在模拟器/虚拟机失败 | 同版本不同环境的结果及环境检查证据 | 验证环境适配，必要时使用已授权实机 |
| 页面操作成功但网络结果失败 | 业务状态、请求观察与实际错误 | 分析网络/服务端问题；点击方式不能替代协议验证 |
| 转储可解析但不能独立运行 | 原运行身份、取证时机、结构与功能检查 | 区分分析材料和可交付程序，不虚报完整脱壳 |

沿用 `softseep`、`apkseep` 与 `unpack-loop` 的判据和路线，不新建万能脱壳器。一次实验尽量只改变一个相关因素；记录假设、观测方式、结果、影响与下一步。

可重复的成功步骤沉淀为目标相关配方，注明版本、设备、参数、前置状态与仍未知的部分。不能把某个壳的经验提升为全局启动禁令，也不能把某种硬件输入称为完全不可检测。

## 11. Provider 选择与复用策略

先做短名单验证，再决定集成对象，不预先认定某个包适用于所有场景。

| 候选类别 | 本次候选依据 | 选用前必须验证 |
|---|---|---|
| Windows UIA/视觉控制 | Windows-MCP、pywinauto 等现成能力 | 当前维护状态、依赖、协议、DPI、控件/自绘覆盖、截图与输入、异常清理 |
| Android 控制 | Mobile MCP、现有 ADB 与设备工具 | 设备服务、输入实现、版本兼容、中文输入、设备选择、图像返回和凭据输出 |
| 调试控制 | 已有 x64dbg MCP；对照 x64dbg Automate | 当前插件真实 schema、启动/连接/等待/停止、事件与目标身份、权限和断连行为 |
| 浏览器 | 已配置的 PI Playwright 能力 | 实际加载、图像传递、页面控制；虚拟机控制台另做真实验证 |

优先复用本机已有可工作的组件；缺少必要能力时才增加依赖。版本、下载来源、许可与本地适配记录在既有来源和工具配置中。避免同时接入多个功能重复的桌面控制服务。

不把某个供应商的 Computer Use API 设为项目硬依赖。支持工具调用和图像结果的通用宿主通过 MCP 等既有方式使用能力；宿主差异由薄适配层处理。浏览器聊天界面本身不等于本机桌面权限。

## 12. 分阶段实施与退出条件

各阶段形成独立、可回退的变更；后一阶段不能用前一阶段的通过结论代替验收。开发时按依赖推进，不要求同时完成所有平台才交付已验证部分。

| 阶段 | 主要工作 | 交付与进入下一阶段的条件 |
|---|---|---|
| P0 全工作台基线审查 | 沿公共提示词、宿主扩展、九域方法、开发与部署链路查实际限制 | 区分硬阻断、提示偏好、能力缺失和加载失败；只把有证据的问题列为修正项 |
| P1 公共执行规则收口 | 统一已有范围、环境与效果、询问与停止；专业规则按需；保留宿主保护 | 日常开发和静态专业任务可自主执行；边界正反例成立；无新增逆向前置流程 |
| P2 开发与九域闭环回归 | 验证代码修改、测试构建、本地运行、离线分析及跨域衔接 | 各域按实际声明给出通过或缺口；至少一个跨域完整任务；不以注册或数量充当完成 |
| P3 运行与交互能力 | 先完成一个 Windows 后端与功能页闭环，再按任务选择 Android/虚拟机路径 | 每个接入通道证明启动、观察、动作、结果与清理，用户不代做普通技术步骤 |
| P4 专业动态能力 | 将调试、设备、仿真、流量观测与现有主辅域关联 | 专业动作有正确目标、前置条件和证据；断连不盲重放；宿主与客户机不混淆 |
| P5 复杂任务专项 | 按真实需要验证保护目标、设备差异、复杂联调、证据恢复与版本迁移 | 各专项只报告已验证的版本与环境，技术受阻能定位且合理换路 |
| P6 发布与接续 | 回归、受管部署、真实宿主加载、换会话恢复、文档和来源收口 | 通用开发、九域与已支持平台矩阵、未知项、恢复和回退均可复查 |

P0/P1 不能被当作“桌面功能已完成”；开发或普通应用的通过也不能宣称强保护、Android 和全部虚拟机已支持。若 P3 暴露 provider 的根本兼容问题，应换候选，而不是堆更多提示词。

这些阶段有依赖，但不是必须逐域逐平台走完的长流水线。P0/P1 是共同基础；其后可围绕当前真实任务补能力并完成一条纵向闭环，未涉及的领域保留回归或待验证状态。Windows 路径可提前开展对应 P5 专项，无需等待 Android、真机全部接通。已有可用实验虚拟机可以直接用作验证环境；各平台的通过结论分别记录。同一交互桌面的动作须串行归属。

第一份可交付增量应包括：公共规则与提示一致、一个日常开发修复到测试/构建的完整任务、现有专业分析回归、明确的宿主保护及可回退部署。Windows 从启动到功能页的闭环是紧随其后的专项；若已有组件可用，也可一并交付，但不能因此忽略九域与开发的共同问题。后续按实际目标扩展，避免为“全平台”迟迟交不出能使用的版本。

不提供没有验证依据的工期承诺。P0/P1 影响规则消费者较多；P2 验证是否误伤正常工作；P3 决定交互工具路线；P4/P5 耗时取决于真实设备、保护和材料。每阶段结束后根据实测估计后续工作。

## 13. 验收矩阵

### 13.1 必须覆盖的行为

| 场景 | 通过证据 |
|---|---|
| 普通缺陷修复 | 从问题复现到代码修正、适当测试或构建；不要求创建逆向案件、lab 开关或重复执行许可 |
| 新功能开发与联调 | Agent 自主使用必要依赖、测试和本地服务，功能结果与用户目标对应，启动后能正确清理 |
| 依赖与供应链维护 | 版本、来源、安装脚本与影响被正确区分，相关构建/测试通过；不把所有安装都推给用户 |
| 九域现有能力 | 每域至少一个对应已声明能力的有效任务，并保留必要负例；深层缺口单列，不以单例宣称全域完善 |
| 跨域项目 | 主辅资产与结论回到同一项目，域切换不丢范围或重复要求用户输入，至少一条端到端路径 |
| 不同任务的提示词装配 | 普通开发不会被套用壳判型、补丁分档或专业报告；专业任务能按需获取对应方法 |
| 普通 Windows 程序 | Agent 自主启动、到达功能页、执行一个有后置条件的操作并验证 |
| 不同 UI 技术 | 标准控件与至少一种自绘/非标准控件分别验证；失败保留支持边界 |
| 启动器与同名实例 | 不误认已有同名进程；子进程或单实例转发后仍绑定正确目标 |
| 文件与多窗口操作 | 文件对话框、菜单、弹窗、窗口切换均作用于正确目标 |
| 中文输入与缩放 | 所选输入法和 DPI/分辨率变化下结果正确，旧坐标不会误用 |
| 调试器组合 | 正常启动、调试启动/附加按任务选择，事件与实际目标绑定 |
| Android 功能页 | 正确设备、包与前台页面，完成点击/滑动/输入和结果检查 |
| 虚拟机 | 控制地点、目标地点、快照和日志身份明确，不误改宿主 |
| 反分析对照 | 能复现正常与仪器接入差异，结论有证据，不以目标退出猜原因 |
| 换会话恢复 | 能重连并重新核身份，不用过期 PID、截图或错误版本继续点击 |

### 13.2 必须覆盖的失败与拒绝

错误窗口/设备、过期截图、目标版本变化、设备断连、锁屏/UAC、模型不支持图像、图像仅在前端显示、截图受保护、工具未加载、目标崩溃、调用超时但动作可能已执行、用户明确拒绝、宿主系统改动、凭据值出现在返回或证据中。

这些情形必须返回具体原因，不能假成功、静默降级或无限重试。多个 Agent 争用同一桌面时，必须证明不会交叉点击。

通用负例还包括：覆盖用户未提交代码、清理不可再生数据、把测试数据库误当生产库、依赖安装脚本越界、生产部署或外部发送未获相应授权、专业知识库内容被误当用户指令、同一测试失败后合理修复却被两击规则终止。每项按实际支持范围设计行为检查，不能只检查某段提示词是否存在。

### 13.3 证据分级

- 合成控件和自建应用证明输入、观察、身份和边界机制，不证明真实逆向能力。
- 真实普通应用证明日常控制能力，不证明带壳目标分析能力。
- 自建程序加已知壳可验证特定实验路线，不代替用户实际目标见证。
- 受权真实保护目标按具体问题、版本和环境记录通过或未通过，不推广到整个壳家族。

真实运行前确认现有范围与环境；先用无害夹具验证工具机制，不为验收而自动运行仓库中的未知样本。

### 13.4 质量指标

记录：可自动化技术动作的人工代操作次数、重复索取已存在信息次数、无必要的重复确认次数、每个完整场景的通过/失败、错误目标操作次数、无依据成功次数、恢复与清理结果。

受控验收场景中，普通代码修改/测试构建/工具调用/启动/截图/点击/页面导航的人工代操作目标为零；确实需要实体输入或范围决策的介入单独分类，不伪装成自动成功。错误目标操作、覆盖用户改动、宿主越界和虚假成功均不能接受。

性能记录截图体积、调用耗时、无变化轮询与模型开销，不先设没有测量依据的统一阈值。对稳定页面可批量执行已知动作，对未知页面、错误或状态变化及时重新观察。

## 14. 部署、回退与维护

- 源码、依赖、工具声明、MCP 注册、技能引用和部署清单使用现有安装/更新入口，保留用户配置与原有未提交改动。
- 每次部署核对文件身份；随后验证实际宿主工具表、图像往返与动作。PIWeb 新建聊天不自动视为已重载。
- 保存旧版本受管资产与新增依赖清单；回退本次增量，不整体替换用户 AgentRoot，不默认卸载用户原有组件。
- 清理只关闭本次拥有的连接或进程；共享调试器、用户预先启动的目标和未归属资源不得误停。
- 按影响范围运行专项、契约、部署和必要回归。已有总检仍按其现行定义执行，不降低断言或删除失败来获得通过。
- 实施决定写回 `REQUIREMENTS.md`，实际结果写回 `CURRENT-STATE.md`，稳定使用方法进入相应现有手册和技能。本文保持设计来源，不成为长期第二套进度表。

## 15. 需要在实施阶段作出的技术决定

由 Agent 先探测并提出有证据的选择，不要求用户挑库、填 schema 或判断协议细节：

1. 公共层、项目层、九域方法与宿主自身分别承担哪些职责，哪些旧规则需要删除、移回专业层或修正。
2. 日常开发、小任务和长期跨域项目怎样使用现有能力，避免新增强制登记流程。
3. 各工具通道真实边界由谁执行，动作位置与影响怎样可靠判定，无法判定时怎样报告。
4. 现有 Windows 交互会话、输入权限和模型是否支持图像闭环；选择一个主用控制 provider，有明确缺口再增加后备。
5. 当前 x64dbg、Android 模拟器、虚拟机与其他领域工具实际接口和能力；先适配已有组件。
6. 执行记录接入既有项目模型所需的最小字段，以及九域和开发任务各自的最小有效验收案例。

只有缺少不可推断的用户偏好、设备或任务范围时再提问。优先完成 P0 和 P1 的具体可评审变更，再根据验收推进后续阶段。
