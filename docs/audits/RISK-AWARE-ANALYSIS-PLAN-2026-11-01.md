## 0. 先把三个对话放回同一条任务链

### 0.1 用户实际要解决的三个问题

| 工作线 | 用户看到的问题 | 负责回答 | 不应变成 |
| --- | --- | --- | --- |
| 一：能力发现与引用 | 有 KB、技能、工具和 MCP，Agent 却一直手搓 | 有什么现成方法，怎么找到、读取、实际调用与验证 | 强制每个任务调用全部工具 |
| 二：自主执行 | 本可自动启动、点击、输入，却一直让用户代操作 | 已有范围内谁来做、用什么控制通道、如何确认实例和结果 | GUI 等于人工，或每次运行重新索取许可 |
| 三：本方案 | 不识别保护与远端代价，反复试到封卡/封设备 | 当前问题怎样低代价取证，何时可自动继续，何时暂停具体动作 | 所有操作都拦、所有登录都交给人、或追求通杀绕过 |

三者的组合应当是：**找到适用能力 -> 按实际影响选方法 -> AI 在已有范围内执行 -> 检查业务结果和风险反馈 -> 必要时换路并接续。**

风险感知不是自主执行的反面，而是让自主执行知道哪些动作不能盲目重复。缺少能力先查能力，缺少证据先取证，只有缺少用户独有输入或确需扩大影响时才询问。

### 0.2 本次用户明确的范围

- 跨九域，也支持普通开发借用方法；网站/接口的反爬、JS 混淆、会话和限流必须纳入。
- 结合现有 SEEP 与公开工程实践，形成足够详细、能够落地和验收的方案。
- 本对话用自己的分支和 worktree，不干扰另两对话，最终由新对话适配合并。
- 不要求用户学习内部字段、选择专业工具或守在电脑旁完成普通点击。

本轮按“详细方案”交付，不提前部署新的风险闸，也不把下文所有字段和默认值冒认为用户已逐项批准。

### 0.3 成功标准

不是“以后什么都能逆”，而是：

1. 本可离线回答的问题，不启动生产软件或反复访问外部站点。
2. 需要动态观察时，能解释所选方法、检测面、输入条件和停止条件。
3. 正常开发、本地测试、范围内 GUI 操作不被重新交回用户。
4. 真实账号、卡密、设备、生产数据和配额不会被无预算重试或多 Agent 同时消耗。
5. 出现风险后暂停相关影响，其他可做的工作继续，换会话也不会忘记。
6. 能明确证明已覆盖哪些执行通道，不用“有规则”冒充全局约束有效。

| 观察 | 为什么影响本次目标 | 设计裁定 |

| 工具自己启动合理，但目标可能已在同机运行 | 新启动的分析组件也可能是目标可见环境变化 | 按目标上下文判断，不因“我们自己的工具”就忽略检测面 |
| 自主执行分支允许修代码后重测 | 对本地测试正确，但不该清空卡密风险历史 | 技术重试计数与外部资产累计完全分离 |

这些是局部静态阅读发现，不是已经在真实客户目标上复现封禁或崩溃。不得借本报告推断所有专业方法无效，也不得无理由删除原证据判据。

## 2. 跨场景模型：保护层、观察层、权威层、代价分开

### 2.1 保护层分类

| 保护层 | 常见表现 | 要回答的问题 | 不应跳到的结论 |
| --- | --- | --- | --- |
| 静态分析阻碍 | 壳、混淆、字符串加密、虚拟化控制流 | 当前问题涉及的代码是否实际可见 | 熵高就确定某商业壳，或任何问题都先全脱壳 |
| 动态观察阻碍 | 调试器/插桩/root/模拟器检测、延迟退出 | 是环境故障、插桩错误还是检测触发 | attach 失败必然是保护，或进程存活必然绕过成功 |
| 完整性约束 | 签名、文件/内存校验、反回滚 | 修改影响哪个范围，怎样验证业务仍正常 | EXE 签名没变就没有检测面 |
| 网络信任约束 | CA 信任、pinning、mTLS、应用层加密 | 需要的是元数据、明文还是协议语义，在哪层可见 | 装 CA 就都能抓，或 HTTPS 密文就是反抓包上报 |
| 网站环境/会话约束 | JS、Cookie、CSRF、nonce、时序、浏览器 API | 请求依赖什么前置状态，是否仍有效 | 复制 headers 就等于真实浏览器，或 200 就是目标内容 |
| 远端风控与证明 | 账号/设备/IP/租户频控、完整性证明、业务限制 | 谁作最终决定，哪些资产可能被累计记录 | 本地改提示就取得远端授权 |

同一目标可以同时有多层保护。优先处理阻碍当前证据目标的那一层，不以“检测全部绕过”为默认交付目标。[S01-S04, S11-S13, S23-S28]

### 2.2 三种不同的未知

- **方法未知**：不知道怎么观察。先调用现有能力发现和专业资料，不立刻让用户选工具。
- **事实未知**：不知道是否联网、是否绑定、哪个实例。先用低影响证据核实；必要时保留未知。
- **影响范围未知**：下一步可能接触真实资产且后果不能限定。缩小实验或集中询问，不把未知改成 false。

“不知道怎么用工具”和“需要你决定是否消耗唯一激活额度”是不同问题，不能用同一种人工接力解决。

### 2.3 保留本机层级，增加外部影响维度

沿用 L0-L4，不重定义它；另外按动作判断：

| 外部影响类别 | 例子 | 默认工作方式 |
| --- | --- | --- |
| 无外部交互 | 读工作副本、静态反编译、解析已存在 HAR | 已有范围内自主执行，不需要登录预算 |
| 有界常规访问 | 用户要求访问公开页面、查询已批准 API | 正常自主访问，限制意外扩散，不每个 GET 都弹确认 |
| 有状态/有价值的外部交互 | 登录、激活、刷新、发送短信、消耗云配额 | 沿用已有明确范围；缺少上限或发生新影响时补一次决策 |
| 异常与结果不明 | 风控提示、设备绑定变化、请求超时但可能已处理 | 暂停相关远端尝试，核对状态并继续离线工作 |
| 超出本机/数据边界 | 改整机网络、驱动、破坏性写盘 | 按现有边界换环境/路线，不转交用户代做来绕开 |

进程内只读也可能引发检测或客户端上报；网络 GET 也可能被计数。方法的直接写入属性与目标的间接反应分开记录。

## 3. 从逆向和测试实践借什么，不照搬什么

公开实践能够支持的是“小范围、分层、对照、scope、节流、证据和恢复”，不是一套所有工程师都会使用的通杀流程。

| 来源实践 | 借入 SEEP 的机制 | 不照搬的推论 |
| --- | --- | --- |
| OWASP MASTG：静态/动态与 resilience 方法 | 按问题选择观察层，注明环境和证据强度 | 有耐心理论上可分析本地代码，不等于能复刻服务端或无限预算 |
| Check Point：多种检测面与调试器副作用 | 建候选检测画像，检查工具本身对观察的影响 | 发现某 API 就立即套补丁 |
| OWASP 锁号测试 | 使用能承受锁定的账号，正式唯一资产不测阈值 | 教程示范次数就是安全次数 |
| Burp resource pools | 同一范围共享并发/速率，依据反馈节流 | 每个工具各限速就等于全局总速率已限制 |
| ZAP scope/modes | 把行为能力与允许目标范围结合 | passive scan 不改包就代表浏览器动作没有业务副作用 |
| HTTP 标准/AWS 重试设计 | 超时结果未知、重试需看语义和预算 | 幂等就是不会被风控记录，或所有 5xx 都可重发 |
| Cloudflare 网站排障 | 区分 JS/Cookie/WebView/挑战兼容性，保留诊断证据 | 换个 UA 或自动化浏览器就保证通过生产挑战 |
| GitHub API 规则 | 多种入口可能累计，串行和退避按服务规则配置 | 从一个服务复制速率和锁定参数给所有网站 |

详细来源见配套资料。特定厂商文档提到的换网络、系统设置等排障，不自动获得在用户主机实施的许可。

## 4. 任务启动与实验选路

### 4.1 不设所有任务必过的重型流程

以下是触发式决策，不是固定九阶段流水线：

1. 理解用户要得到的结果与已有范围。
2. 准备选择专业方法、重复手写或受阻时，用第一工作线的共享发现入口找现成资源。
3. 仅对即将执行的动作检查环境、保护线索和影响，不先扫描整台用户电脑。
4. 能从已有材料得到答案，直接离线推进。
5. 需要运行/访问时，选择能够回答同一问题、影响较小的实际可用通道。
6. 读取目标与业务结果；把风险反馈交给相应适配器和现有状态。
7. 同路线没有新证据时修复或换观察层；出现高损失风险时暂停相关交互。

普通前端改样式、本地单元测试等无需建立专业案件或远端预算。复杂/长期任务才按恢复需要挂接既有 project/version/run。

### 4.2 动态实验的最小内部记录

Agent 自行填写，不让零基础用户填表：

- 本次要回答的问题，以及为什么现有材料不足。
- 明确版本/哈希、目标实例、设备/浏览器配置与环境身份。
- 正常基线来自已有证据还是必须新取得；新取得是否也有外部影响。
- 本次唯一主要变量、预期现象和能推翻假设的观察。
- 可能出现的联网、绑定、扣费、风险上报与后台活动；不确定处保留未知。
- 允许的流程启动数、可观测请求范围、最长运行窗口和停止条件。
- 成功如何检查、失败保留什么、哪些影响不能回滚。

基线不是必须再登录一次。测试新 VM/新手机也不是无成本，可能触发新设备绑定。

### 4.3 通道选择的裁定顺序

先确认能否回答同一问题，再比较改动、可检测性、凭据暴露、范围和可验证性。稳定接口优先不等于永远绕开 GUI：真实页面行为需要浏览器，真实窗口需要桌面/设备工具，内部结构可以用分析接口。

不把 Frida、ETW、抓包、调试器按名称排成永久安全榜。所谓“被动观察”也要看是否安装驱动、注入模块、改变信任或目标可见配置。

### 4.4 保护画像的证据等级

沿用项目既有观察/推导/假设/未知，不引入第二套结论等级。建议画像事实至少区分：

- 静态线索：疑似调用、字符串或壳特征。
- 运行观察：什么环境、哪个时间点实际发生了什么。
- 因果支持：单变量对照或可定位的调用/返回证据。
- 反例/边界：同环境未发生、工具故障或只在某版本可见。

没有观察到事件，也要说明采集通道是否确实工作；“无日志”不自动变成“未检测”。

## 5. Windows / Android 等强保护目标的实际分支

### 5.1 软件尚未运行

优先保留原件、判格式/架构/签名和静态保护线索；明确当前问题。不得仅为了判型而登录或激活。若有驱动/服务安装线索，先核实际运行环境，不自动从普通软件启动升级成系统安装。

工具发现/安装也应考虑目标是否已经在同机或相关设备上运行；不在主机上为了隐藏痕迹批量卸载或修改系统配置。

### 5.2 只有工具接入后才异常

先用无害自建样本确认控制链能工作，再分析本目标已有对照证据。区分权限、ABI、版本、脚本错误、停顿超时和真实检测。对唯一付费目标不反复生产复现来满足教科书式对照次数。

确认为本地局部检查且实验条件明确时，按已有专业方法在隔离副本做局部验证。记录修正位置的版本/架构/语义和验证，不把工具模板视为已验收补丁。

### 5.3 改了以后“能启动”

至少分别检查：启动、实例/窗口、预期业务、错误/异常、必要网络或离线行为、修改范围。阻止退出后程序卡住、计时失真或线程不再响应，不能当成成功。

局部分析成果不必等到整个产品完全恢复才交付，但适用性必须明确，不能写成“完整破解成功”。

### 5.4 Android 重打包与设备证明

签名、ABI、安装来源、root/模拟器、调试标志与后端设备证明分别考虑。换设备、重签名和重新安装可能改变绑定条件。可控源码优先调试构建和测试后端，未知第三方成品不能直接套调试信任配置。

仿真只证明被模拟的函数/协议行为，不证明完整设备、真实硬件证明和后端业务已经复现。App 内可以修改的检查，不等于服务器会接受伪造证明。

### 5.5 技术边界

不自动上内核、不以关闭主机安全机制作为默认路线、不承诺所有壳可以完整去除。遇到环境缺口时，继续可用静态、离线协议和行为规格工作；给出准确缺项而不是笼统“你来点一下”。

## 6. 网站、接口、反爬和 JS 混淆：独立完整路线

### 6.1 先区分任务，不能访问一个网址就变成扫描

| 用户任务 | 合理默认 | 不自动扩大到 |
| --- | --- | --- |
| 开发自己的网页 | 代码、构建、本地浏览器、已有接口契约 | 扫描第三方站点或改生产 WAF |
| 查看公开网页 | 正常有界浏览与必要资源 | 目录枚举、批量抓取、循环刷新挑战 |
| 分析给定 JS/HAR | 本地格式化、AST、调用关系、协议结构 | 自动把旧 Cookie/签名请求发回生产 |
| 测试自己的接口 | 本地/测试租户与明确数据集 | 生产写入、短信/支付/删库 |
| 研究外部页面机制 | 范围内浏览、已有页面/资源/记录，必要低量取证 | 轮换身份/代理、规模化挑战规避或未知频控压力测试 |

### 6.2 收到的究竟是不是目标页面？

记录最终 URL、重定向、内容类型、业务标志和页面类别。区分目标内容、登录页、挑战页、软封禁页、缓存错误与真正的空数据。

200 可能是挑战页；401 可能来自某个正常子资源流程；403 可能是权限、WAF 或其他业务原因；429 可能是账号/服务/路由共享配额。既不能全部误判封禁，也不能全部视为正常重试。

对挑战页不反复刷新。若任务是自有站点开发，按测试配置与测试 key 完成自动测试；生产挑战兼容性另外验证，不承诺自动化工具能完成真人校验。[S25-S29]

### 6.3 JS 混淆与请求签名

先在离线副本识别打包/模块边界、配置、字符串、算法输入输出和调用链。静态不够再在已有范围内观察浏览器运行时。补环境和自动化脚本要说明模拟了什么、缺什么。

HAR 里已有的 nonce、CSRF、一次性票据、时间戳和会话状态可能已经过期或被消耗；不能把签名不通过一概解释为“算法写错”，更不能靠不断新登录获取材料。

区分四件事：离线函数输出一致、能生成一条新请求、真实服务器接受、本轮完整业务成功。前者不能自动证明后者。

### 6.4 会话稳定性

复用明确的浏览器/账号上下文；区分读取状态、提交登录、刷新令牌和注销。无理由清 Cookie、换浏览器指纹、换设备或新建 profile，可能让会话失效并制造新风险。

会话失效时，先判断是否确实需要重新认证、是否有现成范围和安全输入能力；可以自主完成的登录仍由 AI 完成，不自动交给用户。

OAuth/OIDC 的 state、PKCE、回调和重放检查由已有认证方法处理。测试构建可使用明确测试身份；不能为了便于自动化把生产认证/挑战关闭。

### 6.5 请求扩散与范围

以实际 origin/端口/路径/操作和必要依赖定义范围。重定向、SSO、CDN 与 iframe 并非一律非法，也不能从同一可注册域或名称相似推断全部获准。

顶层导航和主动 API 重放必须检查实际目的地；跨 origin 时不转发不匹配的认证材料。真实浏览器可能发出大量子资源、预取、Service Worker 或 WebSocket 流量，不能以“一次导航”宣称只发了一次请求。

本地开发服务可能代理到生产；`localhost` 名称不自动证明无外部影响。robots.txt 是爬虫规则，不是访问授权、API 配额承诺或无副作用证明。[S30-S31]

### 6.6 限流处理

- 有明确服务规则时采用其 scope、配额和时间窗；所有相关任务共享限制。
- 普通有界浏览不为“寻找最佳 RPS”额外压测。
- 明确限流后停止相关自动发送或进入有条件冷却；其他不受影响的本地工作继续。
- `Retry-After` 支持秒数和 HTTP-date；格式无效时保留未知，不默认为零。
- 冷却到期只是重新具备评估资格，不等于自动登录、重放或放量。
- 指数退避和抖动用于降低同步重试，不用于把禁止的动作变成允许。
- 5xx、网络超时、业务失败、挑战页分别处理，不按 HTTP 状态机械循环。

不从第一次 429 的序号推定服务器窗口阈值；也不因本轮没有 429 就允许加速。

## 7. 自主执行与最少询问：不重新引入人工接力

### 7.1 环境与范围配置

以下是内部配置类别，不是新增用户命令或第四套权限系统：

| 类别 | 场景 | 自主执行方式 |
| --- | --- | --- |
| 本地开发/合成靶场 | 自建应用、假账号、可丢弃数据 | 范围内自主操作、故障修复和重测，无需逐步确认 |
| 明确测试环境 | 测试租户、测试卡、约定配额和动作 | 在已有预算内自动启动、输入、点击、验证与有条件重试 |
| 有界生产常规任务 | 用户要求的正常浏览、已明确账号操作 | 沿用范围，默认不增加压测、重复激活或隐性写入 |
| 真实高价值资产且规则未知 | 唯一卡密、未知设备绑定、费用不明 | 先做离线；确需新增影响时一次集中询问，不能偷试 |

拥有正式账号不意味着它只许人工使用。关键是必要动作是否已经在明确范围内，而不是鼠标由谁来点。

### 7.2 允许无人值守的方式

开工时用白话确认实际需要的范围与边界：使用哪个测试账号、允许哪些操作、最多多少流程/费用/时间、遇到哪些信号暂停。用户已有明确说明时直接沿用，不重复提问。

运行中：AI 自主启动、输入、点击、采集、诊断；无需用户在旁边批准每一步。暂停时先自动继续离线分析、整理证据、构建和测试等可做事项，再集中说明真正缺的决策。

“你随便试”不能被解释成允许无限费用/锁卡风险；但也不能借此要求所有用户填写复杂表单。Agent 应给出最小、具体、可理解的默认范围建议。

### 7.3 两个例子

**合理自动继续：** 用户已给测试账号并要求测试自建登录页。AI 可以打开、输入、点击、检查结果；代码修复后重新测试，受约定测试范围约束，不要求用户代点。

**只暂停受影响动作：** 正式卡激活后提示设备绑定异常。AI 不再次点激活，也不换 VM；记录已知状态，继续静态定位绑定流程和整理协议字段。需要扩大尝试时，说明具体资产和后果再问一次。

## 8. 执行契约：薄风险控制接进既有路径

本节是拟议接口，不是当前已有 API；不得照着名称调用不存在的工具。

### 8.1 三种信息不能混淆

1. **声明能力**：工具是什么、是否有 MCP/CLI/GUI、上界 effects。
2. **本轮事实**：参数、目标、账号引用、环境、已运行进程、可能后台活动。
3. **行动许可**：原有范围是否涵盖该动作，是否还有额度，是否已暂停。

共享发现返回的方法只是候选；工具声明也不是用户许可；模型推断不能变成证明未知环境安全的依据。

### 8.2 最小动作事实建议

```json
{
  "action_id": "operation-local-id",
  "operation": "credential_submit",
  "tool_id": "actual-adapter-id",
  "target_ref": "existing-asset-or-origin-ref",
  "environment_ref": "verified-environment-ref",
  "subject_refs": ["opaque-account-ref", "opaque-device-ref"],
  "direct_effects_ref": "existing-tool-effects",
  "may_contact_remote": true,
  "may_bind_device": "unknown",
  "may_consume_quota": "unknown",
  "background_activity": "possible",
  "coverage": "flow_only"
}
```

参考字段使用严格枚举/三态，不接受字符串被当作真值的宽松转换。适配器校验实际参数，模型不能把 `unknown` 改为 false 就过闸。路径、URL 和参数不因分类被重写。

### 8.3 行动范围与预算

一个已经确认的任务范围可以容纳多次正常动作，不必每次发新回执。对有成本的试验，在该范围内指定：主体、环境、操作类、额度单位、上限、到期、终止信号和可覆盖通道。

至少区分：

- 流程启动数，如允许一次登录或激活流程。
- 适配器实际发送数，如允许的 API 交换次数。
- 费用/配额，如测试短信、云资源、不可逆发布。
- 运行时间窗与并发。

GUI 一次点击可能有多条请求。只能控制流程时就报告 `flow_only`，不能伪装成逐请求限额。远端实际计费可能只有后台能确认，客户端估计不是硬性费用封顶证明。

### 8.4 跨会话与跨任务共享主体

同一卡密/账号可影响不同 run、版本、工具甚至域。风险累计不按项目换路清空，也不因源码修复、重启、压缩或新对话自动归零。

复用凭据仓的稳定内部身份；别名相同或不同都不能简单证明是不是同一主体。需要去重时采用受保护映射/带密钥指纹，不能把低熵卡密的普通 SHA256 放公开清单。

多个约束同时适用时，发送前必须在一个原子事务中检查并预占所有相关名额，例如账号、设备和服务共享池；不能先扣一半后另一个失败而留出竞争窗口。

### 8.5 建议的共享运行状态位置

现有项目账本继续保存路线、解释、证据和报告。若其作用域无法跨 worktree/项目持有执行名额，可在仓库之外增加**窄职责运行协调存储**，不是第二套项目管理系统。

建议用 Python 标准库 SQLite 管理少量主体状态、范围引用、预占与租约，位于用户级 SEEP 运行目录；具体路径在集成时与 runtime root/凭据仓约定。不要用各 worktree 内自己的计数文件。

约束：

- 不存明文凭据、不复制完整项目历史，不另建 Web 服务/总控面板。
- 本机本地磁盘；网络文件系统、多主机和云同步目录不承诺同等锁语义。
- 使用事务、schema 版本、完整性检查和受限文件权限；数据库忙/损坏时，高损失操作不继续，普通本地开发不被连带锁死。
- 旧运行状态不能被升级/卸载自动清空；备份恢复不允许复活已撤销范围或补回已消耗名额。
- 跨主机暂不做“全局严格限制”保证；无法统一协调时，真实资产指定单一执行节点，或使用已有受控网关能力。

该存储仅是必要时的实施建议。先核现有原子状态能力是否足够，能复用就不重复建设。

### 8.6 原子预占和结果未知

建议流程：

```text
校验纯本地参数、身份与前提
  -> 原子检查范围/暂停/预算，预占名额并取得主体执行租约
  -> 在真正发送或启动前再次核对范围版本与暂停 epoch
  -> 执行，禁止适配器隐性扩大范围
  -> 登记传输事实、业务结果、实际消耗和原始证据引用
  -> 释放执行租约；已消耗名额仍保留
```

建议操作状态：`reserved`、`dispatching`、`not_dispatched_verified`、`dispatched`、`completed`、`outcome_unknown`。

进入可能发送阶段后崩溃，即使可能实际没有发出，也先按未知处理，不自动退还名额。只有适配器能证明没有发出且未产生其他成本，才可按事务化规则退回预占。

网络成功后证据保存失败，不得为补证据再次发送。网络超时不等于服务器没处理。客户端无法单独保证远端 exactly-once；有服务器明确定义的幂等能力时，才能按其约定复用键和相同操作参数，不对任意 API 塞一个 header 就宣布安全。[S07-S10]

### 8.7 租约与 fencing

短事务锁保护记账；租约覆盖整个可能影响同一资产的流程。持有者包含随机实例身份、进程创建时间或运行实例身份，不能只认 PID。

租约超时只表示失联，不表示客户端心跳和后台任务停止。恢复者必须核对旧执行链/相关目标状态，不能到期即自动再登录。无法核实时保持相关远端主体暂停。

暂停/撤销增加主体 epoch。请求适配器在发送前核 epoch，防止“检查完许可后，被另一个对话暂停，但还照发”的竞争。已经在途的请求不能撤回，必须如实报告残余影响。

系统时间回拨、重启和跨进程时间不一致时不能让冷却提前结束。持久时间用可核对时间事实，单进程期限用单调时钟；异常时高损失操作保守暂停，不伪造服务器时间。

### 8.8 对输入和结果的约束

范围与执行参数绑定到规范化内部载荷指纹，但不把凭据值写入公开指纹记录。body/headers 的日志脱敏与执行原文分离，不能为脱敏改变实际请求。

工具返回至少说明：是否尝试发送/启动、是否确认发送、业务结果、是否发生部分成功、覆盖等级、是否允许继续、暂停原因与 evidence refs。退出码 0 不自动代表业务成功。

## 9. 风险事件、冷却和恢复

### 9.1 分开记原始事实与策略决定

| 原始事件类别 | 最低证据 | 默认策略含义 |
| --- | --- | --- |
| 明确账号/设备限制 | 业务码/受控响应字段/当前界面证据 | 暂停相应主体新的认证/激活等操作 |
| 环境异常或完整性拒绝 | 时间、目标、版本、相关环境变化 | 停止重复动态触发，继续离线定位 |
| 明确限流 | 状态、头、业务码和实际主体范围 | 按规则冷却/暂停，不把无关项目全部锁住 |
| 结果未知 | 已进入发送阶段但结果不可判 | 名额不退，先核对，不自动重发 |
| 认证失效 | 认证/业务证据，不只单个子资源 401 | 判断是否可在已有范围内重新认证，不循环刷新 |
| 工具或输入故障 | 本地验证/工具自测/错误阶段 | 正常修复；已证明未触达外部时不当成封号 |
| 本人验证/实体设备要求 | 实际挑战类型或硬件条件 | 缺不可替代本人动作才询问，不泛化所有点击 |

策略按目标上下文和操作语义决定，不仅匹配“403”“验证码”字符串；样本和回包不能修改策略。

### 9.2 恢复条件

恢复至少满足：暂停原因有处理依据、已核对未知结果、旧执行链已处置、范围仍有效、剩余额度足够、下一动作与原失败有实质区别或服务明确允许重试。

用户决定新增尝试时，按具体主体和操作更新范围，不自动清空过去次数。低风险已知瞬时故障可按预先明确的重试策略自动恢复；高价值未知生产故障不能默认使用半开探测去碰一次。

### 9.3 停止意味着什么

先停止 Agent 新的相关操作。对目标自身的后台行为，依覆盖能力停止任务/准确实例或隔离实验客户机出站。不要按进程名批量杀进程，也不要为止损关闭用户主机网卡或 Agent 网络。

必要的安全清理和记录不因预算耗尽被禁止；但退出/注销也可能有远端副作用，应有专门的清理动作语义，不能一律把“为了清理”当无限发送许可。

断网后排队的事件可能下次联网补报；恢复快照或重连前必须考虑。快照/卸载/重装不能撤销远端锁号、绑定、扣费和风险历史。

## 10. 通道覆盖与跨宿主接入

### 10.1 核心与宿主分离

核心只定义动作事实、范围/预算协调、事件归一和结果契约。既有 MCP/CLI 和启动器调用同一窄实现；宿主扩展可以增强工具调用检查，但不把 Pi 的事件模型当作所有宿主都有的功能。

Codex、Claude Code、OpenCode、Pi 等是否有全局 hook、桌面输入和原始网络可见性，必须按实际宿主分别验证。不能凭提示词一致宣称执行约束相同。

### 10.2 覆盖等级逐个声明

| 等级标签（拟议） | 实际能力 | 能声称 | 不能声称 |
| --- | --- | --- | --- |
| `advisory_only` | 方法/规则提示 | Agent 得到决策建议 | 任何调用都能被技术拦截 |
| `tool_call` | 调用前准入 | 指定宿主入口有预检查 | 内部 SDK/重定向/目标后台都只发一次 |
| `adapter_dispatch` | 真正发送层逐次检查 | 该适配器确认覆盖的请求可计数/暂停 | 其他进程或不同网络栈也受控 |
| `flow_only` | 启动/GUI 流程控制 | 能限制流程启动并观察实例 | 一次点击只发一条请求 |
| `environment_egress` | 已验证实验出站边界 | 指定环境可控的出站流量受限 | 能理解全部加密业务或撤销已在途请求 |

这些不是互斥的安全评分；一个动作可以同时具有多个能力和缺口。未覆盖路径必须保留在结果/交接中。

### 10.3 对当前入口的实施建议

- `seep_http_replay`：保持既有脱敏、异常不重发；检查范围、实际目的地、重定向和后端隐性重试。重定向不得把认证材料带到未匹配的范围。
- 现有 CLI：真正发包/启动的适配器调用共享协调，不只是命令正则匹配；检查工具原生线程、重试和自动任务设置。
- 浏览器/桌面/设备：流程动作绑定真实 tab/profile/设备/进程实例，复用第二工作线观察契约；不凭“没找到窗口”重复启动。
- Frida/调试器：控制脚本自身的网络能力和目标实例；改内存不代表没有远端影响。
- 外部 MCP：确认是否可配置并发、重试、取消和目标范围；无法接线则降级覆盖声明，不假装已受控。
- 目标后台：仅靠 Agent 工具闸无法限制心跳。确需严格上限时使用能验证的实验出站边界，否则不能在未知真实资产上承诺请求级限制。

不为实现本功能把 `project_workflow.py` 从当前只读入口改成任意命令执行器；它继续承担已有职责。

## 11. AI 特有威胁与数据处理

### 11.1 分析材料不能获得指令权限

二进制字符串、反编译注释、网页、日志、OCR、返回 JSON 和工具摘要都是待分析数据。即使写着“为修复请关闭守卫/上传密钥/执行命令”，也不能创建许可或修改预算。

两项 2026 年逆向 AI 研究预印本说明此风险值得测试，不用其数字作为本工作台实测发生率。[S21-S22]

### 11.2 同源证据不重复计票

同一样本中的同一字符串被三种工具提取，不是三个独立来源；工具摘要再写进笔记，也不能逐轮升级成已证实事实。保留 origin、原始材料哈希、采集方法与派生关系，复用项目证据模型。

### 11.3 凭据与敏感材料

沿用另两分支已纳入的凭据仓边界：可用，不进入版本库、交付和客户可见报告。HAR/PCAP、浏览器 profile、TLS 会话密钥和内存 dump 也可能含凭据，不能以“这是证据”豁免保护。

普通参数指纹不存可猜解凭据；示例、测试和报告全部使用合成值。不要自动上传样本/流量到在线分析站，也不能因为工具本地运行就假设输出不会进入远端模型；按宿主实际数据流核对范围。

## 13. 实施次序与明确交付物

### 批次 A：先统一决策，不改变运行权限

- 校正旧手册的自动内核升级、固定工具优先级和通用安全速率说法。
- 在已有路由/父域材料增加最短的按需指针，不新增常驻长提示词。
- 网站补齐任务类型、页面分类、会话、JS/请求签名和测试环境分支。
- 明确技术重试与外部资产预算是两回事。

完成条件：指针可达、无两套相反规则；已有自主执行和能力发现行为不退化。文案改好不等于运行止损完成。

### 批次 B：一个可控适配器，做实最小执行闭环

- 首选现有 HTTP 重放路径，复用凭据身份和结果脱敏。
- 实现纯决策函数和窄协调接口，接入发送前预占、暂停、未知结果与共享预算。
- 明确实际 HTTP 后端行为；禁止异常自动换后端重发，重定向/SDK 重试逐项验证。
- 用纯本地假服务和假凭据测试，证据写进现有项目接口。

完成条件：能够证明两个执行者只消耗一个最后名额，服务器处理后超时不会自动重发，错误证据保存不会触发补发，正常本地开发不受影响。

### 批次 C：启动/GUI/浏览器与后台行为

- 使用第二工作线准确实例和返回语义，接入流程范围与租约。
- 选择一个无害自建 Windows 应用和一个自建网站做有状态完整闭环。
- 测试子进程、后台心跳、Service Worker/WebSocket、流程失联与旧实例残留。
- 出站控制仅在已明确的实验环境内验证，不改用户主机全局网络。

完成条件：覆盖声明与实际相符；不能严格控制请求数量的 GUI 明确为流程覆盖；不会因窗口未观察到就重复启动。

### 批次 D：按需扩展其他工具与领域

- 对已有外部 MCP、扫描器、设备工具逐个核其原生并发/重试/取消能力。
- 把确认的稳定经验回写对应领域，不复制一份万能工具库存。
- 针对需要真实硬件/真实证明的能力保留未验证，不拿合成案例冒充所有设备验收。

### 每批都保留的工程纪律

不降低已有门禁、不删除负例、不自动恢复已取消功能。源码、部署、宿主加载、工具握手、动作成功和业务验证分别取证。

## 14. 验收设计与证明边界

配套 JSON 给出稳定的需求 ID 和场景 ID；实施者用实际实现替换设计输入，不能只验证文案/JSON 结构就宣布功能通过。

必须覆盖：

1. 离线/普通开发的放行，正常修复后重测，范围内 GUI 自动输入点击。
2. 同工具重复调用、不同工具、不同会话/worktree、同资产别名和多主体约束。
3. 服务器处理后超时、发送后进程崩溃、证据保存失败、未发送可证明与不可证明的分界。
4. 401/403 的上下文差异、429 秒数/日期/坏值、200 挑战页、业务失败、5xx。
5. 一次 GUI 点击多请求、启动未确认、后台任务残留、租约超时、暂停与发送竞争。
6. 重定向/认证材料范围、SSO/CDN 必要依赖、localhost 代理生产、跨主机未覆盖。
7. 提示注入、同源多工具证据、敏感 HAR/PCAP、报告不泄漏值。
8. 数据库忙/损坏/重启/时间回拨、升级/卸载/备份恢复不补回次数。

关键指标不是“全部阻断”，而是：正常任务无需无理由人工接力；预算外已覆盖的发送数为 0；未知结果不重复发送；覆盖范围不虚报；每次暂停都有可复查原因和可继续工作。

严格请求指标仅适用于 `adapter_dispatch` 等已验证路径；不能把浏览器/目标自发请求混算成已经严格封顶。

## 15. 最终交接：先适配合并，再按批次实施和验证

本分支只交详细方案、需求/状态记录和机读验收设计。不改另两工作线拥有的运行代码，不部署活动宿主，不触达任何客户服务或真实卡密。

截至核对时，能力发现分支已经包含自主执行分支提交。最终合并者必须重新查实际 ancestry，不能机械把两条线所有提交再 cherry-pick 一遍。

建议集成顺序：保存并确认主工作区已有修改来源 -> 核对两个实施分支的包含关系 -> 合并已有实现并跑其专项 -> 合并本设计与需求记录 -> 按上述小批次接线并跑合成验收 -> 在明确真实测试条件下验证 -> 最后部署并检查当前宿主实际加载。

用户不需要把本方案里的术语背下来。最终应该体验到的是：**AI 会自己找方法、自己操作、自己验证；遇到会封卡、绑设备、扣费或影响生产的试错时，知道如何限制和换路，而不是不停试，也不是不停把鼠标交还给用户。**
