# Seep 跨宿主能力引用与使用链路：最终优化方案

> 日期：2026-11-01，Asia/Shanghai。
> 状态：用户已采纳的设计依据；首批核心实现及实际验证以 CURRENT-STATE 为准。其余设计建议不自动算已实现或验收通过。
> 本稿替换同路径上一版，不保留另一套并行方案。
> 核心定位：Seep 是跨 Agent 宿主的工作台。Pi、Codex、Claude Code、OpenCode 等是使用它的宿主，不是能力体系的归属。
> 改造尺度：保留九域、既有技能、MCP、脚本、知识库和项目记录，补齐发现、引用、组合和验证链路，不全面重构。

## 0. 先重新对齐本次对话的需求

### 0.1 起因

用户提供了一个真实 Pi Web 会话：Agent 长时间使用基础工具和自写脚本，未及时读取 Seep 专业技能、查知识库或利用既有工具入口；用户提醒后，方法选择和进度明显变化。

这说明需要检查和优化 Seep 的能力使用链路，不能仅以“技能已安装、MCP 已注册、文件存在、静态检查通过”判断工作台已经发挥作用。

Pi 是这次问题发生的地方，不是本次改造的目标平台边界。

### 0.2 用户已经明确的六项需求

1. Seep 是工作台，可接入多个 Agent 宿主，不能深度绑定某一个宿主。
2. 九域是现有专业能力的归属分类，普通开发也可以借用其中的方法、工具和知识。
3. 用户只用自然语言描述目标，不负责记内部命令、提醒查库或选择技术工具。
4. 相关技能、子技能、工具、MCP、知识库、配方、案例和样本，应能被合理发现、组合并真正使用。
5. 参考 Seep 上游、reverse-skill、Hacker Skills、P4nda 的专题方法和 REA，但必须适配本项目，不整体移植。
6. 不大改、不新增总管理框架；本对话只负责能力归属与引用使用链路，独立 worktree 工作，最后再合并。

### 0.3 上一版需要纠正的偏差

上一版把 Pi 事件、自动装配和 SDK 验证安排成实施主线，混淆了“某宿主如何增强接入”与“Seep 核心如何把能力组织并用起来”。

本稿纠正为：先完成宿主无关的资源关联、共享发现、统一引用和操作结果契约；各宿主通过通用规则、技能、MCP 或 CLI 使用同一套核心。可选宿主 hook 不决定核心成立，不是本轮必要改动。

本轮不把 Pi SDK 适配列为 Seep 核心问题，也不要求 Codex、Claude Code 等实现 Pi 的事件模型。

### 0.4 最终目标

> 不论在哪个宿主，Agent 面对一个实际问题，都能从 Seep 找到适用的方法、真实可用的执行入口和必要的验证办法；任务推进或受阻时，能继续找到相关辅助能力，而不靠用户反复提醒。

这里的“能用上”不等于每个任务调用全部资源；应做到该用的有入口、不该用的不强加、实际用了有结果、结论有依据。

## 1. 最终设计结论

### 1.1 九域不变，跨域借用开放

保留现有九个正式域作为专业维护、方法和判据归属，不新增“日常开发域”或“总控域”。

普通开发是用户工作的性质，不需要先被塞进九域。开发中的一个问题，可以调用任意适用的域内方法；专业任务也可组合主辅域。

例如：

| 用户目标 | 当前问题 | 可借用能力 | 不应发生的改变 |
| --- | --- | --- | --- |
| 实现登录功能 | 回调、PKCE、JWT 和会话绑定 | OAuth/OIDC、JWT、API 验证方法 | 不自动把项目变成渗透测试 |
| 开发协议客户端 | 帧结构和解码结果如何核对 | 协议分析、PCAP 提取、构包测试 | 不自动重放外部请求 |
| 排查自己的程序崩溃 | 符号、调用约定或模块边界 | 软件分析、运行时观测、取证方法 | 不固定走脱壳流程 |
| 发布软件 | 依赖清单与构建配置是否可靠 | 供应链方法、锁文件和已有 SBOM 检查 | 不把保留能力说成生成器 |
| 分析给定软件 | 有哪些保护，下一步如何取证 | 主域、脱壳专题、KB 和已有工具 | 不先盲写大量脚本 |

### 1.2 最小增量：一套共享发现逻辑，两个通用入口

建议在现有结构中增加一个窄职责、只读的资源发现实现：

- CLI：扩展现有 `Tool/scripts/route.py`，增加独立发现模式，保留原 `--resolve`。
- MCP：在现有 `seep` 服务增加一个薄封装的资源发现工具，调用同一实现。

两者只返回方法、资源关系、真实入口、适用条件及下一项建议，不执行目标、不建项目、不调度任务、不改变操作权限。

不建立新的总管理器、向量数据库、常驻服务、全局账本或宿主插件框架。

### 1.3 让链路贯通，而不是只增加“搜索工具”

```text
用户原始目标 + 当前问题 + 实际材料
    -> 共享发现：查现有方法和资源关系
    -> 读取：父域必要上下文 / 子技能 / 相关知识
    -> 选用：根据输入输出、环境和证据目标选择方法
    -> 执行：已有 MCP / CLI / 脚本 / 必要 GUI
    -> 验证：实际结果 + 对照 + 限制
    -> 留痕：沿用项目 / 版本 / run 或普通项目产物
    -> 遇到新问题再发现和组合
```

共享发现必须同时接入通用规则、技能导航、MCP 说明和现有配方。否则只会得到“又一个已经实现但 Agent 不使用的工具”。

## 2. 现有架构中保留什么

### 2.1 架构事实

以下来自本次对有关本地源码和文档的只读核对，不是对所有文件的完整审计。

| 既有组成 | 当前落点 | 本轮处理 |
| --- | --- | --- |
| 正式域身份 | 各域 `pack.json`、`lib/domain_registry.py` | 保持为唯一域来源 |
| 分类路由 | `Tool/scripts/route.py` | 保留分类职责，旁加只读发现模式 |
| 顶层与子技能 | `Tool/skill/<domain>/`、`subskills/` | 保留层级，补实际可发现性与跨域导航 |
| 能力记录 | `Tool/capabilities/*.json` | 复用输入输出、成熟度、引用和组合 |
| 能力组合检查 | `capability-gate.py` | 保留资格、无环和引用检查 |
| 任务配方 | `Tool/playbooks/` | 衔接发现与实际步骤，清理误导的统一流程 |
| MCP 服务 | `Tool/mcp/seep_mcp_server.py` | 增加一个只读薄入口，不整体重写 |
| 工具声明、依赖、通道 | `Tool/config/` 现有配置 | 分别消费，不合并成新权威表 |
| 知识库 | 现有 `seep_kb_search`、`seep_kb_read` 与 KB 路径 | 使用现有入口，不复制知识库 |
| 案例与样本 | `Tool/cases/`、`Tool/samples/` | 区分经验参考、见证和本轮证据 |
| 项目和路线 | `project_state.py`、`manager_state.py`、`project_workflow.py` | 保持，不另建状态体系 |
| 通用执行约定 | `Tool/prompts/AGENTS.md` | 写一次资源使用原则，不复制到各宿主 |
| 宿主接入模板 | `Tool/prompts/contracts/` 和现有配置生成 | 薄指针，加载方式分别验证 |

### 2.2 不改的根本边界

- 正式域仍由合法 pack 定义，目录数或来源仓库名不定义域。
- 主辅域和方法组合不改变用户原始目标、材料身份和操作范围。
- `project_workflow` 仍只控制经自身入口的动作，不宣称约束全部宿主调用。
- 受控执行中的工具、域和副作用检查不能因资源可发现而被绕过。
- 发现资源不触发安装、联网、目标执行或系统修改。
- 用户已有规则、凭据政策、原件保护和系统边界不属于本次重写范围。

## 3. 需要解决的真实断点

### 3.1 入口断点：资源存在，Agent 不知道什么时候找

技能简介、规则和资源路径都存在，但仅靠模型自发记忆容易漏用。真实会话已经出现长时间不读取相关专业方法的情况。

处理：通用规则与路由技能明确“出现专业未知、选择方法、准备重复试错或被用户点名资源时，先使用共享发现”；同时提供 MCP 和 CLI 两个等价入口。

不处理为：所有任务先跑完整分诊、查库、建案、报告。

### 3.2 粒度断点：只看域名，找不到具体问题的方法

子技能、references、配方、KB 和脚本可能隐藏在父域内部，普通开发很难仅凭九个域名判断哪个方法适合当前问题。

处理：按现有子技能简介、能力输入输出和资源引用发现专题；不必先阅读整个父域才能找到一个子方法。

### 3.3 引用断点：同样写“工具”，实际可能是不同对象

本地存在多种引用：能力 ID、外部程序 ID、脚本 stem、MCP 服务 ID、MCP 方法名、技能路径和 KB 文章路径。

必须区别：

- `tool:ida`：工具声明，不是一次可直接调用的 MCP 方法。
- `mcp:playwright`：MCP 服务，不是任何一个浏览器操作。
- `repo:kb-query`：脚本引用，不等于 MCP 的 `seep_kb_search`。
- `probe:sbom-build`：能力线索，不表示本机已经支持生成 SBOM。
- KB 中的 `die_scan`：可能只是其他生态的工具名，不能当作本机接口。

处理：返回带类型和来源的准确引用，不再让 Agent 靠字符串猜。

### 3.4 归属断点：维护归属被当成使用范围

某个方法归属 web-pentest，不代表普通开发不能读；某能力归属 softseep，也不意味着它引用的脚本一定在 softseep 目录。

处理：域归属、实际资源位置、方法适用范围、执行准入分别表达。

### 3.5 资格断点：文件存在被当成可执行能力

例如 `native-hook` 的记录有 `reserved`；`sbom-build` 有 `probe/reserved` 和只消费已有材料的限制。

处理：读取时继续消费原有资格检查。可以展示受限方法，但不能把它升级为自动执行能力。

### 3.6 方法到执行断点

读到知识库推荐方法后，Agent 仍可能调用不存在的工具或猜错参数；这次会话出现了判壳参数错误、超时和 KB 参数纠错。

处理：步骤引用真实接口；执行前查实际 schema；失败按具体阶段恢复。新发现入口要返回准确读法和限制，不只返回工具名字。

### 3.7 验收断点

“意图覆盖 100%”“所有链接存在”“工具退出 0”都不能证明自然语言任务能正确借用资源，或证明专业结论成立。

处理：把测试从词条命中延伸到资源可达、实际调用、结果核对及跨宿主使用。

## 4. 上游与参考项目如何适配

### 4.1 Seep 上游：保留技能调度 + MCP + 按需参考的骨架

参考：

- [上游 softseep 技能](https://github.com/angusdevgo/Seep-Reverse-Lab/blob/main/Tool/skill/softseep/SKILL.md)
- [上游 seep MCP](https://github.com/angusdevgo/Seep-Reverse-Lab/blob/main/Tool/mcp/seep_mcp_server.py)

读取到的上游骨架是：用户自然语言，经技能判断平台与问题类型，按需分发到技能、references、工具和 MCP，再执行与报告。

本地已演化为九域和独立路由，不应退回把 softseep 当全部任务的唯一总控。应保留“主入口负责指路、深度方法按需读、MCP 提供实际工具”的思路，并补齐本地资源关联。

上游针对安全任务的固定前置和开关，不自动成为本地普通开发的新要求；本项目当前用户需求优先。

### 4.2 reverse-skill：三轴选择与明确下一入口

参考：[PRIMARY 快路径](https://github.com/zhaoxuya520/reverse-skill/blob/main/skills/MASTER-ROUTING.md)、[路由脚本](https://github.com/zhaoxuya520/reverse-skill/blob/main/skills/scripts/master-route.ps1)。

借鉴：目标、意图、工具条件共同判断；给出主方法、辅助方法和“下一步读哪份技能”；缺工具沿真实清单恢复。

本地映射：`route.py`、pack、子技能、工具发现与现有证据。对方的 scope、时间线、路由配置和经验库不另复制一份。

边界：脚本输出“立即打开 SKILL”仍然不是宿主已读。需要通用使用约定和实际任务验收，不能把文本要求当执行事实。

### 4.3 Hacker Skills：观察驱动的分层专题与交叉引用

参考：[hack 总入口](https://github.com/yaklang/hack-skills/blob/main/skills/hack/SKILL.md)、[API 入口](https://github.com/yaklang/hack-skills/blob/main/skills/api-sec/SKILL.md)、[认证入口](https://github.com/yaklang/hack-skills/blob/main/skills/auth-sec/SKILL.md)。

借鉴：总导航、分类、深度专题分层；依据实际观察切换相关专题；API、认证和业务逻辑之间可连续调用。

本地映射：父技能保留专业导航，具体问题可直接发现子技能和必要参考，不强制加载所有安全测试步骤。

### 4.4 P4nda：小能力可嵌入大任务

参考：[reverse-skills](https://github.com/P4nda0s/reverse-skills/blob/main/README.md)。

借鉴：符号分析、结构恢复、插桩、局部模拟各有输入输出，可作为开发或分析的一个步骤使用。

不照搬：特定 IDA 导出环境成为所有任务前提，也不把“技能已安装”当作“引擎已安装”。

### 4.5 REA：真实接口和证据契约

参考：[REA 技能](https://github.com/morluto/rea/blob/main/.agents/skills/reverse-engineer-anything/SKILL.md)、[工具执行契约](https://github.com/morluto/rea/blob/main/src/server/contractToolHandler.ts)。

借鉴：实际工具清单优先；输入校验、结果、证据、限制和未知相互关联；不以文档工具名冒充当前接口。

本地映射：沿现有工具契约、MCP 结果契约和项目证据接口做定点增强，不安装完整 REA 服务。

### 4.6 共同结论

可借鉴的是资源组织和执行方法，不是来源仓库的全部制度。引用来源要保留到具体方法；任何来源的技能正文都不能覆盖宿主边界或当前用户要求。

## 5. 核心关系模型：从现有事实生成视图

### 5.1 统一“关联”，不统一搬家

```text
正式域 -> 维护父技能和专业判据
父技能 -> 导航到子技能、参考、配方
能力声明 -> 输入、输出、脚本、参考、组合与资格
配方 -> 在某类问题上组合能力和工具
工具声明 -> 可控制方式和执行通道
MCP 服务 -> 该连接实际暴露的方法与 schema
知识库 -> 方法、判据、坑点和历史生态信息
案例/样本 -> 经验或能力验证材料
项目/run -> 本次执行事实、证据和验收
```

这些关系保留在原有来源中。查询时生成一个只读视图，不建立另一份手填总表或图数据库。

### 5.2 单一事实源清单

| 问题 | 权威来源 |
| --- | --- |
| 有哪些正式域 | 合法 pack + `domain_registry` |
| 某方法是什么、何时用 | 技能、子技能、参考的实际正文 |
| 某能力输入输出与成熟度 | 现有能力 JSON 与资格检查 |
| 某配方引用了什么 | 配方正文与既有引用解析 |
| 某程序如何控制 | `tool-capabilities.json`、`tool-runtimes.json` |
| 服务如何注册 | `mcp-servers.json` |
| 服务此时有哪些方法 | 当前实际工具列表与 schema；不可得则标未知 |
| 调用依赖及副作用 | `mcp-tool-dependencies.json`、`tool-effects.json` |
| 文章实际在哪里 | KB 返回路径与根边界检查 |
| 案例角色是什么 | pack 的案例角色及原案例元数据 |
| 本次任务是否成功 | 当前材料对应的执行、对照与验收 |

生成索引和矩阵只做派生视图。不能用它们覆盖源文件、工具状态或本次证据。

### 5.3 引用类型需要明确，但不重写全部格式

沿用现有 playbook 的 `tool`、`repo`、`apk`、`mcp`、`probe` 等引用语义。发现结果中为不同资源标出类型和精确定位，不批量发明新的配方命名空间。

尤其注意：现有 `playbook-capability-aliases.json` 只登记某些 `repo` 脚本别名，不是通用 MCP 方法映射表。不能拿它给任意文章工具名做自动替换。

### 5.4 稳定身份与可打开路径分开

同一方法在不同宿主可能有不同部署路径，但应保留同一资源身份，例如父域加子技能相对路径。

查询输出同时说明来源根、资源相对身份和当前可读入口。路径不存在、部署陈旧、同名歧义必须明确，不靠宿主名称或本机盘符猜。

## 6. 共享发现实现

### 6.1 职责

只回答：

1. 这个问题有哪些相关现有资源？
2. 哪些适合当前输入，哪些只供参考或需要补材料？
3. 应先读哪份方法，实际执行入口在哪里？
4. 哪些依赖、工具状态或验证要求仍未知？

不回答：整个任务是否完成、是否获得新的执行授权、下一条任意 shell 应自动运行什么。

### 6.2 实现落点

推荐新增一个无宿主依赖的只读 helper，例如 `Tool/scripts/lib/capability_discovery.py`，由现有 route 和 MCP 服务共同调用。

它不是新管理器：不保存任务状态、不选定路线、不启动进程、不调模型、不建项目、不安装工具、不 import Pi/Codex 客户端库。

需要 IO 的加载与纯候选排序分别可测试。模块导入期不遍历资源、不写缓存，不触发服务启动。

### 6.3 为什么需要共享 helper

如果 CLI 在 route 中一套、MCP 在服务里一套，就会再次产生路由、过滤、成熟度和路径漂移。应共享同一读取和候选解释逻辑，传输封装保持很薄。

现有 `capability-gate.py` 的私有函数不是稳定公共 API。确需共享资格判据时，仅抽取窄读取/校验函数，保持原门禁语义和测试；不得在每次查询中运行全量 gate 或写覆盖矩阵。

### 6.4 输入建议

以下为拟议契约示例，不是已实现接口：

```json
{
  "query": "实现 OAuth 登录时如何验证回调与 PKCE",
  "user_quote": "给我们的应用增加登录，并补测试",
  "context": {
    "operation": "design-and-test",
    "material_kinds": ["source", "sanitized-config"],
    "observations": []
  },
  "limit": 5
}
```

约束：

- `user_quote` 原样保留，不能加审计前缀、同义词或其他任务内容。
- `query` 是当前检索问题，可以是用户原句，也可以是 Agent 的明确工作问题；来源需可区分。
- `context` 可省略；它是适用性线索，不是权限声明或新的项目配置。
- 观察带来源，推断不能写成已实测。
- 域只能作为非排他提示，不过滤掉其他域相关方法。
- 输入大小有界，不接受整段会话、完整客户源码、dump 或真实凭据作为检索数据。

### 6.5 输出最小契约

| 字段 | 作用 |
| --- | --- |
| `status` | `matches`、`no_matches`、`partial` 或明确错误 |
| `resources` | 方法资源及准确入口 |
| `why` | 来自意图、材料、输入输出或观察的依据 |
| `applicability` | 适用、需补输入、只读参考、当前不适用等 |
| `execution` | 已注册入口与资格；没有则为空或未知 |
| `limitations` | 环境、成熟度、工具、材料或验证边界 |
| `next` | 先读方法、查 KB、核 schema 或选择对照的建议 |
| `sources` | 当前读取来源与必要版本指纹 |
| `continuation` | 其余候选和正文的准确入口 |

这些是资源查询结果，不是第二份状态账本。不能写 `task_pass=true` 或把一个候选标成已验收。

### 6.6 首版发现范围

先读取：合法 pack、父/子技能 frontmatter、既有导航、能力输入输出、脚本/参考引用和配方元数据。

知识库全文搜索继续走已有搜索入口，不在首版重建全文索引。案例先用角色及元数据，不遍历其原始二进制、抓包或内存文件。

若某类资源缺乏可靠元数据，输出明确不完整并定点补描述；不为“搜得到”批量创建假的 usable 能力。

## 7. 两个入口，一份语义

### 7.1 CLI 入口

扩展现有 route，而非新增另一套路由脚本。拟议形式：

```text
python Tool/scripts/route.py --discover "当前问题" --json
```

复杂上下文可用一个有界 JSON 输入选项。具体参数在实现时固定，保持 `--resolve`、`--index`、`--check` 和原输出兼容。

`--resolve` 继续做领域候选；`--discover` 做跨域资源发现。没有专业资源匹配时，后者正常返回空集合，不提示普通开发用户必须选择一个域。

CLI 不启动 MCP 服务，不需要 Pi 环境，也不因为某宿主未登录而无法查询本地资源。

### 7.2 MCP 入口

在现有 seep 服务中增加一个工具，建议名称 `seep_capability_discover`；最终名称在实现 PR 固定。

职责与 CLI 相同，调用同一个 helper。完整注册包括：真实 schema、结果预算、依赖声明、副作用声明、契约检查和正反例。

工具说明明确适用场景：选择现有方法、普通开发中借用专业能力、分析前查资源、受阻后寻找替代；不描述成“仅逆向任务可用”。

不得在这个工具内部自动调用目标分析、重放、安装或另一个模型。

### 7.3 当前工具状态的边界

MCP 服务能准确说明自身提供的方法；它通常不知道宿主连接的其他所有 MCP 服务。

因此：

- 本服务自身方法可以关联真实注册及其 schema。
- 外部 MCP 服务默认只报配置/声明；实际暴露和连通由宿主按其现有工具列表核对。
- CLI 不把静态 AST 方法清单称为当前连接成功。
- 不起额外客户端后台探测所有服务，不为了资源发现拉起 GUI 或改配置。

### 7.4 CLI/MCP 一致性

相同资源基线、输入及选择条件，应产生语义一致的资源身份、适用性、资格和限制。只允许传输包装、实际路径及本连接已知状态不同。

测试必须验证这一点，避免宿主不同得到两套分类和能力资格。

## 8. 相关资源如何被选中

### 8.1 两阶段判断

第一阶段召回候选：任务意图、当前问题、材料、实际观察、输入输出、既有引用和 compose 关系。

第二阶段核对适用：是否回答当前问题、前提是否满足、是否确有入口、是否有副作用、是否需要补证据。

文件后缀、单一缩写、工具名和“分析”等宽泛词只作弱线索，不独立决定专业路线。

### 8.2 当前已确认的误命中

只读复现显示：React 白屏命中 softseep 的逆向/脱壳；会员订阅页面命中卡密审计；普通 Python 测试被判未分类并要求问用户。

先做定点修复：独立缩写边界、实现/审计/分析的语境、无专业需求的正常出口。不要通过继续加大量词把所有开发都纳入 softseep。

旧 route 的合法主辅域案例保留；发现模式和分类模式分开测试，不为新模式改坏旧契约。

### 8.3 提供多少资源

首屏给少量有解释的主要与辅助资源，余项可继续查看。正文按需展开，保留必要约束，禁止截断后说已完整读取。

候选排序不能静默删除旧 route 的完整命中集合。摘要预算只决定展示，不改变资源是否可达。

首版采用确定性元数据排序和 Agent 语义判断，不引入后台模型调用、向量服务或未经校准的成功概率。

### 8.4 源坏不等于无匹配

损坏 JSON、缺文件、部署漂移、错误根和同名歧义应返回明确诊断或部分结果；正常无匹配才是 `no_matches`。

不能因坏资源抛异常使整个发现器崩溃，也不能把它静默过滤后告诉用户“无需工具箱”。

## 9. 让各宿主的 Agent 都有同一条使用约定

### 9.1 通用规则只写一次

在 `Tool/prompts/AGENTS.md` 中，用简短规则说明：

- 面对需要选择专业方法的新问题、明显受阻或准备重复造轮子时，优先查 Seep 的相关现有能力。
- 使用 MCP 发现入口；无该入口时用等价 CLI；两者都不可用时按现有技能和 KB 指针直接查，不把任务全部锁死。
- 阅读选中方法的实际正文，核输入输出与适用条件；不要只看名字。
- 跨域可借用，主任务不被改写；没有相关能力就正常继续。
- 已有等价能力优先；手写脚本允许，但要说明既有能力不适用处和验证办法。
- 查到了不代表用过，用过不代表验证成功。

这不是“每次回答前都必须查库”，也不是为每次小改代码建项目。

### 9.2 技能入口要承担导航责任

`seep-router` 从“所有任务的第一步”调整为“专业判型与能力选路入口”，明确普通开发可直接发现和借用子方法。

父技能保留方法和专业判据，子技能导航明确：何时使用、输入、产出、必要工具、相关 KB/参考及返回内容。

已有子技能不全部提升为顶层技能；也不要求必须完整读完父域所有内容才能借用一个专题。

### 9.3 接入模板只负责指向共同核心

现有 `Tool/prompts/contracts/` 保留宿主接入说明，指向共同规则、技能和 MCP/CLI 入口，不在每份模板复制领域路由、工具清单或知识正文。

检查各模板是否实际被相应宿主加载；模板存在不等于已生效。不同宿主保留自身规则优先级和技能发现方式，不互相模拟。

### 9.4 MCP 本身也提供导航

在现有 seep 服务器说明和新发现工具 description 中增加准确的资源使用指引，让只连接 MCP 的宿主也能看到入口。

这只是提高入口可见性，不声称所有客户端都读取 server instructions。必须通过工具列表和真实任务验证。

### 9.5 不把 hook 作为成立条件

Pi 自动注入、Codex 的特定插件能力或其他宿主事件，都只可作为后续可选增强。

本轮核心验收要求：不加载任何 Pi 扩展时，共同技能、共享查询、MCP/CLI 和既有执行链仍能工作。

本方案不修改 Pi SDK、不要求宿主替换 Agent loop、不把某宿主的登录或事件回调作为 Seep 核心依赖。

## 10. 方法、工具与执行链如何接起来

### 10.1 一个候选必须有可走的下一步

不能只返回“用 IDA”“查知识库”。应明确：先读哪份方法、输入是什么、当前可调用入口及其待核对状态、下一项能支持什么结论。

例如分析 PE：先读相关主域/专题，选择静态画像工具，依据真实 schema 调用，再针对观察查 KB；不是所有 PE 一律先完整脱壳。

### 10.2 工具、服务和方法不能互相冒充

工具声明可控，不代表本机已找到；本机找到，不代表服务已启动；服务可达，不代表当前目标正确；调用成功，不代表任务完成。

现有 `tool-acquire`、doctor、运行通道与工具契约继续处理这些事实，发现器只引用。

### 10.3 故障恢复沿已有路径

| 故障 | 应走的路径 |
| --- | --- |
| 方法无匹配 | 正常工程方法或明确能力缺口，不强塞域 |
| 技能/KB 路径坏 | 核源码根和实际返回路径，不整盘搜索 |
| 参数错误 | 读 schema/错误中的字段并修正，不猜多个变体 |
| 工具缺失 | 既有发现/获取链；副作用按当前政策处理 |
| MCP 不通 | 区分注册、启动、端口和握手，使用已有诊断 |
| 调用超时 | 确认是否仍在执行或结果未知，不原样重复重型操作 |
| 工具不适用 | 换等价能力或明确限制，不继续强用 |
| 当前路线证据不足 | 重查相关方法/案例，选择最小反证实验 |

本轮不新增另一套熔断或全局自主策略；向既有路线机制提供准确资源与故障原因。

### 10.4 受控执行不因跨域而放松

读取辅域方法无需把所有域加入项目。但真正经 `project_workflow act` 等受控入口执行时，仍按原主辅域、动作、资产、generation 和副作用检查。

需要补辅域时先核现有接口是否支持安全更新；不假定存在未核实的 `add-domain`，不把所有 tools 加进所有 pack，不绕过执行器改跑 shell。

## 11. 知识库引用优化

### 11.1 不新建第二份 KB

继续使用现有 `seep_kb_search`、`seep_kb_read`。CLI 可使用现有离线 `kb-query.py`，但它与 MCP 搜索算法不同，不能宣称搜索结果天然完全一致。

共享发现先返回相关专题与精确检索入口；专业未知明确时再用实际搜索。首版不为强行同分重写两套搜索，更不复制所有文章到技能目录。

### 11.2 文章工具名的处理

分成：本机实际提供的方法；已核实输入输出等价的现有替代；仅为文章背景、尚未接入。

不得按名字相似自动换 MCP 方法，不把 donor 的 `mcp_tools` 元数据当本地安装状态。当前步骤指引必须使用真实 schema。

### 11.3 查库要改变工作方法

有效使用应能解释：资料解决哪个未知、采用了什么办法、前提是否满足、下一项验证是什么、结果支持什么。

这些可用一句步骤说明和原输出引用表达，不强制长报告；但不能用“检索成功”代替方法采用和验证。

### 11.4 保持资料与指令的边界

第三方技能、KB 和案例是方法材料，不提升为宿主最高规则。自动安装、全局网络修改、越过守卫等正文不能改变本地操作边界。

## 12. 配方和资源引用的定点清理

### 12.1 当前已读到的具体不一致

`Tool/playbooks/README.md` 目前有“先写 scope.md”和“所有配方最后跑 preflight”的统一描述，部分具体配方也带固定旧阶段说法。

与当前需求核对时，必须区分：资源/配方结构检查，具体目标验收，以及现有项目身份记录。结构 preflight 通过不能自动证明专业任务成功；普通开发借用方法也不应被固定 scope 文件流程绑住。

### 12.2 修复方式

只修相关入口及已确认误导：

- 配方为适用任务的可复用方法，不是所有任务的前置。
- 项目和证据沿已有项目/单案接口，不另要求平行状态文件。
- 步骤引用的脚本和能力要可解析；真实工具条件在执行时核对。
- 收尾按当前任务的具体判据；结构检查单独报告。
- `probe/reserved` 明确不算已安装自动能力。

不批量重写全部配方，不因历史路径存在就把历史流程恢复成强制主链。

### 12.3 新增方法的规则

以后导入外部技能时，除了文件、frontmatter、父导航和部署，还需验证它能被共享发现，并且具有能走通的输入、引用和验证出口。

不为导入一份技能自动创建新域、工具别名、case 框架或宿主专用管理器。

## 13. 案例和样本如何参与

### 13.1 案例是方法参考，不是万能答案

发现阶段优先用案例元数据、问题类型、保护、已证方法和限制。历史客户路径、服务或原件缺失时保留边界。

`witness`、`depth_gate`、历史参考、合成夹具和归档必须区分。某案例存在不能证明当前工具、当前目标或当前结论成立。

### 13.2 样本用于特定验证

需要核对工具链、解析行为或方法可行性时，才选择适合的小样本。样本运行与只读解析分别处理，不能为了“把样本用上”每次都执行它。

样本结果记录样本身份；不能绑定成当前客户材料证据。

### 13.3 经验沿原路径沉淀

任务事实先留本项目；稳定重复的方法再更新已有技能、KB 或配方。不能自动把每次模型推断、失败脚本或客户秘密写成全局知识。

## 14. 结果契约：与宿主无关地核对实际使用

### 14.1 五个层次分别表达

| 层次 | 可证明什么 | 不能证明什么 |
| --- | --- | --- |
| 资源可达 | 路径/注册与引用存在 | 已被模型读取 |
| 方法已读取 | 实际正文/章节已返回 | 模型理解并正确采用 |
| 工具已执行 | 某调用有输入、输出和错误状态 | 内层业务成功 |
| 结果已验证 | 明确对照支持或否定某项结论 | 整个任务或九域全完成 |
| 项目验收 | 当前资产、版本、run 的具体标准通过 | 任意版本或未知目标也能通过 |

### 14.2 沿用现有记录

有 Seep 项目时沿现有原输出、证据、claim 和验收接口；普通开发只借用方法时，可留在现有项目代码、测试和任务记录，不强制建 Seep case。

不新增全局 `capability-state.json`、操作事件库或第二个完成标记。没有可靠观察渠道时，不捏造“已读取”或“已执行”。

### 14.3 MCP 新入口采用清晰业务状态

新发现工具的无匹配、源坏、参数错和资源约束分别表达；不能把字符串中的 `[ERROR]` 包成无条件业务成功。

旧工具已有消费者，不能一轮改写全部返回格式。先对本次真实暴露的参数提示、KB 长度提示、超时诊断和工具名漂移做独立小补丁，分别测试兼容性。

### 14.4 包装调用的诚实边界

codemode/bash 外层成功不代表内层 MCP/脚本业务成功。能取得实际结构化结果就核对，拿不到就标明观察范围。

本方案不承诺解析任意 shell 程序的全部内部动作，也不依赖某宿主特定事件才能保留工具原输出和专业验证。

## 15. 既有检查如何增强

### 15.1 不再只检查“名字命中了”

保留原路由、意图和链接测试，但增加以下链路检查：

```text
用户说法 -> 相关资源 -> 真实正文/入口
          -> 实际调用 -> 输出条件 -> 结果验证
```

每层都有正例与反例。静态覆盖结果只证明该层，不写成总体能力成熟度。

### 15.2 结构检查补什么

- 子技能身份和路径可解析，同名跨父域不串。
- 能力成熟度、reserved、compose 和旧检查口径一致。
- 配方的引用类型正确、脚本歧义不乱选。
- MCP 新工具的方法、依赖、副作用和实际注册闭合。
- KB 中外部工具提示与本机调用资格不混淆。
- 导入、部署和改源码根后资源身份保持，坏映射明确报告。

### 15.3 使用检查补什么

- 普通开发无匹配可继续，相关时能借用方法。
- 专业任务无用户提醒也能找到并读取相关方法。
- 工具失败后核 schema/恢复入口，而非盲试。
- 输出中的推断、未知、已证和未满足条件不互相冒充。
- 手写脚本有必要性和验证方法；已有能力不适用时不强迫复用。

## 16. 跨宿主接入与验收

### 16.1 接入分层

| 层 | Seep 提供 | 宿主负责 |
| --- | --- | --- |
| 通用内容 | 规则、技能、配方与资源引用 | 按自身机制加载并遵守优先级 |
| 共享发现 | 同一 helper、CLI/MCP 契约 | 使用可用通道调用 |
| 实际工具 | seep 工具、已有脚本与外部工具通道 | 当前连接、schema 和用户侧交互 |
| 项目验证 | 资产、证据、原输出与验收 | 将实际结果交回，不伪造状态 |
| 可选增强 | 后续可用的接入说明 | 如有 hook，可增加提醒或自动呈现 |

前四层不依赖 Pi。第五层不是首轮完成条件。

### 16.2 至少两个不同宿主的真实见证

首轮选择用户实际使用的 Pi 和 Codex，各运行：

1. 一个不需要专业能力的开发任务。
2. 一个开发中借用专业方法的任务。
3. 一个九域专业小任务。
4. 一个已有工具不可用、需要合理替代或明确限制的任务。

不允许在测试前替 Agent 手工调用 route、读取技能或指定“必须使用哪个工具”，再把结果算成自然语言入口成功。

无法访问某宿主或模型时，报告该宿主未验证，不以另一宿主通过替代。其他宿主暂只报告内容/CLI/MCP 契约可用，不宣称真实接入已完成。

### 16.3 对“保证遵循”的准确回答

Seep 可以保证受控核心中的路径解析、资格判断、接口校验和结果契约；可以用真实任务证明某宿主的 Agent 是否使用了链路。

Seep 不能仅靠技能文字保证任何模型永不遗漏，也不能在不控制所有宿主执行通道的情况下宣称全局强制。要降低漏用，采用共同入口、短规则、多处准确导航、实际工具结果和失败回查，而不是虚构一个跨宿主硬控制能力。

这不等于放任不管：某宿主在验收任务中反复漏用，就应判该接入未通过，继续修入口和导航，而不是说“模型问题所以已完成”。

## 20. 测试方式与完成条件

### 20.1 四级验证

1. 单元/契约：临时资源根测试身份、引用、资格、输出和诊断，不启动外部工具。
2. 结构回归：现有路由、域注册、能力组合、工具契约、子技能、导入部署和项目证据测试。
3. 链路任务：真实读取方法并调用现有小工具，用公开或自建材料核对结果。
4. 宿主任务：至少 Pi 和 Codex 的自然语言见证，不先人工替 Agent 选路。

每一级分别报告，前一级不替代后一级。

### 20.2 性能与体积

先测资源读取和输出体积，再决定是否需要派生缓存。首版无向量库、无全文复制、无后台模型、无启动全部 MCP。

输出预算控制展示，不能静默删掉限制或把不完整结果称为完整。缓存如确有必要，键包含源码根及内容版本，不保存用户完整任务和秘密，不成为权威表。

### 20.3 评价重点

- 相关资源是否在用户提醒前进入工作过程。
- 是否真的采用适用方法并得到有用证据。
- 无关资源是否误导甚至误执行。
- 工具错误后是否按真实接口恢复。
- 首个有效证据之前的无效尝试是否减少。
- 普通开发是否仍轻量，跨域是否保持原目标。
- 换宿主是否保留同一引用、资格和结果语义。

不以调用次数越多越好，也不以删掉失败任务抬高“覆盖率”。

### 20.4 可以报告完成的条件

核心、两个入口、导航、引用和相关回归通过；九域及混合任务有实际链路结果；至少两类宿主有真实入口见证；既有适用完整检查实际运行；未知和失败范围如实保留。

`--fast`、工具列表、文件同步、意图命中或某一个样本成功，都不足以宣称整项完成。

## 23. 最终建议摘要

本轮只补四件核心事：

1. **把已有资源关联清楚。** 域、能力、方法、脚本、工具、服务、文章和案例各自身份清楚，引用可解析。
2. **提供跨宿主的共同发现入口。** CLI 与 MCP 同一实现，任务按当前问题找资源，普通开发也能借用。
3. **把入口接回既有技能和配方。** Agent 不再只看域名，也不把查库、读方法和工具选择全留给用户提醒。
4. **用实际链路而不是库存验收。** 方法读了、工具跑了、结果核对了，哪些仍未知明确留下；在不同宿主分别做自然语言见证。

最终形态仍然是现有 Seep 工作台，只是其方法、资源、执行和验证之间的连接变得准确、可用、可复查，而不是变成 Pi 专用系统或再多一层管理平台。
