# 为什么有这个对话：Seep 跨领域决策质量优化与接续方案

## 0. 先读这里：本对话不是第四次重做工具接入

本对话起因于用户的真实经历：分析带保护的软件时，Agent 反复启动、调试和抓包，最后出现卡密被封、设备受限；即使没有封禁，反复脱壳、Dump、反编译和追版也可能花费大量 token，却没有推进用户想要的功能。用户进一步问：工作台虽然有技能、MCP、知识库和工具，是否仍然不能让 Agent 主动判断“为什么做、值不值得做、什么时候换路”？

本对话的研究结论不是“现有能力没有用”。main 上已经存在判型、权威归属、脱壳价值、失败换路和证据要求。真正的痛点是：**方法可找到，不等于会被选用；工具执行成功，不等于用户目标获得新证据；本地可回滚，不等于远端账号/设备后果可撤销。** 优化目标是让已有方法成为可检查、可接续的判断过程，而非继续增加工具数量或长篇“必须”提示词。

用户说明另有三条工作线：能力发现/引用、自主操作、保护与风控识别。前两条已经组合，第三条正在适配它们，尚未合入 main。本线必须独立 worktree，不碰其他对话的未提交改动，也不把对方已经做好的功能再做一份。

2026-11-01 用户明确要求本线：先写详细缘由与方案，再按方案实施优化；覆盖现有九域及日常开发，不只优化 Windows 脱壳。以后由用户指定在本对话或其他对话合入 main。本文件是研究背景、设计和交接材料，不替代 REQUIREMENTS 的需求权威或 CURRENT-STATE 的状态权威。

压缩/换会话后恢复顺序：`REQUIREMENTS.md` → `docs/CURRENT-STATE.md` → 本文件 → 本分支 git diff 与实际测试日志。不要只读旧聊天里对 main 的判断，然后重复修复已在集成分支解决的问题。

## 2. 四条线的职责，不重复建设

| 工作线 | 主要回答 | 本线如何对接 |
|---|---|---|
| 能力发现/引用 | 已有方法在哪里，如何读取/调用，何时允许临时脚本 | 复用共同 CLI/MCP 入口和短提醒，不再造检索器 |
| 自主操作 | Agent 能做的启动、GUI、输入、验证为何不应交给用户 | 不恢复逐步回执，不用“不确定”要求用户代做技术操作 |
| 保护/风险感知 | 谁异常、请求在哪一阶段、外部试错额度、暂停和恢复 | 复用 runtime-risk/diagnose，不复制账号额度数据库 |
| **本线：决策质量** | 这一步回答哪个问题、什么证据改变判断、成功输出是否有收益 | 在既有 Manager 中补可选决策上下文和专业进展复核，配场景验收 |

“先判断”不是“每一步先问用户”。已有范围内的技术判断与操作由 Agent 完成；只有真实缺用户独有输入、新增影响或范围变化时才集中询问。暂停线上动作后仍可整理证据、读代码、离线实现和测试。

## 3. 研究发现与需要纠正的旧判断

### 3.1 main 已经有的方法

- `Tool/skill/seep-router/SKILL.md`：目标、保护、关键判定位置与上限。
- `Tool/skill/unpack-loop/SKILL.md`：判据驱动，不必完成所有脱壳步骤，先判脱壳收益。
- `Tool/skill/unpack-loop/references/ace-and-commercial-walkthrough.md`：账号/机器标记、服务端封禁、时间预算、取得 Dump 后的下一问题。
- `Tool/scripts/case_state.py` 与策略矩阵：按缺件和仪器记录过滤路线。
- `Tool/scripts/manager_state.py`：现有项目中的路线、证据、等待、失败和重规划。

### 3.2 冻结集成基线已补上的能力

`Tool/playbooks/risk-aware-analysis.md`、runtime-risk 同核 CLI/MCP 已具备异常诊断、HTTP 单次发送、共享主体额度、未知结果暂停、冷却及显式恢复；Windows 新启动还有可选流程边界。能力短提醒已接在既有 Pi 提示词装配中。

因此，本对话上一轮基于 main 得出的“缺共享远端试错控制”等判断，不能原样用来指挥新开发。现在要继续核对的是覆盖范围、采用效果，以及**工具没有报错但研究没有推进**的问题。

### 3.3 仍有价值的明确增量

1. 路线可说明“使用什么”，但不一定说明“用它区分哪两个候选解释”。
2. 工具成功与专业进展不同：重复成功导出同类文件，可能没有缩小任何未知。
3. 现有工具错误熔断按错误结果计数；不适合替代专业结果复核。
4. 工时/成功率先验不是当前目标的统计保证；任务成本上限需要依据和适用范围。
5. 新技能、配置、单元测试通过，不能证明自然语言 Agent 在真实复杂任务里会作出相同选择。

## 4. 跨领域的共同判断方法

只对存在路线取舍、外部影响、重复空转或需要接续的专业任务使用完整方法。简单代码修复直接读改测，不为一句问题建立完整案件。

这里的“角色意识”不是再加一张人格卡，也不是每次启动一组子代理。主 Agent 需要承担五种判断职责：任务定义者核验收目标，领域分析者选适用方法，实验设计者找区分证据，结果复核者主动找反例，维护交接者判断后续成本和适用版本。可以由同一个 Agent 按问题完成，不增加常驻服务、必需多代理或额外 token 仪式。各域改变的是专业证据与后果，不改变这几个共同职责。

### 4.1 动作前：六个问题由 Agent 自己回答

1. **目标**：用户要什么可验收结果？分析、修改、独立实现和上线不是同一目标。
2. **未知**：现在最影响路线的未知是什么？不要同时铺开所有问题。
3. **区分实验**：这个动作得到什么分别支持/反对当前解释？仅“运行工具看看”不足。
4. **替代路线**：是否有利用现有材料、更少侵入或更低维护成本的办法？不用为了调用库存而调用。
5. **代价与边界**：本地、远端、隐私、配额、生产状态、时间/token 和后续维护分别考虑。
6. **结束条件**：拿到什么就停止这一小步？没有新信息、出现风险信号或额度不足时怎样继续离线工作？

不要求未知事实被强行填成确定值。不能因为静态材料不足，就猜测壳名或服务端权威；不能将一次闪退、403 或工具崩溃单独解释成封禁。

### 4.2 动作后：把工具结果与专业收获拆开

工具返回码、产物和业务后置条件各自记录。专业复核允许三种声明：

- `new_evidence`：已有证据确实缩小了未知，说明改变了哪个判断；否定原假设也是进展。
- `no_new_evidence`：动作成功或失败，但没有新增可用信息。
- `inconclusive`：结果不足以判断，写出仍缺的区分证据。

上述都是调用者的专业判断，不是语义验真器。真实证据仍按已有项目身份、run、哈希和时效校验；一份新文件不自动等于新知识，相同字节也可能在新的受控条件下构成有意义的重复验证。不能用文件数量或哈希新鲜度代替语义。

### 4.3 何时换路、何时继续

- 明确新证据支持继续：保留既有自主操作，不向用户转交本可完成的工作。
- 同一路线连续两次已复核为无新增证据/无法裁定：在 Manager 范围内要求重规划，不能因工具 exit=0 清掉专业停滞。
- 真实假设被推翻：这是进展，解释改口原因后自主选择新实验；不是把“失败假设”算成工具坏掉。
- 编译修复、测试迭代、负例成功：有新诊断不属于本线的专业停滞，不把所有任务机械两次即停。已有 Manager 的连续工具失败条件仍保留；命中时由 Agent 通过原 replan 记录诊断后的实质修正，不要求用户代做，也不以 new_evidence 清除原失败条件。
- 遇远端限制或未知结果：交给现有 runtime-risk 的暂停/核对流程，本线不解除额度或冷却。

## 5. 最小实现：扩展现有 Manager，而不是新建“大脑”

### 5.1 路线的可选 `decision` 上下文

在既有 route 对象中支持一个可选、受限的对象，包含：

| 字段 | 含义 |
|---|---|
| `question` | 这条路线需要回答的具体问题 |
| `supports` | 哪种可观察结果支持当前解释 |
| `refutes` | 哪种结果否定当前解释 |
| `alternative` | 更低成本或不同原理的候选路线及取舍 |
| `cost_limit` | 本轮成本/停止上限与依据；不是虚构实测 token 数 |
| `impact` | 本地/远端影响、可回滚边界及未知，不充当授权证明 |

通过现有 `plan --route-json` / `replan --route-json` 使用，不增加要求用户填写的表单，不强制历史 route 迁移。字段有界、拒绝错误类型和未知字段，继续走既有敏感值检查。无需把全部技术细节常驻提示词。

### 5.2 尝试的可选 `progress` 复核

在既有 attempt 中支持 `progress={assessment,reason}`，CLI 用 `--progress` 与 `--progress-reason`。两者同时提供；API/CLI、落盘重放均校验类型和内容。没有 progress 的历史记录/自动工具捕获保持兼容，不假装已经获得专业复核。

同一路线的显式复核独立计数：两次 `no_new_evidence` 或 `inconclusive` 触发现有 `replan_required`；明确 `new_evidence` 才重置专业停滞计数。未复核动作既不凭空算失败，也不能当成语义进展清零。路线切换不会抹掉同一路线已有记录。

沿用 Manager 的既有锁、事件账、generation、目标版本、证据校验和 check-action。继续区分专业停滞与工具失败，两类任一达到既有换路条件就进入重规划。换路仍需说明实际改变，不能仅换 ID。

### 5.3 接续与真实覆盖

在既有 state/handoff 增加有界的 `decision_quality` 摘要，显示当前路线的问题、复核数量、未复核数量和停滞次数。摘要明确：`manager-recorded-reviews-only`、调用者声明、不自动证明结论、并非全局工具拦截。

本线不修改 HTTP 发送、启动器、GUI、浏览器、调试器、设备后端和 Pi 注入代码；不把 Manager 的检查说成这些通道全部接线。project_workflow 自动捕获返回码不自动生成人工语义评价；Agent 需要专业复核时使用已有 Manager 入口记录带证据的尝试。

### 5.4 不在本轮声称实现的东西

- 模型权重改变、专家思维保证、任意软件可复刻或任意风控可绕。
- 实际计费 API 的 token/人民币自动计量和跨机器协调。
- 自动识别每个结果的真实信息增益，或校准未知目标的成功率。
- 新的全局授权层、第二套额度/项目账本、强制每次动作询问。
- 对第三方工具、目标心跳和服务器封禁结果的全局控制。

## 6. 九域与日常开发的对照场景

| 场景 | 必须先区分 | 有价值的证据 | 应避免的空转 | 完成/停止边界 |
|---|---|---|---|---|
| 软件逆向 softseep | 破解现程序、理解算法、独立实现；本地/远端权威 | 当前功能输入输出及实际依赖 | 为得到“完整干净 Dump”无限拆无关保护 | 满足功能规格即可；远端核心不可得则保留上限 |
| Android apkseep | Java/ART/native、目标问题与工具兼容问题 | 同运行时无害对照、包/设备身份和业务日志 | 用 native 自测宣布 ART 链路正常；反复卸装清数据 | 包能安装不等于功能成功；保留用户数据 |
| Web/API web-pentest | 页面挑战、权限、业务拒绝与请求未发送 | 请求阶段、业务后置条件、合成测试 | 见 403 就自动换账号/IP或重发写请求 | 已发送未知结果先核对；离线分析可继续 |
| 固件 firmware-iot | 提取结构、仿真、真机更新 | 架构/布局、可解释的仿真输出 | 为修仿真盲刷真机或改供电 | 提取成功不等于真机可刷；不扩大设备影响 |
| 协议 protocol-plugin | 解析、状态机、合法测试端点重放 | 分帧、关联 ID、正反会话 | 成功发包等于协议理解；重放真实交易 | 业务状态不明则暂停发送 |
| Pwn/密码 pwn-crypto | 假设、约束、可利用性与数学候选 | 独立样例、反例、真实本地 harness | 暴力扩大搜索而不核参数/约束 | 推翻候选是进展；不把自验当目标接受 |
| 取证 forensics-mobile | 观察事实、时间线推断、采集造成的变化 | 来源、哈希、多源时间关系 | 重复导出同一数据而继续提高置信度 | 工具解析不代替归因；原件不改 |
| 恶意样本 malware-analysis | 未触发分支、环境检测、样本/工具崩溃 | 隔离证据、受控刺激与行为 | 为求“全行为”开放真实外连 | 未观察到不等于不存在；不突破隔离 |
| 供应链 supply-chain-security | 声明、来源、构建执行、实际风险 | 锁文件/制品身份、安装脚本、重现构建 | 为确认版本盲跑不可信安装脚本 | SBOM 完成不等于无风险；发布另看范围 |
| 日常开发/跨域 | 小修复还是长期实验，回归还是新目标 | 失败测试、新诊断、业务验收 | 强制建案、全部技能/MCP都调用 | 范围内直接修测；两次合理修复不机械停工 |

九域是维护归属，不是互斥角色或调用权限。普通开发可借协议、格式、加密和供应链方法；跨域结果仍返回同一 project/version/run，不新增第十域。

## 7. 验收设计与结果解释

### 7.1 可自动检查的内容

复用 `test_manager_integration.py`，不另增测试脚本：

1. 无新字段的历史 CLI/API/账本仍可用。
2. decision/progress 错误类型、空值、过长值、未知字段和敏感值在写盘前拒绝。
3. 工具连续成功但两次专业无进展，第三次 Manager 检查拒绝。
4. 不同路线穿插、未复核成功，不清掉某路线的专业停滞。
5. 新证据复核重置停滞；假设被反例推翻同样可声明新证据。
6. 失败工具有新诊断时，原失败纪律仍保留；不倒置已有规则。
7. CLI 记录、状态重放、handoff 一致；证据仍绑定本次目标/run。
8. 九个正式域及普通开发的合成情景均走同一核心，不写十套硬编码。
9. 并发第二次停滞与第三次动作遵守原锁与重规划语义。

### 7.2 必须另行验证的自然语言能力

自动合同测试只能证明机制对“传入的判断”有一致行为，不能证明模型自主判断正确。后续获准的 Agent 场景验收应保留原始对话、能力读取与执行记录，由独立复核者检查：是否先问有区分度的问题、是否引用已有能力、是否避免无收益动态动作、是否保持自主修复。

不使用真实正式卡密/生产资产测阈值。可用合成服务、无害程序、冻结日志和人工标注的候选事实。不能只查回答是否含“风险/证据”等词；要看所选动作与输入事实和目标是否一致。

### 7.3 不造虚假指标

分别报告：字段与状态回归、既有工作流兼容、资料/入口可达、宿主加载、自然语言选择、真实目标业务结果。未测就写未测；不把合成场景数量包装成九域真实任务都完成。

1. 固定集成基线，先保存本文及本轮用户决定，不碰其他工作树。
