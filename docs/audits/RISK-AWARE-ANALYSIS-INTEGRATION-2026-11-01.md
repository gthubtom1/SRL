## 2. 三条工作线的所有权

| 工作线 | 主要负责 | 第三线不接管 |
| --- | --- | --- |
| 能力发现 | 资源身份、归属、搜索/发现、读取、调用与验证关联 | 不再造发现器，不复制工具库存，不把风险候选当作工具就绪 |
| 自主执行 | 任务范围沿用、可安全输入的凭据、启动/实例/GUI、人机交接 | 不恢复历史每次运行确认，不把 GUI 改回人工，不重写启动器 |
| 风险感知设计 | 保护画像、观察路线、外部影响、预算/租约/暂停/恢复与覆盖 | 本轮不部署新的阻断，不扩大现有只读 workflow 能力 |

后续实施会有公共文件重叠，应先锁定对方已提交的接口版本，只在自己的实现/验证 worktree 组合必要依赖并按批次更改。三条线各自完成后，才由新对话最终集成；不要三边同时重写 `AGENTS.md`、MCP 主文件、启动器或守卫，更不要提前覆盖主工作区。

## 3. 与能力发现的输入/输出约定

### 3.1 已有接口照用

只读参照的能力发现分支有：

- `seep_capability_discover(query=...)`，薄 MCP 入口。
- `Tool/scripts/route.py` 的 `--discover` / `--json` 模式，CLI 等价入口；本分支旧基线尚无该参数，合并后才可使用。
- `Tool/scripts/lib/` 中的 `capability_discovery.py`，该分支新增的共享实现；本分支旧基线尚无此文件。
- 结果 schema `seep.capability-discovery/1`，含 `resources`、`warnings`、`source_revision` 等。
- 候选资源保留 `runtime_status=not_checked` 等实际边界，不会因为返回了资源就执行它。

第三线应读取其真实 schema，不用本文猜测构造正式调用。合并后如接口变化，按该分支实际契约适配。

### 3.2 第三线消费什么

当前问题、原始资产/版本身份 -> 发现候选方法 -> 读取方法前提 -> 形成动作事实 -> 选择现有工具 -> 核参数、环境与影响 -> 执行。

风险判断结果可以作为下一次发现的上下文，例如“已有 HAR、不能再生产登录、需要离线定位签名输入”。不能修改用户原始目标、URL、路径或参数来影响路由。

### 3.3 不能跨越的语义

- 资源被找到不等于适用、已安装、可控、运行许可或当前目标成功。
- 历史案例中的安全次数、偏移和插件组合不提升为全局默认值。
- 搜索结果/KB/案例和样本内容不具备修改范围/预算/系统边界的权限。
- 一个来源被多个工具摘要引用，不增加独立证据数量。

## 4. 与自主执行的行为约定

### 4.1 必须保留的结果

- 已有范围内自行启动、点击、输入和验证，不因为本方案提到“风险”就全部改 ASK。
- 凭据按现有仓库边界使用；工具能安全输入则由 Agent 输入，非默认用户代输。
- 普通本地开发无需先 lab、建案、填风险表；技术失败由 AI 诊断，不让用户代执行。
- GUI/MCP/CLI 依实际目标选用，不用换 GUI 绕开原系统边界。

### 4.2 启动结果的消费

自主执行分支启动器的语义应原样保留：

| 字段/状态 | 第三线应怎样处理 |
| --- | --- |
| `launchRequested=true` | 可能已经启动并联网；后续观测失败也不能当成没运行 |
| `reusedExisting=true` | 核对准确实例及既有后台活动，不自动重复提交参数或重启 |
| `launched` | 兼容字段，表示已看到匹配实例，不是业务已成功 |
| `windowVerified=true` | 仅是窗口观察，不代表激活/登录完成 |
| `functionalityVerified=false` | 本轮业务检查仍需补齐，不篡改启动器声明 |
| 返回 4，未确认启动 | 先检查已有执行链；不能为了获得 0 反复启动 |
| 返回 6，多实例歧义 | Agent 根据完整路径/PID/创建信息和任务选择，不按标题乱点 |
| 显式人工模式 | 保留其真实等待原因；不是对所有 GUI 的默认分支 |

进程退出/停止也要绑定准确实例，不按 `app.exe` 名称全杀。任何正常启动通道都不承诺不可被检测。

### 4.3 技术熔断与外部预算

源码 edit/write 后允许重测，是本地开发能力；不得连带把已提交登录、激活或费用名额清零。

Agent 可以自动修复适配器，然后先在假服务/无害样本重测。真实资产已暂停时，修代码不是自动恢复许可。

## 5. 与现有项目状态的对接

project/version/run、资产、路线和证据继续使用现有接口。新增运行协调状态只保存主体并发/预算，不承载第二份需求、任务树、报告或验收历史。

建议动作级持有：`operation_id`、范围引用、风险主体引用、执行预占引用和 evidence refs；报告只引用脱敏事实，不暴露内部凭据值或可猜解指纹。

当前 `manager_state.check_action()` 明确是快照检查，不能宣传它已经保留执行名额或约束所有入口。后续接线在真实执行处完成，原项目入口语义保持兼容。

### 暂停一条远端路线，不锁死整个项目

目标账号受限时，可以继续离线解析、构建、写测试和整理证据。风险主体的暂停由发送/运行适配器检查；Manager 仍可选择不触及该主体的允许路线。

如果使用现有全局 `WAIT_USER`，应遵守它原有阻断语义；不能一边称 WAIT_USER 已锁住、一边偷走旁路执行。只有任务确实没有可继续工作才整体等待，或者在正式迁移中明确引入兼容的动作/路线级等待语义。

不要把暂停恢复藏在新 generation、改 route_id 或重新导入项目里。

## 7. 推荐提交拆分

1. `docs(risk): align protected-target and web decision guidance`：只校正方法和指针，不恢复旧人工门。
2. `feat(risk): add shared operation reservation and pause state`：窄协调和纯策略，配本地单元/并发测试。
3. `feat(http): enforce scoped dispatch and uncertain outcomes`：一个适配器的真实闭环与假服务集成测试。
4. `feat(runtime): bind flow limits to observed instances`：无害 GUI/浏览器应用，覆盖后台活动和实例恢复。
5. `test(risk): verify cross-host coverage and delivery boundaries`：实际支持宿主逐个验收，不靠一个宿主替所有宿主背书。

每步保持可独立审阅和回退。代码回退不能删除外部风险累计；发布失败不能以恢复旧数据库来补名额。

## 9. 接手者的完成判定

本轮静态设计校验及文件指纹见[设计校验回执](../verification/risk-aware-analysis-design-2026-11-01.json)。它只证明文档/场景结构与引用，不把 68 个待实施场景当作已经执行的测试。

用户追加的[社区实战研究](RISK-AWARE-ANALYSIS-COMMUNITY-CASES-2026-11-01.md)强调：先实现可判断的运行/请求阶段和证据接口，再接风险控制；不要将“暂停”等同崩溃、工具问题等同目标检测、抓到数据等同业务成功。将 4 个访问受限案例与 16 个取得相关内容的讨论分开，不把外部工具推荐直接写进自动安装/内核升级路线。

- 本轮完成：分支独立、设计/资料/对接/验收场景齐备，文件引用与结构核对，Git 提交可交接。
- 本轮未完成也未声称：运行预算控制、请求级拦截、GUI 端到端、真实保护目标绕过、全工程检查、宿主加载与生产验收。

最终要合并的是三种互补能力，而不是三套互相覆盖的提示词：**会找能力、会自己做、会控制试错代价。**
