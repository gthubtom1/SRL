## 1. 方案目标

本方案用于项目完成后的正式验收，目标不是证明项目永远不会出现任何问题，而是证明：

- 项目的公开能力已经登记；
- 所有主要领域都有代表性验证；
- 共享核心链路可以真实运行；
- 每个关键分支都有正例和负例；
- 工具确实进入真实会话并被正确使用；
- 用户需要操作时系统能够暂停等待；
- 失败时能够停止、报警、留痕并说明上限；
- 产物可以按用户可见结果验收；
- 未验证的能力不会被宣传为已完成。

本方案不接受以下结论作为验收结果：

- “代码整体没有问题”；
- “AI 已经审查很多次”；
- “脚本全部通过，所以项目完成”；
- “没有发现明显问题”；
- “剩下只是小 bug”；
- “文档中已经写了，所以功能存在”。

正式审查必须覆盖整个项目，而不是只审查某一个逆向领域。

### 2.1 共享核心

- 自然语言入口；
- 目标识别与分类；
- 总控路由；
- 技能加载；
- 工具发现；
- MCP 注册、启动、连接和会话暴露；
- 工具参数和 schema；
- 子代理和任务编排；
- 权限与安全护栏；
- 用户等待和恢复；
- 状态机；
- 案例状态；
- 事件账；
- 证据链；
- 报告和产物生成；
- 交付验收；
- 安装、部署、升级和卸载；
- 版本、哈希和部署态一致性。

### 2.2 领域范围

至少包括：

- Windows、PE、原生二进制和软件逆向；
- Android APK、AAB、DEX、SO 和移动端逆向；
- iOS、macOS、移动取证和游戏客户端；
- Web、API、网页安全和漏洞验证；
- 浏览器插件、扩展和 Native Host；

- 网站 1:1 复刻；

- 固件、IoT、路由器、设备和硬件接口；

每个领域还必须考虑以下分支：

## 4. 全项目能力台账

正式审查必须建立“能力—证据”台账。每一条公开能力至少包含以下字段：

| 字段 | 说明 |
|---|---|
| 能力 ID | 全局唯一编号 |
| 用户说法 | 用户可能使用的自然语言 |
| 所属领域 | reverse、apk、web、protocol 等 |
| 细分分支 | 例如 TLS Pinning、重打包、协议签名 |
| 路由 ID | 实际命中的路由 |
| 实际技能 | 真实加载的技能文件 |
| 实际工具 | 真实调用的 MCP 或 CLI |
| 前置条件 | 样本、账号、证书、设备、网络等 |
| 用户动作 | 是否需要双击、输入、扫码或确认 |
| 主要产物 | 报告、脚本、补丁、APK、固件等 |
| 正例测试 | 正常情况下应如何通过 |
| 负例测试 | 故意破坏后应如何失败 |
| 回滚方式 | 失败后的恢复方式 |
| 证据位置 | 日志、报告、截图、哈希和事件账 |
| 当前状态 | PASS、FAIL、PARTIAL 等 |

只存在于文档、配置、路由或提示词中的能力，必须标记为：

```text
DECLARED_ONLY
```

不能标记为 `READY`。

## 5. 八环生效链审查

每个领域、路由、能力都必须验证以下链条：

```text
用户输入
  ↓
目标识别
  ↓
路由命中
  ↓
技能加载
  ↓
工具进入真实会话
  ↓
实际执行
  ↓
证据和产物
  ↓
用户可见验收
```

“文件存在”不等于“功能可用”。

“端口监听”不等于“MCP 已连接”。

“MCP 已连接”不等于“工具出现在当前模型会话中”。

“模型调用成功”不等于“用户得到了可用产物”。

任何一环没有实际证据，该能力只能标记为 `NOT_TESTED` 或 `INCONCLUSIVE`。

## 6. 共享核心验收

### 6.1 路由验收

每条路由必须至少准备：

- 一个应该命中的输入；
- 一个相邻领域的混淆输入；
- 一个不应该命中的输入；
- 一个复合任务输入；
- 一个模糊任务输入。

必须验证：

- 是否命中正确领域；
- 是否出现领域串味；
- 是否错误落入兜底；
- 是否能拆分复合任务；
- 信息不足时是否提出必要问题。

### 6.2 技能加载验收

必须证明：

- 命中路由后加载了正确技能；
- 加载的是当前版本；
- 部署目录和源码一致；
- 技能确实影响了后续行为；
- 删除或禁用技能后系统会退化或阻止继续。

### 6.3 工具验收

必须分别验证：

```text
工具安装
→ 工具启动
→ 工具探活
→ MCP 连接
→ 当前会话工具表出现
→ 模型实际调用
→ 结果进入事件账
```

必须故意测试：

- 停止工具；
- 错误参数；
- 错误 schema；
- 版本不兼容；
- 空结果；
- 超时；
- 工具返回异常。

系统不得静默假装成功，也不得无限循环。

### 6.4 用户等待验收

以下情况必须进入 `WAIT_USER`：

- 用户双击目标；
- 用户输入卡密或账号；
- 用户输入验证码；
- 用户扫码；
- 用户连接设备；
- 用户确认授权范围；
- 用户批准安装工具；
- 用户确认外部写操作。

等待期间，危险工具必须锁定。用户回复后必须能从案例状态恢复。

### 6.5 安全验收

必须验证：

- 网络配置不会被擅自修改；
- 代理不会被擅自改变；
- hosts 不会被擅自修改；
- 默认路由不会变化；
- 未授权外部目标不会被访问；
- MCP 不能绕过 shell 护栏；
- 子代理不能绕过主控规则；
- 写操作必须有授权、记录和回滚。

### 6.6 证据验收

每次真实动作必须记录：

- 时间；
- 阶段；
- 工具；
- 输入摘要；
- 输出摘要；
- 结果；
- 产物路径；
- 哈希；
- 风险等级；
- 是否需要人工操作。

不能依赖模型主动记账。

## 7. 各领域的最小黄金样例

每个领域必须拥有：

1. 一个正常 fixture；
2. 一个失败 fixture；
3. 一个代表性案例；
4. 一份领域验收表；
5. 一份失败判据表；
6. 一份工具依赖表；
7. 一份人工操作清单；
8. 一份产物验收清单；
9. 一份回滚方案；
10. 一份回归测试。

### 7.1 Windows/PE/原生逆向

验证架构、壳、完整性、动态观察、ImageBase、RVA/VA、补丁、回滚、重复启动和功能清单。

### 7.2 Android/APK

验证 Java、Native、JNI、加固、TLS Pinning、重打包、签名、安装、启动和功能回归。

### 7.3 Web/API

验证资产识别、登录态、Cookie/JWT/OAuth、CSRF、API 签名、权限边界、请求重放和报告复现。

仅允许使用授权目标、回环服务或本地靶站。

### 7.4 浏览器插件

验证 Manifest、权限、Content Script、Service Worker、Native Messaging、安装、卸载和浏览器兼容性。

### 7.5 私有协议

验证 pcap 解析、请求构造、响应解析、会话状态、nonce、时间戳、错误包和重放。

### 7.6 网站和后端复刻

验证页面路由、DOM、视觉、静态资源、API、登录态、数据模型、错误码、幂等性、迁移和重启。

### 7.7 固件/IoT

验证识别、解包、启动链、服务、默认凭据、Secure Boot、OTA、仿真或硬件以及恢复路径。

### 7.8 AD/云原生

验证范围、身份、权限、只读侦察、证据、非破坏性和环境恢复。

### 7.9 恶意样本/取证

验证隔离、静态分析、IOC、时间线、样本哈希、误执行防护和结论置信度。

### 7.10 Pwn/密码学

验证输入条件、环境版本、复现命令、成功判据、失败判据、稳定性和独立验证。

### 7.11 供应链

验证依赖识别、SBOM、秘密扫描、恶意依赖 fixture、CI 阻断和误报处理。

### 7.12 LLM/MCP/A2A

验证工具权限、提示词注入、越权调用、秘密泄露、子代理边界、事件账、熔断和上下文污染。

### 7.13 登录/签到/多账号自动化

验证账号隔离、Cookie 隔离、Session 过期、验证码、重试上限、失败暂停和通知。

### 7.14 OSINT/差分/版本迁移/文档治理

分别验证来源链、范围控制、版本匹配、补丁迁移、回归、文档索引和历史状态隔离。

## 8. 每个分支必须有四类测试

### 8.1 正常测试

目标、工具和前置条件都正常时，流程可以完成。

### 8.2 前置缺失测试

故意缺少样本、凭据、证书、设备、工具、权限或网络，系统必须明确说明缺失项。

### 8.3 故障测试

故意制造错误参数、工具超时、进程崩溃、空输出、地址错误、版本错误和产物损坏，系统必须停止、报警或转人工。

### 8.4 交付反例测试

故意提交空报告、空事实账、不存在的证据、损坏 APK、无法启动的补丁或只能启动一次的成品，交付门必须拒绝。

## 9. 审查阶段

### P0：冻结项目

生成源码、部署、工具、路由和版本快照。

### P1：建立全项目资产地图

核对：

```text
路由 → 技能 → 工具 → 能力 → playbook → 案例 → 产物 → 验收
```

### P2：审查共享核心

完成路由、工具、等待、安全、状态、事件账和恢复测试。

### P3：逐领域黄金测试

每个领域至少完成一个正常样例和一个失败样例。

### P4：细分分支测试

所有公开分支必须有状态、证据、正例、负例和验收条件。

### P5：组合场景测试

重点测试人工操作、外部网络、写操作、子代理、长任务、上下文压缩、真实设备和回滚。

### P6：弱模型测试

使用项目实际可能采用的较弱模型，以自然语言运行黄金任务。

### P7：清洁室审查

审查者不得读取之前的“已完成”结论，只能根据项目本身和用户目标独立判断。

### P8：最终发布裁定

输出项目能够做到什么、不能做到什么、哪些分支未验证、是否允许发布。

## 10. 状态定义

只能使用以下状态：

| 状态 | 含义 |
|---|---|
| PASS | 正例、负例、证据、验收全部通过 |
| FAIL | 实际行为不符合要求 |
| PARTIAL | 只能完成部分目标 |
| BLOCKED | 缺少外部前置条件 |
| NOT_TESTED | 尚未测试 |
| INCONCLUSIVE | 证据不足，无法裁定 |
| STALE | 当前部署态不是审查源码版本 |
| DECLARED_ONLY | 只有声明，没有真实执行证据 |

禁止使用“整体没问题”“基本完善”“小 bug”作为正式状态。

## 11. 最终通过条件

项目只有同时满足以下条件，才允许标记为 `RELEASE_READY`：

1. 共享核心测试通过；
2. 所有公开领域都有黄金样例；
3. 每个重要领域都有失败样例；
4. 关键分支不再是 `DECLARED_ONLY`；
5. 工具确实进入真实会话；
6. 用户等待和恢复有效；
7. 危险动作确实被阻止；
8. 事件账自动生成；
9. 空证据不能交付；
10. 至少一条完整真实黄金路径可以闭环；
11. 未完成能力已明确列出；
12. 清洁室审查没有发现未登记的重大缺陷。

如果只完成静态门禁，必须标记：

```text
PACKAGED_BUT_UNPROVEN
```

不能标记为最终可用。

## 13. 审查 AI 的固定指令

正式触发本方案后，审查 AI 必须遵守以下规则：

```text
你现在负责审查一个已经完成开发的多领域 AI 工程系统。

本次任务是正式验收，不是继续开发，也不是证明项目没有问题。

除非用户另行授权，你不得修改源码、配置、部署态或测试文件；不得安装依赖；不得修改系统网络、代理、hosts、路由或其他环境配置。

你必须分别审查共享核心、所有领域、所有公开路由、所有重要能力、所有写操作、所有人工交互流程和所有交付型产物。

静态文件存在不等于功能可用；脚本 self-test 通过不等于真实链路通过；模型口头说明不算证据。

每项能力必须提供：触发点、加载证据、执行证据、产物证据、用户可见验收、负例结果、回滚方式和最终状态。

没有证据时必须标记 NOT_TESTED，不得猜测通过。

状态只能使用 PASS、FAIL、PARTIAL、BLOCKED、NOT_TESTED、INCONCLUSIVE、STALE、DECLARED_ONLY。

最终必须说明项目真正能做什么、哪些能力只是声明、哪些共享问题会影响全部领域、哪些分支尚未验证，以及是否允许发布。
```

## 14. v2.0 深度强化审查层

### 14.1 先说明边界：不存在“有限测试保证所有潜在问题”的方法

即使不考虑 Token，也不存在一个有限的审查方案能够数学意义上证明复杂软件不存在所有未来问题。

本方案的强化目标不是做出虚假的“绝对无缺陷”承诺，而是把遗漏风险压到最低，并保证：

- 每个公开入口都有审查记录；
- 每个共享机制都有黑盒验证；
- 每个领域都有代表性路径；
- 每个高风险组合都有专门测试；
- 每种已知失败模式都有回归用例；
- 未知风险会通过故障注入、生成式测试、清洁室审查和长期运行主动暴露；
- 任何无法证明的能力都不会被标记为完成。

### 14.2 十六类问题必须分别审查

正式审查不能只查功能 bug，还必须分别检查：

1. 需求理解错误；
2. 路由和分类错误；
3. 技能和提示词未加载；
4. 工具未连接或版本漂移；
5. 参数、schema 和编码错误；
6. 模型错误决策、幻觉和静默假设；
7. 用户操作等待和恢复错误；
8. 权限、范围和授权错误；
9. 网络、系统和外部副作用；
10. 证据、日志和事实账缺失；
11. 产物不可运行、不可重复或不可回滚；
12. 并发、重复执行和状态污染；
13. 超时、崩溃、断网、重启和上下文压缩；
14. 性能、Token、磁盘、内存和进程泄漏；
15. 安装、更新、迁移、卸载和跨机器问题；
16. 恶意输入、提示词注入、恶意工具输出和供应链风险。

每一类问题都必须有：

```text
测试方法 + 正例 + 负例 + 外部判定器 + 证据 + 状态
```

### 14.3 “全覆盖”分成三种覆盖

#### A. 资产覆盖

确认所有以下对象都被登记：

- 路由；
- 技能；
- 子技能；
- MCP 工具；
- CLI 工具；
- 能力；
- playbook；
- 任务卡；
- 配置；
- 脚本；
- 案例；
- 产物类型；
- 人工操作点；
- 外部依赖。

资产没有登记，就不能称为“审查完整”。

#### B. 行为覆盖

确认这些对象在真实运行时被实际触发、执行和验收。

文件存在、引用正确、self-test 通过，只能证明资产覆盖，不能证明行为覆盖。

#### C. 组合覆盖

用以下维度组成测试矩阵：

```text
领域
× 载体
× 用户意图
× 保护类型
× 工具可用性
× 用户交互
× 外部副作用
× 交付等级
× 失败类型
× 运行环境
```

不可能把所有组合全部穷举，因此必须：

- 所有 P0 高风险组合全部测试；
- 其他组合至少进行两两覆盖；
- 涉及权限、网络、凭据、硬件和写操作的组合至少进行三维覆盖；
- 每个领域至少有一个完整端到端组合。

### 14.4 增加八种高级测试

#### 1. 变异测试

故意修改或删除：

- 路由关键词；
- 技能引用；
- 工具注册；
- schema 字段；
- 证据路径；
- 产物内容；
- 状态字段；
- 安全规则。

预期结果：对应门禁必须变红。

如果故意破坏后仍然通过，说明检查是“假检查”。

#### 2. 故障注入测试

故意制造：

- MCP 停止；
- 工具超时；
- 错误参数；
- 空响应；
- 错误编码；
- 进程崩溃；
- 网络中断；
- 文件锁定；
- 磁盘空间不足；
- 权限不足；
- 子代理失联；
- 上下文被压缩。

验证系统是否会正确停止、重试、转人工或恢复。

#### 3. 属性测试

验证不依赖某个具体样本的通用性质，例如：

- 同一输入重复运行不会产生互相矛盾的结论；
- 证据哈希改变后验收必然失败；
- 删除关键产物后交付门必然失败；
- 未授权写操作永远不会执行；
- `WAIT_USER` 状态期间危险工具永远不可用；
- 工具不可用时不会伪造工具结果。

#### 4. 变形测试

对输入做不改变语义的变化，结果应该保持合理一致，例如：

- 文件改名；
- 路径包含空格；
- 路径包含中文；
- 大小写变化；
- 换行符变化；
- 用户使用同义词；
- 用户用口语描述同一任务；
- 同一目标重复启动。

如果仅仅因为换了文件名、语言或表达方式，系统就走出完全不同的错误路径，需要记录为缺陷。

#### 5. 差分测试

使用两个独立来源对同一结果进行比较：

- 两个独立解析器；
- 两个独立脚本；
- 工具结果与人工抽样；
- 模型结论与外部判定器；
- 旧版本与新版本；
- 原始证据与生成报告。

实施者不能同时作为唯一判定器。

#### 6. 生成式和模糊测试

生成大量变化输入，覆盖：

- 模糊自然语言；
- 错别字；
- 中英文混合；
- 复合任务；
- 缺少上下文；
- 恶意提示词；
- 畸形文件；
- 超长字段；
- 空字段；
- 重复字段；
- 错误类型；
- 恶意工具返回。

重点观察是否出现：

- 错误路由；
- 越权工具调用；
- 无止境重试；
- 静默失败；
- 伪造证据；
- 错误交付。

#### 7. 长时间和压力测试

至少测试：

- 连续运行多个案例；
- 长时间工具调用；
- 大文件；
- 大量日志；
- 大量并发任务；
- 频繁暂停和恢复；
- 多次启动和关闭；
- 磁盘空间接近上限；
- 内存和进程是否泄漏。

#### 8. 环境矩阵测试

至少覆盖：

- Windows 版本差异；
- 管理员与普通用户；
- 干净机器与已有环境；
- 工具完整与工具缺失；
- 有网与断网；
- 中文路径与英文路径；
- 路径含空格；
- 不同编码和换行符；
- 不同 Python/PowerShell 版本；
- 不同 CPU 架构；
- 代理存在与不存在；
- 用户配置完整与不完整。

### 14.5 AI 专用深度审查

由于项目由 AI 驱动，必须额外测试模型行为：

- 强模型与弱模型是否差距过大；
- 长上下文和短上下文是否行为一致；
- 上下文压缩后是否丢失授权边界；
- 工具返回错误时是否会编造结果；
- 多个工具名称相似时是否误调用；
- 工具参数不明确时是否先查询 schema；
- 文档和样本中的恶意提示词是否能污染模型；
- 外部目标返回的文本是否能诱导模型越权；
- 子代理结果是否未经验证就被主代理采信；
- 模型是否为了“完成任务”而跳过等待、授权和安全规则；
- 模型是否在长时间无进展时主动停下；
- 模型是否能准确说明“没有证据”。

至少使用：

- 一次强模型测试；
- 一次实际常用模型测试；
- 一次弱模型测试；
- 一次短提示测试；
- 一次自然口语测试；
- 一次恶意或混淆输入测试。

### 14.6 人机交互审查

正式审查不能只让 AI 自己跑，也要观察真实用户是否会误操作。

需要检查：

- 用户是否知道当前阶段；
- 用户是否知道下一步要做什么；
- ASK 卡是否足够清晰；
- 是否会把“等待用户”误解成“AI 卡死”；
- 是否会误把测试目标当成真实目标；
- 是否知道当前操作可能改变环境；
- 是否知道如何停止任务；
- 是否知道如何恢复任务；
- 是否知道结果是否已经交付；
- 是否能理解“部分完成”和“明确上限”。

### 14.7 最终发布门禁

最终发布必须同时通过：

1. 资产完整门；
2. 路由和技能门；
3. 工具真实连接门；
4. 共享核心行为门；
5. 安全和权限门；
6. 证据和可追溯门；
7. 各领域黄金路径门；
8. 细分分支覆盖门；
9. 负例和变异门；
10. 故障恢复门；
11. 长时间和资源门；
12. 环境兼容门；
13. 弱模型门；
14. 清洁室门；
15. 用户可见交付门。

任何 P0 缺陷未关闭，不得发布。

P1 缺陷必须关闭，或由项目所有者明确签字接受风险。

P2/P3 可以登记延期，但必须记录：影响、临时规避方式、预计修复时间和责任人。

### 14.8 深度审查结果目录

正式触发后，审查结果应写入独立目录：

```text
work/audit/<审查日期>/
├── 00-baseline.md
├── 01-system-inventory.json
├── 02-requirements-matrix.md
├── 03-shared-core-report.md
├── 04-domain-reports/
├── 05-branch-matrix.csv
├── 06-negative-tests/
├── 07-fault-injection/
├── 08-environment-matrix/
├── 09-ai-behavior/
├── 10-evidence-index.json
├── 11-findings.md
├── 12-release-decision.md
└── 13-independent-review.md
```

本封存方案本身不得被测试结果覆盖。

### 14.9 深度审查的最终结论格式

最终不得只输出“通过”或“不通过”，必须输出四个层次：

```text
A. 已被证明可以工作的能力
B. 已被证明不能工作的能力
C. 尚未证明的能力
D. 目前无法排除的潜在风险
```

只有 A 类能力可以标记为已交付。

C 类和 D 类不能被包装成“没有问题”。

## 15. 文件维护规则

本文件是项目完成后的审查协议，不是日常开发文档。

除非项目所有者明确要求更新本方案，否则：

- 不得自动修改本文件；
- 不得把审查结果写回本文件；
- 不得把本文件内容复制进运行时提示词；
- 不得因为新增功能而自动触发本方案；
- 不得在普通会话中主动引用本文件作为开发依据。

正式审查结果应写入单独的审查报告目录，不应覆盖本封存方案。

推荐审查结果位置：

```text
work/audit/<审查日期>/
```

本文件始终保持为“项目完成后、由用户明确触发的全项目审查方案”。
