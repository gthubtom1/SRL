# PRODUCT —— 这个项目到底该长什么样（产品规格，非计划书）

> 写这份的原因：此前一直是"用户报问题 → 我修一处"，结果是 4 套路由、163 项门禁、29 个配置的"四不像"。
> 这份文件只做一件事：**把产品钉死**，之后任何改动都要能回答"符合 PRODUCT 哪一条"。

---

## 1. 定位（一句话）

> 给一个目标，先说清**这是什么 / 能到哪一级 / 缺什么**；然后按该领域的技能链干活，每步留证据，结论可复查。

**不做**：不做"一键全自动出成品"。深度上限由壳/授权位置/服务端权威决定，谎报做不到的事比做不到更糟。

## 2. 用户与主回路（用户只感知 4 步）

```
/rev <目标>              ← ① 选域（显式斜杠命令，100% 加载该域技能链）
判型 + M1–M4 + 我缺什么    ← ② 30 秒内必须给；缺输入就问（问不是退缩）
按该域 SKILL 干活          ← ③ 工具/命令/hook，硬规则写在命令卡里
证据落账 → 可复查          ← ④ facts.jsonl + artifacts/MANIFEST + 结论分级
```

**入口只有 2 个**：`/域` 命令（显式）+ 技能 `description`（兜底）。`route.py` 只是测试工具。

## 3. 内容三层（渐进披露，不再加层）

| 层 | 内容 | 体量 | 谁读 |
| :-: | :-- | --: | :-- |
| L1 | 10 张 `/域` 命令卡 | ~12 行/张 | 用户打 `/` 时 |
| L2 | 每域 `SKILL.md` | ≤600 行 | 模型必读 |
| L3 | `references/` + `_pending/` 归档子技能（18 个，按需链接） | 按需 | 模型按需 |

## 4. 状态与证据（唯一事实源）

| 文件 | 作用 | 谁写 |
| :-- | :-- | :-- |
| `<case>/case.json` | 结构化元数据（域、目标、上限、结论） | `case_state.py init/verdict` |
| `<case>/facts.jsonl` | 逐条事实（claim / state / event / gaps / plan / ask） | 工具与 Agent |
| `<case>/artifacts/MANIFEST.sha256` | 交付物哈希 | 生成脚本 |
| `<case>/scope.md` | **授权与边界契约**（做什么/不做什么/环境） | `init` 自动生成 |
| `docs/LESSONS.md` | **跨案例经验回流**（同类工作台都有的 field journal） | Agent 结案时追加 |

## 5. 测试口径（一条命令）

```bash
python Tool/scripts/check.py          # 全量 6 套件（lint/unit/e2e/skill-tests/route-tests/kb-tests）
python Tool/scripts/check.py --fast   # 提交前 4 套件
```

**"合格"的定义 = check.py 全绿 + 下面第 7 节风险登记表没有新增未处置项。**

## 8. 路线（只 3 项，按风险排序）

1. **R1 实测**：新会话打 `/rev` → 验证命令卡是否真加载技能（一次即可，成本 2 分钟）
2. **scope.md 落地**（学 case-guard）：`init` 时生成授权/边界契约，`gate` 检查新案必须有它
3. **跨案例经验回流**：`docs/LESSONS.md` 每次结案追加一条"形状 + 判据/机制改动"，让同类错误只犯一次
