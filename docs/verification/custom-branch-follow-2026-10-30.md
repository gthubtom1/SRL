# 1.30.0 定制分支跟随更新交付说明

1.30.0 把“软件更新后继续使用我方定制 UI 和旧逆向成果”接入现有追版能力。它增强现有 `version-migrate` 配方，没有增加第十个正式域、独立工作流引擎或新的项目状态 schema。

## 用户入口

首次完成逆向和 UI 定制后，用户不需要再次说明内部步骤。以后只需要说：

```text
软件更新了，跟随更新。
新版路径是刚拖进来的新版文件。
```

系统先找回唯一旧项目并读取旧上游、旧定制成品、补丁、UI、构建和验收记录。无候选、多候选或产品身份冲突时必须停下确认，不能因为文件名相似而自动合并。

追版比较三个对象：

1. 旧上游原版到新上游原版：识别上游新增功能、保护、接口、资源和构建变化。
2. 旧上游原版到旧定制成品：识别我方真正添加的补丁、UI 和品牌层。
3. 我方定制改动到新原版：把仍有效的改动重新应用，不覆盖新版新增内容。

复用顺序是覆盖层/自有启动器/服务端内容、外部资源、稳定接口或资源锚、AOB、代码级重写。只有上一级无法完成时才进入更高成本路线。

## 已实现的机器账本

`version-migrate.py add-ui` 现在只登记和验证 UI 定制，不自动执行 UI。它会拒绝：

- 重复 UI ID；
- 未知技术栈、应用方式或锚点类型；
- 缺少上游锚点、自定义资产、前后截图或验收项；
- 项目外路径、绝对路径、`..`、符号链接或重解析点；
- 不存在或登记期间变化的文件；
- 非 `seep-ui-inventory/1` 的机读 UI 清单；
- 非法清单对象结构。

成功记录写入现有 `seep-reverse-baseline/1` 的 `ui[]`，保存清单、资产和截图的 SHA256 与大小，并标记 `recorded_custom_ui_only_not_applied`。所有拒绝路径都验证不会改动已有基线字节。

## 追版闭环

配方现在要求固定生命周期、按目标选择技术路线：

```text
找回旧项目
→ 读取旧记录
→ 登记新版
→ 比较旧上游、新上游和我方定制
→ 分类 reused / relocated / needs_manual / missing / multi / blocked
→ 迁移 UI 并合并新版功能
→ 从新上游重新构建、打包和签名
→ 补丁、UI、功能、安装和回滚验证
→ 写回新版本账本
```

`unique` 只表示定位候选。缺失、多重命中、语义未确认或环境阻断必须保留在报告中，不能改写成“追版成功”。

## 边界

- 第一版支持面是 PE/Windows 与 APK。其他载体可以继续使用各自技能，但不能声称已经具备专用追版适配器。
- `add-ui` 只记录已验证 UI 账本，不自动操作窗口、资源、安装包或目标程序。
- 本轮使用合成夹具验证账本与拒绝路径，没有真实客户软件的“新版本追版”运行证据。首个真实目标仍需按壳、保护、签名、UI 栈、服务端、设备和构建条件验收。
- 已登记资产的哈希在追版开始时会重新核对；本轮没有增加后台常驻监控。
- 旧 `_pending/00..05` 保持归档，仅提取生命周期思路，不恢复强制阶段链。
