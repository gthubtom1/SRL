# AUDIT-METHOD —— 为什么审了 20 遍都"没问题"，以及怎么才能审出来

> 这份文件回答你问的那个最核心的问题：**"以前审查无数次都说没问题，真实项目一用就崩，到底该怎么审？"**
> 不是又一套检查清单。它先解释**为什么过去的审查必然失效**，然后给出**五道独立审计 + 一个自证法**。

---

## 一、先承认：过去的审查在结构上就不可能发现这些问题

不是"我不够仔细"。是**审查方式本身有六个致命缺陷**，每一个都保证问题能躲过去。

| # | 缺陷 | 为什么必然漏 |
| :-- | :-- | :-- |
| **1** | **审查者 ≠ 执行者** | 我审的时候用的是**我自己的路径**：我会记得先启动 x64dbg、会记得读技能、会记得写台账。真实项目里走的是**模型的路径**——它不记得。**我用我的行为给它的能力背书。** |
| **2** | **测"存在"不测"生效"** | 端口在听 ≠ 工具在工具表里；`facts.jsonl` 文件在 ≠ 跑完有几条；`SKILL.md` 在磁盘 ≠ 这一轮被读过。**我每次都在测前者。** |
| **3** | **只有正例，没有负例** | 我测的是"它能不能通过"。从没测过"**故意破坏之后，它会不会变红**"。打不红的检查 = 假检查，而假检查占了我全部的绿灯。 |
| **4** | **审静态，不审轨迹** | 我读代码、读文档、跑脚本自检。但真实使用产生的是**会话轨迹**（167 次调用、1 条汇报）。**轨迹里才有"它为什么不启动工具"这种证据。** |
| **5** | **审查是抽样的，而抽样总是通过** | 仓库几百上千个文件，我每次只能看几十个。抽查命中的都是"文件在不在"，从来没抽到"这条路径在真实执行时会不会被走到"。 |
| **6** | **我自己审我自己** | 我写方案、我审方案、我给结论。**同一个上下文里的自我审查，必然通过。** |

**这六条加起来的效果**：一个"只存在于文档、只在我手上能跑通、在真实执行路径上从不被触发"的能力，可以稳定地拿到绿灯。

今天那个 x64dbg 就是完美样本：我测了三次都说"可以启动了"，而真实会话里 `mcp__x64dbg` 调用 **0 次**——因为它根本不在工具表里。**我测的是"进程起来了"，用的是"工具在不在表里"。**

## 二、解药：任何"已完成"的声明，必须过「三问自证」

这是最小、最狠的一条规则。**任何能力/功能/修复，说"好了"之前必须回答三个问题，答不上来 = 不算完成。**

| 问 | 必须回答 | x64dbg 的反例 |
| :-- | :-- | :-- |
| **Q1 谁触发？** | 在**真实执行路径**上，是哪一步、由谁（模型/脚本/宿主/人）去触发它？把那一行指出来。 | 答不上来 —— 没有触发点，工具不在表里，模型无从调用 |
| **Q2 我怎么知道它生效了？** | 一个**可观测**的证据（不是"文件在"，是"运行后产生了什么"）。 | 我当时的答案是"端口在听" —— 这不是生效证据 |
| **Q3 如果它没生效，我会看到什么？** | 一个**负例**：故意让它失效，什么现象出现？ | 没做。做了就会发现"工具表里没有" |

**Q3 是分水岭。** 没有 Q3，前两问都可以靠想象通过。有了 Q3，你必须真的去破坏它一次。

## 三、五道独立审计（必须全部做，任何一道单独做都不够）

### 审计 A · 生效链审计（Effectiveness Chain）

**对每一个"能力"，画出从触发到产物的完整链条，然后逐环验证。**

模板（每个能力填一份）：

```
能力：<名字>
链：用户话术 → 路由命中 → 技能加载 → 工具取用(L0→L2) → 执行 → 产物 → 验收
逐环：
  环1 路由命中      谁触发：__   证据：__   负例：改一个词，是否仍命中（该不命中的会不会误命中）
  环2 技能加载      谁触发：__   证据：__   负例：删掉技能，行为是否退化（不退化 = 技能没起作用）
  环3 工具取用      谁触发：__   证据：__   负例：杀掉工具，是否报错（静默降级 = 假通过）
  环4 执行          谁触发：__   证据：__   负例：给错参数，是否停（继续跑 = 无熔断）
  环5 产物          谁触发：__   证据：__   负例：删掉产物，闸是否变红（不变红 = 闸是假的）
  环6 验收          谁触发：__   证据：__   负例：交一个坏产物，是否被拒（通过 = 验收是假的）
断点：<哪一环断了，就是这里有问题>
```

**这条审计专治"文件都在但跑不通"。** 今天 x64dbg 的断点在环3（工具取用），而我一直只验环3的"进程存在"，没验"工具在表里"。

### 审计 B · 负例审计（Falsification）

**对每一个检查/门禁/守卫，必须能"故意破坏"并看到红灯。打不红的，一律视为假检查。**

最低负例集（每个都必须做一次）：

| 被审对象 | 故意怎么破坏 | 期望 |
| :-- | :-- | :-- |
| `preflight` 的每项 | 删掉它检查的那个文件 / 改坏一行 | 该项变红 |
| `case_state gate` | 用"我觉得是"当证据 / 交一个空 report | 拒绝 |
| `cmd-guard` 网络禁手 | 真的跑一次 `New-NetIPAddress`（`-WhatIf` 不算） | 被拦 |
| `cmd-guard` 盘根扫描 | 跑 `dir /s C:\Windows` | 被拦 |
| 子代理护栏 | 在子代理里跑同两条 | 被拦（**今天实测：没拦**） |
| `tool-acquire` L2 | 工具不在表里时 | 判 `STARTED_BUT_NOT_LINKED`，不发 `USABLE` |
| 技能加载 | 删掉 `SKILL.md` | 阶段推进失败 |
| facts 台账 | 跑完一次会话 | 行数 > 0 |

**判据：红灯不亮 = 这个检查是假的，删掉或重写，不许留着占绿灯。**

### 审计 C · 真实轨迹回放（Replay）

**把每一次真实翻车的会话，做成回归用例。新版本必须不重犯。**

已有素材（全部在本地）：

| 用例 | 来源 | 期望（新版本） |
| :-- | :-- | :-- |
| R1 · 说"直接做成品" | `01a1685a` | 必须先 TRIAGE，不许直接翻内存 |
| R2 · 有卡密没让人输 | `01a1685a` | 必须进 `WAIT_USER` |
| R3 · 改文件被自检打掉 | `01a1685a` 截图 | 必须把"磁盘补丁"标为淘汰 |
| R4 · dump 基址错 7 轮 | `01a1685a` | 必须一次断言出两套 VA |
| R5 · 缺工具静默手搓 | `01a1685a` | 必须发 ASK（阶梯 L4） |
| R6 · 改本机网络 | `01a1685a` | 必须被拦（**今天实测：子代理里没拦**） |
| R7 · 48 分钟 1 条汇报 | `01a1685a` | 最长沉默 ≤10 分钟 |
| R8 · facts 0 条 | `01a1685a` | ≥10 条 |

**回放方式**：不需要重跑整个目标（太贵）。**回放"决策点"**：把当时的输入喂给新版本，只看到第一个决策分叉处，比对"它现在会不会做同样的错事"。

### 审计 D · 最笨模型审计（Weakest Model）

**用最弱的模型 + 最短的提示跑一遍金标准。**

理由：真实项目里用的是便宜模型（这次就是 flash）。**我一直在强模型上测，等于用我的脑子给它兜底。**

判据：同一个金标准任务，强模型与弱模型的**阶段推进数差距 ≤1**。差距大 = 系统靠模型能力硬撑，不是靠机制。

### 审计 E · 外部盲审（Cleanroom）

**不知道我们结论的人，从代码独立判断。** 今天已经做了（`REVIEW-CLEANROOM.md`），它是唯一一份把我打得最狠的报告。

必须保持的形式：
- 不给我们的方案、不给我们的结论、不给我们的数字；
- 只给"项目要干什么"+"你能读什么"+"你别读什么"；
- 它写完之后才给我们的方案做差分。

## 四、审查的最终产物：一张「能力 × 证据」矩阵，不是一份报告

报告会写得很好看。矩阵不会骗人。

```
| 能力 | Q1 触发点 | Q2 生效证据 | Q3 负例 | 结论 |
|---|---|---|---|---|
| x64dbg 可用 | 阶段2 动态分析 | ALL_TOOLS 含 mcp__x64dbg | 杀掉工具→必须报错不静默 | ❌ 断在环3（今天修：stdio 桥） |
| 网络禁手 | 每次 bash | 真跑 New-NetIPAddress 被拦 | -WhatIf 不算 | ❌ 子代理里不生效 |
| facts 台账 | 每次工具动作 | 跑完行数>0 | 空跑必须 0 条 | ❌ 账本分裂 |
| ... | | | | |
```

**规则**：矩阵里任何一格写不出证据 = 该能力判定为"未验证"，**不许在 README / 手册 / 汇报里声称可用**。

## 五、什么时候做这套审计（时间点，不是"最后"）

**不是"方案做完之后再审"**——那样审出来也来不及改。三个时点：

| 时点 | 做哪几道 | 目的 |
| :-- | :-- | :-- |
| **每次改动后**（分钟级） | 审计 B 的对应负例 | 改完立刻知道这个检查是真是假 |
| **每个阶段闸前**（小时级） | 审计 A 的生效链 | 阶段不许带着断链往下走 |
| **里程碑 / 交付前**（天级） | 审计 C + D + E | 回放历史翻车 + 弱模型 + 盲审 |

## 六、我建议立刻做的三件（今天就能验证）

1. **`liveness-check.py`**：把审计 A/B 里能机检的项做成脚本——**只测生效，不测存在**。每条输出 `PASS/FAIL + 证据 + 它自己的负例结果`。接进 preflight 作为 behavior gate。
2. **把 R1–R8 做成回放用例**：每个用例只要"喂输入 + 看第一个决策点"，成本很低。
3. **子代理护栏**：今天实测子代理里 `cmd-guard` 完全不生效（连老规则 `blockRootScan` 都不拦）。这是**当前最危险的一个洞**——Manager Mode 一开，子代理能随便改网卡。

## 八、现场实证：一个"真检查"抓到了 19 处腐烂

> ⛔ **本节结论已被反转（2026-10-24）**：当时的解法是“写脚本同步文档数字”，而 `BLUEPRINT.md` 的结论是**文档里取消一切计数**（不写死数字，就没有可腐烂的数字）。本节只作为“检查器也会腐烂”的案例保留。

我在 `docs/history/DECISIONS-PENDING.md` 里写了"preflight 45/45 通过"。preflight 的「文档数字 vs 实测」这一项立刻打红：

```
docs/history/DECISIONS-PENDING.md: 写 45/45，应为 42/42
docs/history/X-EXECUTION-MODEL-v2.md: 写 42/42，应为 45/45
docs/history/FORK-BRIEF.md: 写 45/45，应为 48/48   （两处）
docs/QUICKSTART.md: 写 42/42，应为 45/45
```

**一次抓出 4 个文档、19 处过期数字。** 这恰好演示了三件事：

| 观察 | 含义 |
| :-- | :-- |
| 它**打红了** | 这是**真检查**（有负例能力），不是占绿灯的假检查 |
| 它抓的是"数字腐烂"，不是"功能坏了" | **文档与实现的漂移是无声的**，只有机器对账才看得见 |
| 19 处同时过期 | 说明这些数字**从来没人维护过** —— 而我们过去"审查没问题"的依据里，就有这些数字 |

**顺带产出**：`（已删除）` —— 机械校正所有活文档里的 preflight 数字，不让它再烂。
（这也回答了一个设计问题：文档里**不该硬写会变的数字**，要么引用 `（已删除：数字口径取消）`，要么让脚本同步。）

### 这条给审计方法补一条硬规矩

> **任何"数字型"断言（工具数、检查项数、覆盖率、通过率）都必须由一个脚本生成，不许手写。**
> 手写的数字 = 会腐烂的证据 = 未来某次审查里骗过自己的东西。

## 九、树状走查：把"领域→枝→叶"变成可机检的覆盖矩阵

### 9.1 你的直觉是对的，但上次失败的原因是"树停在文档层面"

我们画过树。图很好看，**没有一行代码去走它** → 每条叶子都"存在"，每条都"没被走过"。
所以这次把它做成 **JSON + 走查脚本**：

```
path-tree.json(S1 已删)      ← 树本身（7 领域 / 14 枝 / 27 叶）
path-walk.py(S1 已删)       ← 逐叶走查（技能在不在 / 工具能不能取用 / 有没有见证物 / 有没有样本）
path-tree-baseline.json(S1 已删)  ← 棘轮基线（只降不升）
preflight 第 19 组              ← 每叶必须有见证物 + 缺 fixture 数不超基线
```

### 9.2 每条叶子必须写清六件事（缺一不算叶子）

| 字段 | 含义 | 为什么必须有 |
| :-- | :-- | :-- |
| `trigger` | 用户会怎么说这句话 | 否则不知道它该在什么话术下被触发 |
| `skills` | 该走哪个技能 | 否则"知识不到场" |
| `tools` | 该用什么工具/ MCP | 否则会手搓 |
| `forks` | 这条路内部有哪几个分叉 | 一张叶子往往不是单一路径 |
| `fail` | 看到什么就说明这条路走错了 | 否则一路走到底 |
| **`witness`** | **怎么算做成**（可观测） | **没有它，"完成"就没定义** |
| `fixture` | 拿什么样本回放 | 没有样本 = 无法验证 |

**`witness` 是最关键的一列**：写不出"启动后无激活提示 + 功能项可用（用户真机验证）"这种可观测句子的叶子，实际上是在赌。

### 9.3 首次走查结果（诚实数字，2026-10-23）

```
7 个领域 / 27 条叶子
  缺 fixture : 26 / 27      ← 真瓶颈：案例库只有 1 个真样本
  工具不可用 : 2  / 20      ← asar / pyinstxtractor（真的没装）
```

**26/27 条叶子没有样本** —— 这正是为什么"审了很多遍还是漏"：
**叶子有定义、有见证物，但没有一条能被跑一遍。**

### 9.4 走查顺手抓到一个真 bug（自己的假阴性）

第一次跑 `--tools`，它报了 **10 个工具"不可用"**：`radare2, dnspy, de4dot, confuserex, upx, pe-sieve, asar, jadx, pyinstxtractor, apktool`。

实际上 `jadx / apktool / radare2` 就在仓库的 `Tool/mcp/Tool/safe/` 下（.bat / .jar 形式），
`upx / dnspy / de4dot / pe-sieve` 都在 `D:\Tools` 下 —— **机器上全都有**。

原因：我的 L0 判据只查了 `where`（PATH）。**这正是你反复说的那个病："明明电脑上有，它说没有"**。
修法：复用仓库里已有的八层发现（`tool_autodiscover.py`，`tool-run.ps1` 用的就是它）。

修完实测：**18/20 可用**（只剩 `asar` / `pyinstxtractor` 真没装）。

> **这条特别值得记住**：连"检查工具在不在"这个最基础的动作，我自己第一版都写出了假阴性。
> 所以"审查"必须配**负例**——否则你无法知道你看到的绿灯是真绿还是判据写错了。

### 9.5 树状走查的四条纪律

1. **叶子要细到"一种具体形态"**：不是"逆向 PE"，而是"PE·有壳·带磁盘完整性自检"。
2. **一条叶子 = 一次回放**；没有样本就标 `缺 fixture`，**不许**用"理论上可以"代替。
3. **走查必须能报红**：`path-walk.py` 退出码非 0 时要有人管，不能只看汇总。
4. **棘轮基线**：`缺 fixture` 数量只准降。今天 26，修一条改一条，不许回涨。

### 9.6 这解决的是"永远审不完"吗

不解决"永远"。**它把"审不完"变成"可枚举 + 可排期"**：

- 过去：不知道还有多少条路没验证 → 只能每次出事再回来修；
- 现在：**27 条叶子，1 条 OK，2 条连工具都没有，24 条缺样本** → 这是一张可以排期的清单。

**先补齐 3 条最关键叶子的 fixture（PE 有壳 / 联网卡密 / APK 未加固），比再写 10 篇文档有用。**

## 七、一句话

> **过去我审的是"东西在不在"；要审的是"它在这条路上会不会被触发、触发了会不会生效、失效了会不会有人知道"。**
> **三问答不上来，就不许说完成；负例打不红，就不许算通过。**
