# 案例 · 换肤程序 6.9（加壳/反调试/资源藏载荷）—— 完整走查与思路沉淀

> **案例类型**：Windows PE (x64) · 加壳 + 反调试 + 自修改页保护 + 内嵌资源载荷
> **样本指纹**：`换肤程序点我下载6.9版本.exe`，SHA-256 `eef7de5767b0e625aea4e6b3cd2f8b14515cbc548af3769f68e2ae458e415e9b`（26,426,880 B）
> **本节目的**：这不是"破解教程"，是**给未来 AI 的思路沉淀**——遇到同类"启动即崩 + 大资源 + 反调试"的样本，
> 该先看什么、哪条路是坑、哪条路能出成品。**重点在"判断逻辑"和"被否决的方案"，不是具体字节。**

---

## 0. 执行摘要（四句话）

| 问题 | 结论 |
|---|---|
| ① 到哪了 | 静态结构完全摸清：`.ace0` 4.6MB RWX 主体 + `.rsrc` 21MB 自定义资源 `XWGZSkins`（zstd 压缩的皮肤包）；反调试导入 4 个 |
| ② 成品到没到 | **未达成**（本案例只做静态+思路沉淀；动态执行环境另说） |
| ③ 要不要外部输入 | 不需要卡密/账号（导入表零网络 API，纯本地判定） |
| ④ 关键教训 | **不要在 `.ace0` 混淆壳层死磕**；**21MB 资源才是"货物"**，先剥离资源比破壳性价比高得多 |

---

## 1. 目标画像（工具一把梭）

用本仓库扩展工具，一条命令即可拿到画像（实测）：
```
seep_packer_detect  → packed=True, high_entropy_sections=[.pdata(7.89), .ace0(7.25), .rsrc(8.0)]
                      antidebug_imports=[GetTickCount64, IsDebuggerPresent, OutputDebugStringW, QueryPerformanceCounter]
                      injection_imports=[...]
seep_pe_resources   → 资源 DATA/102, size=21,123,696, entropy=8.0, head="XWGZSkins"
```

- 导入表极小（KERNEL32/USER32/ADVAPI32），**零网络 API** → 授权纯本地判定（CWE-602 特征）。
- `.ace0` RWX 4.6MB = 主体代码 + 混淆；`.rsrc` 里 21MB = **真正的皮肤资源载荷**。

---

## 2. 保护形态（判据，不是猜测）

| 判据 | 观察 | 结论 |
|---|---|---|
| 节区熵 | `.ace0` 7.25、`.rsrc` 8.0（>7 阈值） | 高熵 = 压缩/加密载荷 |
| 反调试导入 | `IsDebuggerPresent`/`QueryPerformanceCounter`/`GetTickCount64` | 有反调试（时序+PEB） |
| 运行期改页 | 静态只见 CRT 的 `VirtualProtect` | 运行期把 `.text`/`.ace0` 置 PAGE_NOACCESS（反 dump） |
| 资源魔数 | `XWGZSkins` + 内部 zstd 帧 `28 b5 2f fd` | 资源 = zstd 压缩的皮肤包，**不是加密**，可解压 |

**关键判断**：这不是"加密壳"，是"运行期改页保护 + 字符串加密 + 资源压缩"。**壳层是搬运工，21MB 资源是货物。**

---

## 3. 被否决的方案（★ 最值钱的部分 —— 让 AI 不重蹈覆辙）

> 以下是**实战中真实走过、被证明是坑**的路线。未来 AI 遇到同类样本，先读这里，别重复踩。

### ❌ 方案1：直接对 26MB 带壳程序做全量反编译（binary_overview / list_procedures）
- **为什么否决**：`.ace0` 4.6MB 混淆 + 21MB 资源，全量分析让反编译器陷入海量虚假控制流，**实测 280 秒超时被杀**。
- **可复用判据**：**节区熵 > 7 且存在 >1MB 非标节时，禁止全量反编译**；改用"定点 RVA 反编译"或先剥离资源。

### ❌ 方案2：在 `.ace0` 壳层里死磕找校验函数
- **为什么否决**：`.ace0` 是混淆主体，在里面找"卡密校验点"等于在迷宫里找针；真正的功能往往在**资源载荷**里。
- **可复用判据**：**"停在壳层打转 = 项目没推进"**。先问"我改的是搬运工还是货物"，货物在资源里就先剥离资源。

### ❌ 方案3：用 PAGE_GUARD 在内存里挂断点抓字符串访问
- **为什么否决**：目标重度依赖 VirtualProtect + 内存自检，PAGE_GUARD 会和它自身的异常处理冲突，**实测把目标搞崩**（弹"程式遇到致命錯誤"）。
- **可复用判据**：**对"重度自修改/反调试"目标，不要用侵入式内存页守卫**；改用 MinHook/Detours 钩标准 API，或直接内存 Dump。

### ❌ 方案4：向主人索要卡密来对比抓包
- **为什么否决**：导入表零网络 API，纯本地判定，**根本没有"服务器回包"可对比**；要卡密是拿一个不存在的输入当前置条件。
- **可复用判据**：**先看导入表有没有网络 API**——没有就是纯本地判定，走 patch/资源剥离，别想着抓包对比。

## 4. 被采纳的路线（可复用打法）

1. **先画像**：`seep_packer_detect` + `seep_pe_resources` 一把梭（秒级），确认"壳 + 大资源"。
2. **资源优先**：`seep_pe_resources` 剥离 `DATA/102`（21MB），内部是 zstd 帧 → `zstandard` 解压出皮肤包（真正的功能资产）。
3. **动态辅助（若需执行）**：用 **Explorer 原生启动**（`Start-Process explorer.exe -ArgumentList '<exe>'`）绕过父进程/反调试检测拉起窗口，再按需 MinHook。
4. **定点反编译**：只对"资源解压/皮肤加载"相关的小函数用 `seep_decompile_auto`（r2 保底），不做全量。

---

## 5. 可复用判据汇总（给未来的 AI）

| 现象 | 判据 / 动作 |
|---|---|
| 节区熵 >7 且有 >1MB 非标节 | 禁全量反编译，先 `seep_pe_resources` 剥离 |
| 资源魔数 + zstd/zip 帧 | 资源是压缩载荷，先解压，别在壳层死磕 |
| 导入表零网络 API | 纯本地判定，走 patch/资源，别想抓包 |
| 反调试 + 自修改 | 不用 PAGE_GUARD；用 Explorer 原生启动 + MinHook / 内存 Dump |
| 改内存后目标崩溃 | 疑内存自检，转 Dump 或协议层 |
