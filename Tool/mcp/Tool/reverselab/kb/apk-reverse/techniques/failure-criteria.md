## 用途

遇到下面任一信号，**先停手判定"到哪一步"**，而不是继续加脚本。
判据的作用是让"只能看懂结构"成为合法交付，避免把不确定性包装成结论。

## 一、硬停手（立刻停，回落到上一档上限）

| 触发 | 判据 | 处置 |
| :-- | :-- | :-- |
| 目标带商业加固壳，且无设备/无内核权限 | 动态脱壳需要进程内 dump，静态只能看到 stub | 上限降到"只能看懂结构"，写清卡在哪 |
| 授权校验在服务端且无法观察响应 | 本地改完仍然联网失败 | 停，报告"关键在服务器上" |
| 需要 root / LSPosed / KernelSU 才能继续 | 设备能力不足 | 列 A/B/C 让用户选，不假设有 |
| 需要重打包签名才能验证，但用户要求保持原签名 | 签名体系冲突 | 停，给两条出路（自签名验证 / 只做静态补丁） |
| 反调试/反注入已在目标内生效 | 附加即被杀或崩溃 | 停，先做检测面枚举，不硬附加 |

## 二、软停手（两次尝试仍无进展就停）

- 同一形状的失败连续两次（同一条命令、同一类偏移、同一种 hook 位置）。
- 静态结论无法用第二路证据交叉（只有一条观察，没有独立复算）。
- 关键偏移在样本更新后失效，且没有版本身份（哈希）记录。

## 三、"看起来成功"的四种假完成

1. **装上了但没验活**：重打包后只说"安装成功"，没有跑核心功能一次。
2. **补丁生效但没有反例**：改完只看 PASS，没有保留一个"应当仍 FAIL"的对照件。
3. **去广告只去掉本地那类**：服务端下发的广告仍在，却被写成"已去除"。
4. **Java2C 结论靠"看不到"**：没做导出符号/调用链对照就断言"不是 Java2C"。

对应修法都在 `Tool/skill/apkseep/references/verification.md` 的 claim ladder 里。
