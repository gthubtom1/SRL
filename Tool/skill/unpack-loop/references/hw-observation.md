# 硬件观测层：软件调试器做不到时的那一层

> 加载时机：加密壳/虚拟化保护让软件断点、单步、内存断点都失效（例如壳检测 dr 寄存器、
> 或用内核/虚拟化层拦截）。**这是最后一条路，也是最贵的一条。**
> 来源参考：exe-reverse 的 hardware-observation 层（我们按自己的判据重写，不照搬）。

## 0. 先明确代价（为什么放最后）

| 项 | 说明 |
| :-- | :-- |
| 需要什么 | 管理员权限；可能需要在**裸金属/可控 hypervisor** 上跑；虚拟机里某些路由不可用 |
| 副作用层级 | **L2–L3**：可能装驱动、开测试签名、改启动项 → 按 `AGENTS §四之五.9`，**必须先问用户**，默认不做 |
| 何时才用 | 软件断点被清、`bph` 被检测、或壳在 VM 层拦截 `int3` |

> 判据：如果普通调试器（x64dbg）还能下断点命中，**就不要上硬件层**。
> 上硬件层的理由必须写进账本，否则下次又会重复"以为软件层不行"。

## 1. 三条硬件路由（按侵入性排序）

| # | 路由 | 能看什么 | 做什么（示例） | 判据 |
| :-: | :-- | :-- | :-- | :-- |
| **1** | **CPU 调试寄存器（dr0–dr3）** | 对指定地址的 读/写/执行 | x64dbg：硬件断点（命令名按版本确认，先 `help bph`）；每次最多 4 个 | 命中时 RIP 落在预期地址；壳没有因为 dr 被清而改变行为 |
| **2** | **指令跟踪（Intel PT / ETW 类）** | 一段时间内的执行流（不中断） | 需要专用工具；产出 trace 再离线分析 | 能定位"从壳跳到原始代码"的那一跳 |
| **3** | **hypervisor 辅助观测** | 壳以为自己在裸机上时的内存/寄存器视图 | 需要在可控虚拟化层；**普通 VM 里壳会检测到** | 壳不再触发反 VM 分支；能拿到解密后的镜像 |

**建议顺序**：1 → 3 → 2（1 最便宜；3 最有效但最贵；2 数据量大、分析成本高）。

## 2. 与"我们的纪律"如何对齐（这几条不能破）

| 纪律 | 在这一层的落地 |
| :-- | :-- |
| **启动纪律** | 目标仍由 `launch-gui.ps1 -Mode shell`（explorer 父进程）拉起，不由 python/bash 拉起 |
| **副作用层级** | 装驱动/开测试签名/改启动项 = **先问用户**；默认停在"只做进程内观测" |
| **两击熔断** | 同一路由失败 2 次 → 停，回报告写"硬件层也不通"，不许第 3 次 |
| **证据** | 每次观测记录：工具/版本、时间窗、地址范围、产出文件哈希；无这些 = 不算证据 |
| **不改整机网络** | 即使壳要联网验证，也不改本机代理/网卡（`cmd-guard` 已拦） |

## 3. 三个"看起来能用其实不行"的坑

| 坑 | 为什么不行 | 怎么避 |
| :-- | :-- | :-- |
| 在普通虚拟机里上 hypervisor 路由 | 大多数商业壳检测 hypervisor（CPUID/时序/驱动枚举），一进就自毁 | 要么裸金属，要么用壳不检测的层（先做环境探测） |
| 用单步代替硬件断点 | 单步会被 `rdtsc` 时间差检测到 | 用"跑一段 + 硬件断点"代替逐条单步 |
| 4 个 dr 寄存器用完还硬塞 | 超出即失效，且行为像"没设断点" | 合并断点（同一页范围）或改用内存断点 |

```text
# 上硬件层前的确认清单（缺一项就不要上）
[ ] 已记录：为什么软件层不行（具体现象，不是"感觉"）
[ ] 已问用户：允许管理员权限/驱动/测试签名吗（L3）
[ ] 已准备：工具名+版本、时间窗、地址范围、产出哈希
[ ] 已设熔断：同一路由失败 2 次即停
```

## 4. DR 预算：4 个断点怎么分配

> x86/x64 只有 DR0–DR3 四个地址寄存器。用完就是没了，而且**用错了会让壳看见 DR 非零**。
> 所以硬件断点不是“随便下”，而是**预算分配**。

| 优先级 | 用途 | 建议断点类型 | 为什么优先 |
| :-: | :-- | :-- | :-- |
| 1 | 目标代码节首（等解密完成/首次执行） | 执行（X） | 不写入内存，不会触发自校验 |
| 2 | 壳的出口跳转（§OEP 的 `jmp`/`ret` 前） | 执行（X） | 直接看到交接点的寄存器/栈 |
| 3 | 被写保护/Guard 的页首地址 | 读写（R/W） | 看到“谁在写解密数据” |
| 4 | 敏感 API 首字节（`NtQueryInformationProcess` 等） | 执行（X） | 观察反调试调用而不 hook |
| 备 | 壳自己会检查 DR 的场景 | **不下**，改外部采样 | 下了就等于打自己一巴掌 |

**判据**：下断后必须能回答“这四个断点分别代表哪四个问题”；
回答不上来就是盲目下断，先回去想清楚要观测什么。

| 错误用法 | 现象 | 后果 |
| :-- | :-- | :-- |
| 在同一页内下 4 个字节级断点 | 4 个 DR 瞬间用完 | 真正的关键地址没位置放 |
| 对 `kernel32` 下执行断点而目标走 syscall | 永不命中 | 误以为“没调用” |
| 断点设在被 CRC 覆盖的页上（硬件断点不改字节，安全） | 安全 | 但若用“内存写断点”去改值就会触发 |
| 下完断点又单步 | 时序跳变大 | 被 `rdtsc` 抓到（AD-14） |

## 5. 把 4 个断点“放大”：页合并与分阶段

| 手法 | 做法 | 适用 | 代价 |
| :-- | :-- | :-- | :-- |
| 页级合并 | 用 1 个断点盯整段（执行断点本身按页生效），而不是每个候选地址一个 | 候选多、都在同一节 | 命中后需自己判断是哪段触发 |
| 分阶段重下 | 阶段 1 用完四个，命中后**立即删除**并下阶段 2 的四个 | 流程分阶段（解密 → 填 IAT → 跳 OEP） | 漏掉阶段间隙的事件 |
| 断点 + 外部采样 | DR 盯“一开始执行”，外部 `ReadProcessMemory` 定时采样内容 | 壳有 DR 检测但代码节可读 | 看不到寄存器，只看内存 |
| 换成 ETW | 不下断点，用事件流定位时间窗，再在窗口内下断 | 需要“大概时间点”而非“精确指令” | 看不到寄存器/栈 |

```text
# 分阶段断点计划（写在纸上再下，不要边试边改）
阶段1 [TLS 后]：DR0=目标节首(X)  DR1=壳出口jmp(X)  DR2=目标节写(RW)  DR3=空留
阶段2 [首次进入目标节]：删 DR0/DR1；DR0=首个API thunk(X)  DR1=IAT区写(RW)
阶段3 [确认 OEP]：全部删除，改外部采样确认稳定（见 oep-locate.md §4）
```

**判据**：每次改断点计划都要在账本里记一行（时间、存活的 DR、删了什么、为什么）。
否则“断点突然不命中”时无法回溯是壳清的还是你自己删的。

## 6. ETW / WPR：不改字节也能拿到时间窗

> 这是硬件层之外最便宜的一层：**完全不接触目标内存**，只拿系统事件。
> 适合“先框时间窗，再决定要不要上硬件断点”。

```bash
# Windows：用系统自带的 WPR 采一轮（需管理员；按本机 WPR 版本确认参数）
wpr -start GeneralProfile -filemode
# …让目标跑到要观察的阶段…
wpr -stop work/task/trace.etl
# 导出成可读事件（tracerpt 随系统自带）
tracerpt work/task/trace.etl -o work/task/trace.xml -of XML -summary work/task/summary.txt
```

**通过长什么样 / 期望输出**：

```text
Summary of tracing:
  Number of events lost: 0
  Buffers: 512
  Events: 1,284,331
  Trace duration: 00:00:41
```

判读：`Events lost: 0` 是硬要求——丢了事件的时间窗就不能用来“证明没发生”。
拿到 `trace.xml` 后用 `grep` 找目标进程名/模块加载/线程创建，得到“大概时间点”，
再在那个窗口内下硬件断点。

| 要看的 | 在 ETL 里找什么 | 能得出什么 |
| :-- | :-- | :-- |
| 进程/线程生命周期 | `Process/Thread Start` 事件 | 解密线程何时出现 |
| 模块加载 | `Image/Load` 事件 | 壳是否加载了额外 DLL（提示注入/反调试） |
| 文件/注册表 | `FileIO`/`Registry` 事件 | 是否落地/写自启动 |
| 网络 | `Microsoft-Windows-TCPIP`/`NDIS` 事件 | 首个外连的时间戳（对照基线） |

**约束**：WPR 需要管理员权限且会系统级采集 —— 按 `AGENTS §四之五` 属于“先问用户”的档位；
不要为了“看一下”就开一小时的全量 trace。

## 7. 三种观测手段的适用边界（别用错层）

| 手段 | 能看寄存器/栈 | 能改字节 | 被 DR 检测发现 | 时间成本 | 何时用 |
| :-- | :-: | :-: | :-: | :-- | :-- |
| 软件断点/单步（int3） | ✅ | ✅（会写 0xCC） | 会（AD-31） | 低 | 无自校验的普通程序 |
| 硬件断点（DR） | ✅ | ❌ | 会（AD-24/25） | 中 | 有自校验、或不能改字节 |
| ETW / WPR | ❌ | ❌ | 不会 | 中 | 定时间窗、看系统侧行为 |
| 外部 ReadProcessMemory | ❌ | ❌ | 可能（AD-33 类） | 低 | 看内存内容是否解密完 |
| Intel PT 类指令跟踪 | ✅（事后） | ❌ | 一般不会 | 高 | 需要完整执行流且不能用断点 |

**判据**：选手段前先回答“目标会不会因为这一层而改变行为”；
会 → 换下一行。这张表就是选择顺序。

## 8. 观测记录：哪些字段缺了就不算证据

| 字段 | 例 | 缺了会怎样 |
| :-- | :-- | :-- |
| 工具与版本 | `x64dbg 2024.05.15` / `WPR 10.0.22621` | 换版本结果不同时无法解释 |
| 时间窗 | `T+1.2s ~ T+3.8s`（用启动时间做原点） | 无法与 ETW/pcap 对齐 |
| 地址范围 | `0x140012000-0x140016000` 及所属模块 | 下次运行 ASLR 后对不上 |
| 断点/采集配置 | `DR0=X@0x140012A40, DR2=RW@0x140013000` | 无法区分“没命中”与“没下对” |
| 产出文件 + sha256 | `trace.etl` / `d1.bin` | 证据不可复验 |
| 环境前提 | 管理员/裸机/VM/`test signing` | 别人复原不了就不再是证据 |

**判据**：六项全有 → 这条观测可以进报告作为 `observed`；缺任一项 → 只能写“仅供自用线索”。

## 9. 上硬件层前先确认“壳看不看得见这一层”

```bash
# 只看不改：确认当前环境是不是虚拟化、有没有内核调试/测试签名
systeminfo | grep -iE "hyper-v|hypervisor|System Model|BIOS"
powershell -NoProfile -Command "(Get-CimInstance Win32_ComputerSystem).Manufacturer; (Get-CimInstance Win32_ComputerSystem).Model"
bcdedit /enum {current} | grep -iE "testsigning|debug|hypervisorlaunchtype"
```

**通过长什么样 / 期望输出**（这是一个要“看清事实”而不是“通过”的例子）：

```text
Hyper-V Requirements:     A hypervisor has been detected.
Manufacturer              VMware, Inc.
Model                     VMware Virtual Platform
testsigning               Yes
```

判读：`hypervisor has been detected` + `VMware` → 壳若有 AV-1/AV-2 类检测，大概率在启动早期就改行为。
两条路：① 换裸机（先问用户）；② 先做环境对照实验，证明“样本在 VM 里的行为差异是环境导致”。
不确认就去上 hypervisor 路由，是最典型的白忙。

**实例说明：VMware 里看不到的“干净行为”不算干净**：
基线在 VM 里跑得通 ≠ 裸机跑得通；反之亦然。任何“硬件层观测到了什么”的结论，
必须配一句“在哪种环境里观测到的”。

## 10. 硬件层的失败判据（看到即停）

| 现象 | 判定 | 动作 |
| :-- | :-- | :-- |
| 下 DR 后目标行为立刻变化 | 壳在查 DR（AD-24/25） | 删 DR，改外部采样/ETW |
| 硬件断点命中次数 ∞（疯狂命中） | 断点落在热循环里 | 缩小范围或改成“命中 N 次后删断点” |
| 4 个 DR 已满但关键点没盯上 | 预算用完 | 分阶段重下（§5），不要硬塞 |
| ETW 事件丢失 >0 | 时间窗不可用 | 减小 trace 体量/缩短窗口重采 |
| 单步 10 条指令后崩 | 时序检测 | 改“跑一段 + 硬件断点” |
| hypervisor 路由下目标仍然自毁 | 壳检测了 hypervisor 自身 | 停（已两次）→ 写“不可绕”或换路线 B |
| 没有管理员权限 | 内核/驱动路由不可用 | 写 `blocked_at=privilege`，不要伪造结果 |

**约束**：上硬件层前必须有“为什么软件层不行”的**具体现象**（不是“感觉被检测”）；
同一路由两次失败就停，这是 SKILL 的铁律 8。

## 10bis. 指令跟踪（Intel PT）的最小落地流程

> 适合“不能用断点、但要完整执行流”的场景。代价是**数据量大 + 事后分析**，不要一上来就用。

| 步 | 做什么 | 产出 | 判据 |
| :-: | :-- | :-- | :-- |
| 1 | 确认 CPU 支持 PT（Intel 6代+，且未被 BIOS/虚拟机关闭） | `/proc/cpuinfo` 与 `perf list` 的 intel_pt 条目 | 有 `intel_pt` 事件可用 |
| 2 | 框定采集范围（只采目标进程/只采某段时间） | perf 过滤器 | trace 体积可控（GB 以内） |
| 3 | 采集 | `perf.data` | 采集期间无断点/无单步 |
| 4 | 解码成地址流 | `perf script` 输出 | 能连续看到地址跳转 |
| 5 | 与静态对照（哪些地址在原始节） | 一张“地址 → 节”表 | 能看到从壳节跳入原始节的那一跳 |

```bash
# Linux 侧最小示例（Windows 下按本机可用工具等价处理）
perf list | grep -m1 intel_pt
grep -m1 -o 'intel_pt' /proc/cpuinfo || echo "no PT flag"
perf record -e intel_pt//u -p <pid> -- sleep 5
perf script --itrace=i0ns -F ip,comm > work/task/pt.txt
wc -l work/task/pt.txt
```

**通过长什么样 / 期望输出**：

```text
intel_pt
     12488173 work/task/pt.txt
```

判读：有 `intel_pt` 说明可用；`pt.txt` 里能看到地址流（百万行量级属正常）。
**关键判据不在这里**，而在“能不能从地址流里找出第一次落入原始代码节的跳转”：
把 `pt.txt` 里的 IP 逐个对到节表范围（`rabin2 -S` 的 VA 范围），出现“前一跳在 `UPX1`、后一跳在 `.text`”
即定位到交接点。

**约束**：

- PT 采集会占 I/O 与磁盘（GB 级），先算磁盘余量；
- 虚拟机里 PT 常不可用（nested 支持差）——这是“环境不匹配”，不是“没这技术”；
- 拿到 trace 后不要直接拿地址当结论：地址必须映射到节/模块，否则只是数字。

**两个常见误判**（写报告前自检）：

1. “PT 里没看到目标地址” ≠ “没执行”——过滤器/权限/丢包都会造成空白；空白时先查 `perf.data` 的大小与丢弃提示。
2. “地址落在原始节” ≠ “已到 OEP”——还需 §OEP 的四条硬判据；PT 只能给出候选地址。
