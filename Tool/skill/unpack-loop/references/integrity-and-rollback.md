# 完整性对抗与回滚：改字节之前先保证能退回去

> 加载时机：目标会校验自身（CRC/哈希/页校验/服务端校验），或者你已经改过一次字节、目标开始"改完又变回原样"。
> 本页只解决一件事：**怎样在不破坏目标的校验链、且任何一步都能退回原状态的前提下工作**。
> 反调试技术本身见 `anti-debug.md` §3；本页是它的**工程化外壳**：排序、记录、回滚。

## 0. 两条前提（缺一条就不要动手）

| 前提 | 具体要求 | 违反的后果 |
| :-- | :-- | :-- |
| **原件只读** | 原始样本 `sha256` 先算好，权限设只读，任何工具都只打开副本 | 原件被改 → 后续所有结论失去基准 |
| **可回滚** | 每次改动前有 `rollback point`（副本 + 快照 + 哈希台账） | 改坏了只能重新找样本，进度归零 |

**判据**：动手前你能同时说出"原件在哪、它的 sha256、我的副本在哪、怎么退回去"四件事。
说不出 → 先补这一步，不要"先改一下试试"。

## 1. 回滚设施的最小集（10 分钟搭好，省几小时）

```bash
# 目录布局：原件只读区 / 副本工作区 / 证据区 / 回滚点区
TASK=work/unpack-$(date +%Y%m%d-%H%M)
mkdir -p "$TASK"/{orig,copy,evid,rb}
cp -n target.exe "$TASK/orig/target.exe"          # 原件（随后设只读）
chmod 0444 "$TASK/orig/target.exe"
cp "$TASK/orig/target.exe" "$TASK/copy/target.exe"
# 哈希台账：每份文件都登记，之后任何"不一致"都能查
( cd "$TASK" && find . -type f -print0 | xargs -0 sha256sum ) > "$TASK/evid/manifest.sha256"
```

```bash
# 回滚点：每次改字节之前打一个（增量，不复制整目录也行）
cp "$TASK/copy/target.exe" "$TASK/rb/step-01-before.exe"
sha256sum "$TASK/rb/step-01-before.exe" | tee -a "$TASK/evid/manifest.sha256"
# 回滚 = 用 rb 里的副本覆盖 copy，并重新校验哈希
```

**通过长什么样 / 期望输出**：

```text
$ sha256sum -c evid/manifest.sha256
./rb/step-01-before.exe: OK
./copy/target.exe: OK
./orig/target.exe: OK
```

判据：`sha256sum -c` 全 `OK` 才能继续；出现 `FAILED` → 说明有文件被工具悄悄改过，
先查是哪一步，不要在当前状态上继续叠加改动。

| 设施 | 最低要求 | 常见偷懒 | 后果 |
| :-- | :-- | :-- | :-- |
| 原件副本 | 只读 + 哈希 | 直接分析下载目录里的文件 | 原件被工具改，无法复验 |
| 工作副本 | 每步一变 | 在原件上反复改 | 无法回滚到上一步 |
| 回滚点 | 改字节之前打 | 只在"大改"前打 | 小改坏掉也要重来 |
| 台账 | 追加式（不改旧行） | 每次覆盖 manifest | 历史不可查 |
| 快照（VM） | 运行样本前 | 跑完再拍 | 残留物污染下一次实验 |

## 2. 完整性校验的六种形态（先判形态，再选策略）

| 形态 | 静态线索 | 动态判据 | 影响范围 |
| :-- | :-- | :-- | :-- |
| 逐字节 CRC32 | `crc32` 串、CRC 表（256×4）、按节循环 | 改任一字节 → 走退出/降级分支 | 被覆盖区 = 整节或整文件 |
| 节哈希（MD5/SHA） | `CryptHashData`/`BCryptHash`、按节调用 | 同上，但只在特定时刻校验（启动/请求前） | 指定节 |
| 页校验（PAGE_GUARD） | `VirtualProtect(...,0x40)`、guard 异常 | 在目标内读解密页 → 自毁 | 解密后的代码页 |
| API 调用型 | 导入上列 API + 一次性调用 | 校验函数返回值决定后续 | 可 patch 返回值 |
| 服务端校验 | 客户端算哈希 → 发出；服务端拒绝 | 抓包看到哈希/签名参数 | 本地改无效 |
| 自修复写回 | 改后几秒内字节自动复原 | 内存字节 vs 你刚写的字节不一致 | 全节（周期性） |

**判据**：能说出"校验覆盖哪段区间、多久一次、失败后做什么"三件事，才算判清形态。
只写"有自校验"等于没判。

## 3. 自修复（self-heal）的识别：为什么"改完又变回去"

| 现象 | 说明 | 怎么确认 |
| :-- | :-- | :-- |
| 用调试器改了内存字节，过几秒又变回原值 | 后台线程/定时器在校验并修复 | 在目标地址下**写**断点，看是谁写的（调用栈） |
| 改了磁盘文件，运行后内存里是原值 | 程序从资源/备份里恢复 | 找第二份副本（`iR` 抽资源或 `.rsrc` 里的 PE） |
| 断点命中几次后"自己消失" | 校验线程还原了 prologue | 对比命中前后 16 字节 |
| 改一处需要同时改 N 处才生效 | 冗余校验（多份副本互相比对） | 搜同一段字节在镜像里出现的次数 |

```bash
# 确认"是不是被写回"：两次 dump 差分（外部读，不注入）
python Tool/skill/malware-analysis/scripts/dump-restore.py dump --pid <pid> --out d_before.bin
# …在调试器里改一个字节…
python Tool/skill/malware-analysis/scripts/dump-restore.py dump --pid <pid> --out d_after.bin
cmp -l d_before.bin d_after.bin | head
```

**通过长什么样 / 期望输出**：

```text
   1301 102 314      ← 偏移 1300（0-based）处，原本 0x42 变成了你写的 0xCC
```

第二次 dump 里那一字节如果又变回 `102`（八进制 = 0x42）→ **自修复已确认**；
此时任何"改字节"策略都注定失败，必须换策略（见 §4 排序）。

## 4. 对抗策略排序：从"不改字节"到"去掉校验"

| 顺位 | 策略 | 改动量 | 风险 | 适用形态 |
| :-: | :-- | :-- | :-- | :-- |
| 1 | **不改字节**：硬件断点 / 外部观测 / ETW | 0 | 最低 | 所有形态（首选） |
| 2 | 内存补丁（进程内，不落盘） | 1–N 字节 | 低（重启即失效） | 有自修复但周期够长；校验只在特定时刻 |
| 3 | 改期望值（把比对目标改成你的值） | 4–32 字节 | 中（改在校验区里可能触发另一处校验） | 哈希比对 |
| 4 | 改校验函数返回值 | 1–8 字节 | 中 | API 调用型 |
| 5 | 让校验读备份而不是被改页 | 指针级 | 中高 | 双视图/双副本 |
| 6 | 去掉校验调用 | 5–16 字节 | 高（可能破坏初始化链） | 最后手段，且必须能回滚 |

**判据**：每次选策略都要写下"为什么不选上一顺位"。写不出 → 你其实可以直接用顺位 1。

**约束**：

- 顺位 ≥3 的改动必须落在**不属于校验覆盖区**的地方，否则会引发下一轮校验；
- 任何写盘的改动前必须有回滚点；改完立刻跑 §1 的 `sha256sum -c` 记录新基线；
- 不为了"过校验"去 patch 内核/驱动（超出用户态范围，且属 L3）。

补两条容易被忽略的约束：

- 顺位 1 也有成本：硬件断点可能被 DR 检测（AD-24），外部读也可能被“读内存即调试”盯上；
  选 1 之前先用 `anti-debug-matrix.md` §十 的检索命令确认目标不查这些。
- 顺位 2 的“内存补丁”必须能重复施加：如果每次重启都要手改 10 处，就把它写成脚本并算哈希入台账。

## 5. 每次尝试的记录模板（事后能复盘的关键）

```json
{
  "step": 3,
  "target_sha256": "…",
  "copy_sha256": "…",
  "change": {"va": "0x140012A40", "file_off": "0x11A40", "before": "74 0F", "after": "EB 0F"},
  "strategy": "内存补丁（顺位2）",
  "why_not_1": "硬件断点被 DR 检测（AD-24）命中，目标自毁",
  "observed": "改后通过校验，首个请求发出（pcap 第 42 帧）",
  "side_effect": "无；重启后失效",
  "rollback_point": "rb/step-03-before.exe",
  "verdict": "confirmed"
}
```

| 字段 | 缺了会怎样 |
| :-- | :-- |
| `before/after` 原始字节 | 无法复现，也无法判断"是不是改错位置" |
| `why_not_1` | 无法证明你真的试过最低风险策略 |
| `observed` + 证据位置 | 变成"我记得改完能跑" |
| `rollback_point` | 出问题时只能重来 |
| `side_effect` | 把"改完就崩"误判成"样本本身坏" |

**判据**：模板五类字段（改了什么/为什么这么改/观察到什么/副作用/怎么退）全填，才算一次有效尝试。

## 6. 回滚演练：3 分钟验证"真能退回去"

```bash
# 1) 故意改一个字节（在副本上），确认能检测到差异
printf '\x90' | dd of="$TASK/copy/target.exe" bs=1 seek=$((0x11A40)) conv=notrunc 2>/dev/null
sha256sum -c "$TASK/evid/manifest.sha256" || echo "diff detected (expected)"
# 2) 回滚
cp "$TASK/rb/step-01-before.exe" "$TASK/copy/target.exe"
# 3) 校验回到基线
sha256sum "$TASK/copy/target.exe" "$TASK/rb/step-01-before.exe"
```

**通过长什么样 / 期望输出**：

```text
./copy/target.exe: FAILED        ← 第 1 步：确实变了
9f2c1a90d3ab…  copy/target.exe
9f2c1a90d3ab…  rb/step-01-before.exe   ← 第 3 步：完全一致，回滚可用
```

判据：两行哈希**完全相同**才算回滚成功；不同 → 回滚点本身已被污染，必须从原件重建。

## 6bis. 校验时机表：决定“什么时候不能改”

| 时机 | 典型信号 | 对你的影响 |
| :-- | :-- | :-- |
| TLS / 入口前 | 一启动就自毁 | 这时改字节必死；只能外部读 |
| 首窗口/首请求前 | 界面出现前崩溃或静默不联网 | 改完要等它过完这一段 |
| 周期定时（如每 500ms） | 改后几秒被写回 | 只适合“瞬时改完即用”的内存补丁 |
| 退出前 | 关闭时崩溃/报错 | 不影响分析，但会让“能跑”结论变差 |
| 服务端触发 | 本地无异常，远端拒绝 | 本地改无效（IR-4） |

**判据**：能画出“时间轴 + 校验点”，才能决定把补丁放在哪个窗口；
画不出就是“随机试”，属 IR-7。

## 6ter. 副本管理：命名、保留、清理

| 规则 | 做法 | 为什么 |
| :-- | :-- | :-- |
| 名称带序号与目的 | `rb/step-03-before-iat.exe` | 一周后还能看懂 |
| 每个副本都有哈希行 | 追加到 `manifest.sha256` | 可批量 `-c` 校验 |
| 回滚点不删 | 至少保留“最后一次可用” | 删除后只能从原件重建 |
| 中间产物（dump/log）同目录分开放 | `evid/` 与 `copy/` 隔离 | 避免把日志当样本重跑 |
| 清理前先归档证据 | 先算哈希再删 | 结论依赖证据 |

```bash
# 一次性校验全部副本并列出不一致项（只读）
( cd "$TASK" && sha256sum -c evid/manifest.sha256 2>&1 | grep -v ': OK$' ) || echo "all clean"
```

**通过长什么样 / 期望输出**：

```text
all clean
```

判据：输出 `all clean`（或空）才算干净；有行 → 那行就是被工具悄悄改过的文件。

## 7. 失败判据（IR-n，命中即停）

| # | 现象 | 判定 | 动作 |
| :-: | :-- | :-- | :-- |
| IR-1 | `sha256sum -c` 对原件报 FAILED | 原件被改 | 立即停，重新取授权样本；不要用现有文件继续 |
| IR-2 | 改了字节，第二次 dump 又被写回 | 自修复确认 | 升到顺位 1（不改字节） |
| IR-3 | 改校验函数返回值后目标仍退出 | 校验有多处/结果被再次使用 | 找汇聚点（`anti-debug-matrix.md` §十二） |
| IR-4 | 改完通过本地校验但服务端拒绝 | 服务端校验 | 停，转协议层分析 |
| IR-5 | 回滚后行为与基线不一致 | 有残留（注册表/文件/服务） | 恢复快照；不要在半污染状态继续 |
| IR-6 | 同一位置改了两次都失败 | 手法在此情形下失效 | 熔断，换策略顺位或换路线 |
| IR-7 | 无法写出"校验覆盖哪段、多久一次" | 形态未判清 | 回 §2/§3，先判清再改 |

**约束**：IR-2 + IR-6 同时出现，说明"改字节"这一整类策略都不通，直接转 `hw-observation.md` 的外部观测。

## 9. 一类常见自欺：把"没被校验"当成"校验已绕过"

| 说法 | 实际情况 | 正确写法 |
| :-- | :-- | :-- |
| "改了没崩，所以没有校验" | 可能校验只在特定时机（请求前/退出前） | "本次路径未触发校验，未覆盖 [请求前/退出前]" |
| "patch 了 CRC 函数，所以完整" | 可能还有第二处哈希 | "已定位 1 处，未穷举；搜索了 [关键词清单]" |
| "回滚了，所以干净" | 注册表/服务/文件可能残留 | "已恢复快照 + 校验 manifest 全 OK" |
| "原件没动过" | 没验证 | 贴 `sha256sum -c` 的 OK 输出 |
| "回滚点有备份" | 备份本身可能被污染 | 备份也要跟着 `-c` 校验一次 |

补一条判定纪律：每次写结论前重跑一遍 §1/§6ter 的校验命令；
命令输出（而不是记忆）是唯一能进报告的“原件没动过”。
