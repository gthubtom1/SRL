# 03 模型常见失误 — 协议复刻里最贵的 20 个错

> 范围：任何"看抓包 → 写字段表 → 重放/构造"的任务。
> 路由：插件装载链、扩展权限面按 `Tool/playbooks/plugin-analysis.md` 分析；纯算法还原组合 `softseep` / `unpack-loop`。
> 每条格式固定：**错误动作 → 为什么错 → 正确动作**。判据见 `01-criteria.md`，停手条件见
> `02-failure-criteria.md`。§1–§5 是主表 12 条（按主题分组），§6 是 13–20 条补充。

## 1. 按 pcap 包边界切消息

### 1.1 把每个 TCP 包当成一条应用层消息

- 错误动作：看到 `frame 8` 有 54 字节就把这 54 字节当一条完整消息解码。
- 为什么错：TCP 是字节流，消息边界由应用层决定；一个消息可能跨 3 个包，一个包也可能含 2 条消息。
  按包切会把 JSON 截成两半，然后得出"协议用自定义二进制"的错误结论。
- 正确动作：先按 TCP 连接、方向和序号重组，处理乱序、重传、重叠和缺口，再分帧；`--extract` 只是按包序拼载荷。无法验证重组时记录限制。对照原字节检查 `skipped_bytes`、尾部和帧对应关系，字节数守恒本身不能证明分帧正确。

### 1.2 用五元组合并会话

- 错误动作：把 `127.0.0.1:50000 → 127.0.0.1:8080` 的所有包当一个会话。
- 为什么错：端口会复用，同一五元组可能是 3 条先后建立的 TCP 连接；合并后 seq 跳变、长度方程解不出来。
- 正确动作：按 `tcp.stream`（SYN 起、FIN/RST 止）分会话；合并前先看 `tshark -q -z conv,tcp`
  的帧数是否对得上。

## 2. 只凭"像"就写字段

### 2.1 看到 `00 24` 就写"长度=36，含头"

- 错误动作：单帧凑出一个自洽解释就写进字段表。
- 为什么错：`len=36`、payload=36、frame=52、52-12-4=36 三者都能自圆其说；
  一帧无法区分"含头/不含头/含自身"。
- 正确动作：取 3 条不同 payload 长度的帧解 `len = a*payload + b`；再做**改长度负例**
  （改大→服务端等更多字节直到超时；改小→截断或 CRC 失败）。只写"疑似"直到负例闭环。

### 2.2 把 magic 当常量、跳过重同步测试

- 错误动作：`data.startswith(b"SPRX")` 就直接切片。
- 为什么错：payload 是 JSON 时可能包含 `"SPRX"` 字样；一旦错位，后续所有帧全错，但前几帧看着正常。
- 正确动作：解析器需统计 `skipped_bytes` 并用垃圾字节、假 magic 和截断分别验证恢复。`proto-repro.py --self-test` 只覆盖垃圾字节，不能证明假 magic 恢复正确。

### 2.3 把 protobuf 字段号当业务 id

- 错误动作：看到字段 3 的值是 1001，就写"字段 3 = 用户 id"。
- 为什么错：protobuf 字段号是 schema 里的槽位，同槽位可承载不同语义；默认值字段可能根本不编码。
- 正确动作：用"相关性"定语义（同字段在多条业务中与某业务值同步变化），
  并检查 `protoc --decode_raw` 的 wire type（varint/len/32bit/64bit）是否与假设一致。

## 3. 校验与加密的错误假设

### 3.1 样本对上 CRC32 就宣布"校验是 CRC32"

- 错误动作：`binascii.crc32(header+payload)` 与末 4 字节相等，直接写结论。
- 为什么错：3 帧样本下，简单和、异或、Adler32 甚至"固定值"都可能碰巧相等；
  覆盖范围（是否含 magic/是否含长度字段）也没验证。
- 正确动作：至少 5 帧 + 改 1 字节负例 + 覆盖范围对照（header+payload / payload / header 三种都算一遍，
  只有一种全部通过）；用 `proto-repro.py` 的 `checks[].covers` 留证。

### 3.2 熵高就判"AES 加密"

- 错误动作：`entropy > 7.5` → 写"AES-CBC 加密，需找密钥"。
- 为什么错：gzip/zstd 压缩、base64、随机 nonce、TLS 记录层的熵都高；
  "看起来像 AES"不是证据，且会把人引向"爆破密钥"的死路。
- 正确动作：先看块长（8/16 倍数）、IV/nonce 是否逐帧变化、有无明文头；
  再拿两条已知明文做 XOR 判流/分组；最后在客户端 `SSL_write`/序列化前后取明文。没有明文对就写"未解"。

### 3.3 把压缩层当协议层

- 错误动作：把 gzip 头 `1f 8b` 后紧跟的 deflate 数据当"自定义帧头"分析。
- 为什么错：压缩是独立一层，解压前后长度/边界完全不同；在压缩流上分帧永远对不齐。
- 正确动作：先探魔数（`1f8b`/`28b52ffd`/`78 9c`）与 `Content-Encoding`，
  解压后再分帧；把"压缩算法 + 解压后格式"写成分层结构。

## 4. 状态机与重放的错误做法

### 4.1 只重放原帧，不构造新帧

- 错误动作：`socket.send(original_bytes)` 成功收到响应，就宣布"协议复刻完成"。
- 为什么错：原样重放只证明链路与会话有效；可能服务端只是按 cache/幂等返回。
  判据要求"不依赖抓包原帧，能生成服务端接受的新业务请求"。
- 正确动作：单变量构造（改业务 id/温度值），预测响应并验证 3 次；用 `proto-repro.py --rebuild`。

### 4.2 一次改多个字段

- 错误动作：同时改 `seq`、`type`、payload，失败后不知道是谁的锅。
- 为什么错：协议字段间有耦合（seq 递增、type 决定 payload schema、长度/校验跟着变），
  多变量同时改会把可解释性清零。
- 正确动作：基线 → 只改 payload → 只改 seq → 只改 type；每次保留原始字节与响应哈希；
  长度/校验由构造器自动重算，不手工改。

### 4.3 把"没观测到"当成"协议拒绝"

- 错误动作：样本里没有 error 帧，就在状态图里写"服务端不会返回错误"。
- 为什么错：未观测 ≠ 不存在；状态机的负例往往需要主动构造非法帧才能看到。
- 正确动作：主动发错 magic/错 CRC/跳步消息，记录拒绝方式；画图时把没样本的边标 `INFERRED`。

### 4.4 忽略心跳/重连/超时

- 错误动作：只分析业务消息，把周期性 ping 当噪声过滤掉。
- 为什么错：心跳间隔、超时阈值、重连退避都是协议的一部分；重放时缺心跳会被服务端踢掉，
  于是误判"协议不可复刻"。
- 正确动作：统计心跳周期与抖动，记录超时后的服务端行为；长会话重放脚本要带心跳线程。

## 5. 工具与证据卫生

### 5.1 用 tshark 的解析结果当"事实"

- 错误动作：`tshark -e modbus.func_code` 有值，就写"功能码=3"。
- 为什么错：dissector 是基于公开规范的启发式；私有协议常被误判成 `data`，
  或按错误端口套用了解析器。
- 正确动作：dissector 结论只作线索；结论必须回到原始字节 + 自己的字段表；
  端口不是协议判据（同一协议常跑在非常规端口）。

### 5.2 抓包/重放污染基线

- 错误动作：一边用 mitmproxy 抓，一边用同一份 pcap 当"原始基线"。
- 为什么错：代理会改 header 顺序、加 `Via`、重排 chunked；用被改写过的流量做基线，
  后面所有"差异"都不可信。
- 正确动作：基线抓包与重放流量分开命名；记录代理是否改写；关键结论用直连抓包复核。

### 5.3 报告里出现真实 token / 账号 / 内网地址

- 错误动作：把 `Authorization: Bearer eyJ...` 原样贴进报告。
- 为什么错：证据卫生问题；token 可能仍有效，泄露即事故。
- 正确动作：脱敏为 `Bearer <redacted:sha256:ab12…>`；只保留长度、前缀、声明字段；
  内网 IP 按需替换为 `10.x.x.x`。

## 6. 失误 13–20（与上面同一格式）

### 6.1 把"构造成功一条"当"能构造"

- 错误动作：改出一个服务端能收的 `temp=22.0`，就写"已具备构造能力"。
- 为什么错：一条成功只证明该值在服务端枚举内；字段的类型、范围、必填性、单位都没测过。
- 正确动作：对同一字段做**边界矩阵**：最小值/最大值/越界/空/非数字/多字节；记录哪些被接受，
  哪些被拒、拒绝方式是否一致。判据：「接受集」与「拒绝集」都能预测。

### 6.2 把 base64 / 压缩当成加密

- 错误动作：看到载荷熵 6.0、字符只含 `A-Za-z0-9+/=`，就写"私有加密"。
- 为什么错：base64 是编码，解完就是明文；把编码当加密会让人去找根本不存在的密钥。
- 正确动作：先试 `base64 -d`/`bytes.fromhex`/`zlib.decompress` 三种“零成本解码”；
  三种都失败且块长 16 倍数，再进加密假设（见 `07-crypto-and-checksum.md` §2）。

### 6.3 忽略端序与位序

- 错误动作：看到 `01 00` 就写"type=1"，换一条 `00 01` 的帧就解释不通。
- 为什么错：头部不同字段可能不同端序；`flags` 的 bit0 可能是 LSB 也可能是文档里的“第 1 位”。
- 正确动作：对每个多字节字段分别用大/小端拟合，看哪种能让**全部**帧成立；`flags` 写成
  `bit0..bit7` 展开表，并用两条 flag 不同的帧验证位含义。

### 6.4 把序号/时间戳当 nonce

- 错误动作：看到每帧有递增的 4 字节，就认定"有防重放"。
- 为什么错：递增字段可能只是单调 id，服务端可能只检查"大于上次"而不检查唯一性；
  真正的一次性 nonce 往往是随机 8/16 字节。
- 正确动作：做三个实验——重发旧值、重发当前值、超前发大值；三种结果分别记录。
  只有当旧值被拒且与签名/时间窗绑定，才写"防重放"。

### 6.5 用同一条连接做所有重放实验

- 错误动作：在已经登录的 socket 上反复重放，前几次成功就写"可重放"。
- 为什么错：连接内可能已有服务端推送/心跳/状态推进，基线被污染；而且真实客户端是新建连接。
- 正确动作：每次实验都**新建连接**，从握手起跑；把"连接内重放"单独列为另一类实验。

### 6.6 只看请求不看响应里的能力协商

- 错误动作：只解析客户端发什么，假设服务端总是接受同一套字段。
- 为什么错：hello/accept 阶段会协商版本、压缩、扩展、最大帧长；后续字段集由协商结果决定。
- 正确动作：把协商响应里的 `version/caps/extensions/max_frame` 抄进字段表，并做一次
  "降级协商"实验（改客户端 caps），看服务端回退到哪套字段。

### 6.7 把 Wireshark "Follow TCP Stream" 的输出当字节流

- 错误动作：直接复制 follow 窗口里的文本当输入喂解析器。
- 为什么错：follow 输出会按可打印性做转义、把两个方向拼在一起、丢掉时间与帧边界。
- 正确动作：`--extract` 或 `tcp.payload` 可提供包级载荷，但均不能直接拼作可靠流；按连接、方向、序号重组并记录重叠和缺口，再核对原始证据，长度一致不足以证明重组正确。

### 6.8 用字符串搜索定字段语义

- 错误动作：payload 里出现 `temp` 就把那段字节标成"温度字段"。
- 为什么错：JSON 的 key 与服务端业务字段不一定同名；同一个 key 可能在多个业务里含义不同。
- 正确动作：用**共变关系**定语义：同一字段在多条业务中随某业务值同步变化；
  并用改值实验验证"改了它，服务端行为真的跟着变"。

### 6.9 把"错"变成可机检的代理信号

| 失误 | 代理信号 | 机检方式 |
|---|---|---|
| 样本不足就下结论 | 应用帧不足 3 条但 claims 里有 `confirmed` | 核实后的应用帧表 + 档位联查；包级 `frames.jsonl` 行数不能替代 |
| 确认无证据 | `level=confirmed` 且 `evidence` 为空 | claims.json 遍历 |
| 把可变项当固定项 | `var_fields` 为空，但响应 sha256 每次都不同 | 3 次响应哈希 |
| 按包切消息 | `frames.jsonl` 里有 `payload_len` 等于 `tcp.len` 的整段 | 与 `pcap-summary` 对照 |
| 字段语义靠猜 | 字段表里 `source` 全部是 `guess` | schema 里 `source` 计数 |

下例的 `application-frames.jsonl` 须由已核实的应用帧解析另行生成；本域 `frames.jsonl` 是包级记录。

```bash
python - <<'PY'
import json, pathlib
card = json.loads(pathlib.Path("artifacts/claims.json").read_text(encoding="utf-8"))
rows = [json.loads(l) for l in pathlib.Path("artifacts/application-frames.jsonl").read_text(encoding="utf-8").splitlines() if l.strip()]
warn = []
if len(rows) < 3:
    warn.append("P1 样本<3帧但有结论")
for c in card.get("claims", []):
    if c.get("level") == "confirmed" and not c.get("evidence"):
        warn.append("P2 确认无证据:" + str(c.get("id")))
if not card.get("var_fields"):
    warn.append("P4 可变项未列")
print("warn", warn)
print("pitfall_proxy_ok", not warn)
PY
```

通过长什么样：

```text
warn []
pitfall_proxy_ok True
```

出现 `P1` 就去补样本；`P2` 就去补命令与帧号；`P4` 就跑 3 次同请求把差异列出来。
代理信号不能证明模型对了，但能便宜地拦住"最贵的错"。

### 6.10 复盘三问（每次交付前 3 分钟）

1. 我这条结论，如果错了，**哪个实验能推翻它**？答不出 → 它不是判据，是猜测。
2. 我引用的每个数字，**来自哪个帧/哪次运行**？答不出 → 删掉这个数字。
3. 我把"没观测到"写成了"不存在"吗？→ 改标 `INFERRED`。

## 7. 为什么模型爱犯这些错（三类根因）

| 根因 | 典型表现 | 防护动作 |
|---|---|---|
| 样本压力（只有 1–2 帧） | 单帧定长度、单次当稳定 | 强制采样量下限（`01-criteria.md` §1.1） |
| 工具幻觉（tshark/dissector 说啥信啥） | 字段语义、协议族全照抄 | 结论必须回原始字节 + 自写表 |
| 交付压力（要尽快给结论） | 措辞越档（"已确认"） | 措辞闸门（`01-criteria.md` §1.2） |

三类根因对应三个卡点：**样本不够就不写、工具结论只当线索、措辞跟证据同级**。

## 8. 自检清单（提交前逐条打勾）

- [ ] 分会话按 `tcp.stream`，没有按五元组合并。
- [ ] 分帧在**重组后的字节流**上做，`consumed + trailing == len`。
- [ ] 长度/校验各有 3 帧以上样本 + 至少 1 个负例。
- [ ] 新构造的帧能被同一张字段表解析回来（`rebuild.verify.crc_ok=true`）。
- [ ] 状态图里没有样本的边都标了 `INFERRED`。
- [ ] 结论里的每个"确认"都能指回帧号/文件/命令。
- [ ] 报告已脱敏；没有本机绝对路径。
- [ ] 失败/未解部分写进了 `02-failure-criteria.md` 对应的分支。

## 9. 失败判据（本页的错犯了会怎样）

- 出现"按包切消息/五元组会话/单帧定长度/只重放不构造"任一条 → 结论不可信，回到对应小节重做。
- 状态图里出现实线但没有样本 → 视为编造，撤回该边并标 `INFERRED`。
- 报告里有未脱敏 token 或本机绝对路径 → 视为证据事故，先修报告再交付。

## 10. 边界

- 本页只列"错在哪、怎么改"，具体命令在 `05`–`08` 四篇；判据档位在 `01-criteria.md`。
- 这些失误在"样本少 + 时间紧"时最容易发生；样本 <3 帧时默认全部降档为疑似。
