# pm-plan —— 把模糊需求拆成可验收任务

> 来源：inspired by `oma-pm`（oh-my-agent）。**已适配本项目**：产物落本仓路径、验证用 `check.py`、
> 不再依赖它的 `../_shared/*` 资源（那些文件我们没有）。

## 何时用
- 用户说"接下来做什么 / 怎么优化 / 帮我规划 / 评审这个设计 / 优先级怎么排"
- 需求含糊、范围大、需要拆成能逐个验收的任务
- 要在多个改进项之间排序（尤其"该修哪个 bug / 该先做哪个功能"）

## 不做
- 不写实现代码（那是域技能的事）
- 不做代码评审（用 `check.py` + 证据）

## 步骤（五段）

1. **PREPARE**：把用户原话、目标、约束、目标用户、验收期望列清楚；缺的先问（问不是退缩）。
2. **REASON**：拆任务。每个任务必须有：`id`、一句话标题、**验收标准（可执行判据）**、依赖、优先级（P0/P1/P2）、风险。
3. **ACT**：沿用当前项目的目标、路线与验收记录；维护本工作台只更新 `docs/CURRENT-STATE.md`，不另造总方案/任务账，不使用不存在的 `case_state.py plan --add`。
4. **VERIFY**：逐条自检——
   - 验收标准是不是**能跑的命令**或**能看到的现象**？（"做得更好"不合格）
   - 有没有任务其实是"两个任务捆一起"？（拆开）
   - 依赖是不是最少？（能并行的不要串行）
5. **FINALIZE**：把"没做的/故意不做的"单列一节（**Know-but-not-done 清单**），并说明理由。

## 排序规则（优先级怎么定，不许拍脑袋）

| 优先级 | 判据 |
| :-- | :-- |
| **P0** | 会让结论**说谎**、会让用户**白忙**、会**伤机器**（A 类） |
| **P1** | 影响"能不能用"（入口不通、工具缺、闸门挡死正常路径） |
| **P2** | 影响"好不好用"（体验、文档、命名） |
| **不做** | 只有某个样本才成立 / 需要大内容工程且不影响使用（记入 Know-but-not-done） |

## 常见坑（来自 oma-pm，已本地化）

- **太碎**：「实现登录」是一个任务，不是五个
- **太虚**：「优化一下」→ 改成「把 X 的 Y 指标从 A 改到 B，判据是命令 Z 输出 W」
- **捆一起**：把"改设计 + 改实现 + 补测试"合成一条 → 拆成三条
- **质量靠后**：测试不是最后一步，每条任务自带验证方式
- **遗漏当前风险**：规划只更新 `docs/CURRENT-STATE.md` 中对应的未知或剩余问题，不另造产品风险表，不从旧方案推导新需求。

## 本项目的固定验证方式

```bash
python Tool/scripts/check.py --strict  # 工作台完整验收，保留实际退出码/WARN
# 客户任务使用自身结果判据；本仓自检不能证明任意客户项目成功
```
