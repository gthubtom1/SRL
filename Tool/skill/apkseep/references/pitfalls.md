## 本页怎么用：这是一份**可检索的失败目录**，不是一份阅读材料

P1–P42 按编号分布在 5 个子篇里。编号是**身份**：`SKILL.md` 的症状索引、子篇之间的交叉引用、
以及你自己记的实验日志都只写编号。所以查它的正确姿势是三步，而不是从头读。

| 步 | 你手上有什么 | 做法 |
|---|---|---|
| 1 | 一个**现象**（"装完什么都没变"） | 按下表先定位到"阶段"，再在对应子篇里找编号 |
| 2 | 一个**阶段**（打包 / 环境 / 补丁 / native / 验证） | 直接打开该阶段的子篇，扫 `## P<n>.` 标题 |
| 3 | 一个**编号**（别人日志里写了 P21） | `grep -n '^## P21\.' pitfalls-*.md` |

| 你处在哪一步 | 子篇 | 编号 | 大多数条目在讲的一件事 |
|---|---|---|---|
| 刚打完包、装不上 / 装上了不启动 | 1 | P1–P8 | 打包与 dex 的**结构性**损坏（签名、顺序、往返、共享方法） |
| 结果可疑，怀疑环境或自己的观察 | 2 | P9–P22 | 归因错误：把环境的、静态的、服务器的当成"我的补丁" |
| 补丁生效了但行为不对 | 3 | P23–P30 | 改了**错的那份数据/那份产物** |
| native 死、ELF 读错、安装码怪 | 4 | P31–P38 | 终止路径、解析层、校验和、`resources.arsc` |
| 一切都对，但"没验证" | 5 | P39–P42 | 安装/UI 验证与解码器失步 |

**一条硬规矩**：命中编号之后，**照它的"正确动作"做，不要照它的"现象"做**。这份目录里每条的
价值全在最后那一段；现象只是让你认出自己正站在哪个坑里。

## 命令块 A：把编号当地址来查

```bash
# 1) 列出全部编号（连续性与总数一眼可见）
grep -h -o '^## P[0-9]\+\.' pitfalls-*.md | sort -t P -k2 -n | tr '\n' ' '

# 2) 按编号查一条（别人日志里只给了编号时）
grep -n '^## P21\.' pitfalls-*.md

# 3) 按现象关键词查（英文条目用英文关键词，别用中文猜）
grep -rn -i 'checksum\|resources.arsc\|INSTALL_FAILED\|META-INF\|move-result' pitfalls-*.md | head

# 4) 查某一条引用了哪些别的条目（追一条链时用）
grep -n 'P[0-9]\+' pitfalls-3-patching-and-artifacts.md | grep -v '^[0-9]*:## P'
```

期望输出（形态）：

```
P1. P2. P3. P4. P5. P6. P7. P8. ... P42.        <- 1) 42 个编号，无空洞
pitfalls-2-environment-and-evidence.md:257:## P21. Changing two things at once, ...
pitfalls-1-packaging-and-dex.md:15:## P1. Stripping the whole `META-INF/` ...
```

**通过长什么样**：编号列表里 1–42 **连续**、无重复；按编号查只命中一处；按现象查命中数不为 0。

## 命令块 B：新增一条坑之前的重复检查

写入前必须先证明"这条还没有被写过"，否则目录会开始出现同一件事的两种说法（这份域里已经有过一次，
`SKILL.md` §Coverage 记录了这个教训）。

```bash
# 【占位符】把 <...> 换成你的真实路径/端口/参数后再执行
# 用"症状"和"机制"两个关键词各查一次；两个都空，才是新条目
grep -rn -i '<症状关键词>' pitfalls-*.md
grep -rn -i '<机制关键词>' pitfalls-*.md
grep -rn -i '<症状关键词>' ../../SKILL.md | head
```

通过的样子：三条都**空**（或只命中一句"见 P<n>"的指路），且你能说出新条目应该落在哪个子篇
（按阶段，不按时间）。

## 一条坑条目的最小格式（照这个写，别自创）

```
## P<n>. <一句话症状——写成你会搜的那个词>

**Symptom**       你观察到什么（含具体字符串/退出码/日志行）
**Cause**         机制层面的原因（不是"我操作失误"）
**Correct action** 下一步做什么，可执行
**Cost**          这条坑一次要花多久（用作优先级）
**See also**      相关条目与外部文件
```

四个字段缺任何一个，条目就退化成一句抱怨。**`Cost` 尤其不要省**：它是这个目录唯一的排序依据，
也是判断"要不要为它加一条自动化检查"的依据。

## 编号纪律（为什么不能重排、不能复用）

- **编号永不复用。** 即使某条被证伪（写错、被后来的测量推翻），也保留编号并标注 `refuted`，
  因为外部引用（日志、提交信息、别人的笔记）只认编号。
- **子篇归属按阶段，不按发现时间。** 加条目时如果拿不准，放进"验证"那一篇永远不算错——它至少
  不会让人在错误的阶段读到它。
- **一条 = 一个机制。** "补丁没生效"和"补丁生效在错的产物上"是两条（P24/P29），合并会让检索失效。
- **交叉引用用编号，不复制内容。** 复制会漂移；编号不会。

## 症状索引 ↔ P 编号：两条查法要能对上

`SKILL.md` 的症状索引按"你看到什么"指向**文件**；本目录按"哪一步坏了"指向**编号**。两条查法
应该能互相到达——对不上的时候，通常是症状索引里那一行描述得还不够具体（那是一个可修的问题）。

| 你在 `SKILL.md` 看到的症状（缩写） | 落到哪个编号 | 为什么是它 |
|---|---|---|
| 安装 `[-124]` / `resources.arsc` 对齐 | P38 | 解包层属性，不是签名问题 |
| 装上了但 `am start` 没反应 / 截到别的应用 | P40 | 前台不是你（P18 是"根本没装上"，不同一件事） |
| "没变化"，且版本号也没动 | P18 → P24 | 先证装上了，再证跑的是新的 |
| `Bad checksum` + 普通类 `ClassNotFoundException` | P37 | 头部两字段顺序错，或改完没重算 |
| 裸数字安装码、无 `INSTALL_FAILED_*` | P39 | 设备侧拦截，不是你的包 |
| 补丁"没生效"，日志干净 | P29 → P25 | 静态数据不是 UI 消费的数据；再往后是"搜错了" |
| 两个观察分不清哪个假设 | P30 | 证据不足却当成结论 |
| 一切正常但功能静默缺失 | P19 → P17 | 内部信号替代了用户可见结果 |

**用法**：如果你从 `SKILL.md` 的症状行进来，只找到文件、没找到编号，就在对应子篇里用**同一个
关键词**再搜一次（`grep -rn -i '<关键词>' pitfalls-*.md`）。搜不到时，说明这个症状还没有编号——
那正是该写一条新条目的时候（按 §最小格式）。

## 按代价排序：先修哪几条

下面这个排序不是"重要性"，而是**一次踩中要花多久**。它决定你该在哪几条上先做自动化检查。

| 代价 | 编号 | 一句话 |
|---|---|---|
| 数小时 | P21 | 两个变量一起改，之后所有归因都作废 |
| 数小时 | P27 | 签名派生密钥：每个签名请求都失败，而应用"看起来正常" |
| 数小时 | P24 | 改对了但执行的是旧产物，后面每条观察都在描述上一版 |
| 1–2 小时 | P1 | 整个 `META-INF/` 被删，启动即死 |
| 1–2 小时 | P3 | 全树 smali 往返，R8 优化过的 dex 只在运行时坏 |
| 1–2 小时 | P36 | 用节头解析被去节的库，得出"没有符号" |
| 1 小时 | P31 | 用"不返回"代替"返回"，进程带锁卡死 |
| 30 分钟 | P12 | shell 吃掉设备侧命令，报错看起来像目标的问题 |
| 30 分钟 | P28 | `logcat -c` 没清 events buffer，上一版的崩溃很像这一版的 |
| 30 分钟 | P2 | 字符串改长了，`string_ids` 顺序被破坏，整包拒绝 |

**读法**：前四行属于"一旦发生，当天基本报废"。它们的共同点是**污染了后续证据**，而不是直接报错。
所以它们也最值得被机检（见下一节）。

## 哪些坑可以变成一条检查

这份目录里已经有若干条被自动化吸收了。判断标准：**症状能否被一条命令的输出判出来**。
能被判出来的，就不该继续靠人记住。

| 编号 | 可机检的判据 | 已经/应该由谁检 |
|---|---|---|
| P1 | 输出 APK 的 `META-INF/` 里除了签名文件是否还有 `services/` | `apk_diff.py` + repack 前后对比 |
| P2 | `string_ids` 是否仍有序、dex 是否仍通过 `dexutil.verify_dex_header` | `dex_strpatch.py` 的排序守卫 |
| P18 | 设备上包路径的哈希是否等于本地构建 | `install_test.py` / `coldstart.py` |
| P24 | 前台 Activity 的包名是否等于目标包 | `coldstart.py` 的"前台不是你"警告 |
| P25/P33 | 命令在**已知有**的输入上是否命中 | 阳性对照（本目录把它写成纪律，而不是脚本） |
| P37 | 头部 `signature`/`checksum` 是否按序重算 | `dexutil.fix_dex_header` |
| P38 | `resources.arsc` 是否 STORED 且 4 字节对齐 | `repack.py` 安装前检查 |

**反过来也成立**：一条坑如果连着两次以上被同一个人踩到，而它又**判不出来**，那么它是候选的
"文档级修复"——把它写进 `SKILL.md` 的立即行动区，而不是留在目录深处。

## 三个反模式：把目录当借口

- **"这条我读过"** 不等于"这次在此情形下失效"。条目是按机制归类的，读的时候要对着**自己当前的现象**再确认
  一次条件，而不是凭"我记得这条"跳过。
- **"目录里没有，所以不是已知问题"** —— 目录只记录被付过代价的坑。没有命中时，正确动作是按
  `SKILL.md` §Stop conditions 停下来分类，而不是继续试。
- **"我先试第三次，说不定这次不一样"** —— 两次同形失败之后，第三次的期望收益是负的（P21 的教训）。

## 一次检索示例（照着走一遍）

现象：重打包后应用能起、UI 正常、日志干净，但"我的"页面里的某个入口点了没反应。

```bash
# 1) 现象关键词（英文条目用英文）
grep -rn -i 'no effect\|never loads\|silent' pitfalls-*.md | head
# 2) 阶段定位：这属于"补丁生效但行为不对" -> 子篇 3
grep -n '^## P' pitfalls-3-patching-and-artifacts.md
# 3) 命中 P29（静态数据不是 UI 消费的数据）与 P25（搜索假阴性）
grep -n '^## P29\.\|^## P25\.' pitfalls-3-patching-and-artifacts.md
```

走完之后你手上应该有两个东西：**一个编号**（解释为什么补丁没生效）和**一个动作**（去证实或证伪它）。
只拿到编号没拿到动作，说明你停在了"读"这一步。

## 不该写进本目录的东西

目录的价值来自**同质性**：每条都是"一个机制、一个现象、一个动作"。下面这些放进来会破坏它：

| 内容 | 为什么不合适 | 放哪 |
|---|---|---|
| "加固壳很难" / "VMP 基本无解" | 是判断，不是坑；无法验收 | `vmp-differential-analysis.md` §decision summary |
| 某个样本的具体路径、包名、版本 | 会过期，且是目标身份（发布前还要脱敏） | 证据文件（`desensitization-and-leak-scans.md`） |
| 一整段操作教程 | 教程会漂移；目录只存"踩过的点" | 对应技法页 |
| "我忘了备份" | 是流程问题，不是机制问题 | `long-task-discipline.md` §live record |
| 一条尚未复现的猜测 | 会污染目录的可信度 | 先写成 `unverified` 的观察，复现后再编号 |
| 只在某一台机器上出现、且无法归因的现象 | 归因不清的条目会被误用到别的机器 | 先按 P9（环境）查一遍 |

**判据**：一条内容如果不能用"现象 / 原因 / 动作 / 代价"四段写清楚，它就不是一条坑。

## 把一条坑写成可复现的最小例子

最好的条目能让人**在十分钟内重现**它。写法是固定的四件套：

```
环境    <设备/系统/工具版本>            <- 换环境后是否还成立，靠这一行判断
输入    <一份最小构建，或一个最小 dex>   <- 不要用"我的项目"
步骤    1) ...  2) ...  3) ...         <- 每步一条命令，可复制
观测    期望看到 <A>，实际看到 <B>      <- A/B 都要具体到字符串
```

例子（P38 的写法，示意）：

```
环境    Android 11 / build-tools 34.0.0 / apksigner 0.9
输入    任意含 resources.arsc 的 APK，用 DEFLATE 压缩该条目后重打包
步骤    1) zipalign -c -v 4 out.apk   2) adb install out.apk
观测    期望 Install succeeded；实际 INSTALL_FAILED_INVALID_APK [-124]，提示 arsc 未对齐
```

**为什么值得多花五分钟写这四行**：它是"这条坑能不能被自动化"的唯一输入。四行都具体，就能写检查；
写不出 `观测` 里的 A/B，说明这条坑还没被真正理解，此时编号会带来虚假的确定感。

## 目录的维护节律（不然它会变成考古现场）

| 触发 | 动作 | 判据 |
|---|---|---|
| 一次失败花了 > 30 分钟 | 按 §最小格式 加一条（或给已有条目补 `Cost`） | 能写出"现象/原因/动作/代价"四段 |
| 已有条目被新的测量推翻 | 保留编号，标 `refuted`，并写"什么测量推翻了它" | 原编号仍可被搜到 |
| 两条条目讲同一机制 | 合并到较早的编号，另一条改为一行指路 | 合并后不出现第二份"正确动作" |
| 某条已被自动化 | 在条目末尾加一行 `mechanized by <script/check>` | 该检查真的会失败一次（否则不算） |
| 某条在三次不同的任务里都没被用到 | 不删除；它可能是"很少发生但代价高"的那一类 | 只有在被证伪时才标 `refuted` |

节律的意义：这份目录**只增不改语义**。删除会让人失去"为什么当初这么写"的记录，而这类记录恰恰是
防止同一条坑第三次被踩的东西。

## 一句话总结这条目录的用法

把编号当**地址**（可检索、可引用、永不复用），把"正确动作"当**内容**（照做，别读现象），
把 `Cost` 当**排序**（它决定先修哪条、以及哪条该被自动化）。三件事都做到，这份目录就是
一份能省下几个小时的工具；只做第一件，它只是一份读物。
