## 本页怎么用：工具链问题，先问"能力闭合"，再问"装什么"

这个域里最贵的工具错误不是"缺一个工具"，而是**用一个弱工具回答了一个它答不了的问题，然后相信了答案**。
`grep` 一个手导出的 smali 树、手工走一遍 ELF、用文本编辑器找偏移，全都会给出**看起来正常**的输出。
所以工具链这一步的产物不是"我装了 X"，而是三条能说清楚的判断：

| 判断 | 输出长什么样 | 归哪篇 |
|---|---|---|
| 这台机器现在能做什么、不能做什么 | 能力清单 + 每项缺失原子 + 装它要多久 | 子篇 1（Tier 0–2 与缺口） |
| 缺的那一层该装什么、从哪装、装完怎么验 | 一条安装命令 + 一条验证命令 | 子篇 1 §closing a capability gap |
| 装了却"不在 PATH 上"、签名器选错、离线怎么办 | 具体陷阱与替代路径 | 子篇 2（Tier 3–4 与信任） |

**顺序**：`doctor.py` 给结论 → 子篇 1 给"怎么补" → 子篇 2 给"补了还是不对时看哪里"。反过来（先读
工具清单再跑 doctor）会让你花时间读一堆本机根本用不上的条目。

## 命令块 A：一次拿到"能/不能"的结论

```bash
# 【占位符】把 <...> 换成你的真实路径/端口/参数后再执行
# 1) 能力闭合：BLOCKED 的那一项，缺的是什么，下一步做什么
python scripts/doctor.py --json > doctor.json
python scripts/doctor.py --capabilities          # 人读版：每项缺哪些原子

# 2) 只看某个能力（按 id），把"缺什么"缩到一行
python scripts/capabilities.py --list
python scripts/capabilities.py <capability-id> --verbose

# 3) 交付脚本本身能不能跑（脚本层的假阴性比工具缺更常见）
python scripts/doctor.py --scripts

# 4) 有设备时，把设备侧结果一并记进同一份 JSON
python scripts/doctor.py --device <serial> --json > doctor-device.json
```

期望输出（形态）：

```
capability                 state    missing                     next
re-sign-apk                BLOCKED  apksigner                   install build-tools;apksigner
dalvik-disasm              ok       -                           -
native-decompile-arm64     BLOCKED  ghidra                      unzip release; set JAVA_HOME
frida-attach               ok       -                           -
unpack-dex-dump            ok       -                           -
```

**读法（判据）**：`BLOCKED` 行必须同时给出 `missing` 与 `next`。只给 `BLOCKED` 不给缺项的，
是这份报告还没跑完（用 `--capabilities` 补），而不是"没有这个能力"。

## 通过长什么样

| 检查 | 命令 | 通过 | 不通过意味着什么 |
|---|---|---|---|
| 能力清单可读 | `doctor.py --capabilities` | 每项都有 `ok` / `BLOCKED` + 缺项 | 只有一堆工具名 ⇒ 你在读目录，不是读能力 |
| 关键能力可达 | 同上 | 本任务要用的那 2–3 层是 `ok` | 先补这一层，再谈目标；缺层时所有结论都带条件 |
| 脚本可用 | `doctor.py --scripts` | 每个脚本 `runnable`，或有明确缺依赖 | 脚本"报错"会被误读成"目标没有这个特征"（P26） |
| 不在 PATH 也能找到 | 子篇 2 §"not on PATH" 的命令 | 能找到并打印版本 | "缺失"结论直接作废，通常是 PATH/驱动名/大小写问题 |
| 版本可复述 | 记录里的版本行 | 每件工具都有版本号 | 换版本会换输出；没有版本的记录不可复现 |

## 三条约束

1. **不从"工具存在"推断"能力存在"。** JVM 在，不等于能签名（还缺 `zipalign`/`apksigner`）；
   `jadx` 在，不等于能反编译到可读（R8 之后的名字本来就没语义）。`doctor.py` 之所以允许报
   `BLOCKED`，就是为了让这句话有地方落。
2. **不手写已有脚本。** 解析、哈希、对齐、热插桩探测都已经在 `scripts/` 里；自己再写一遍,最常见的
   后果是**猜偏移而不是算偏移**（`dex_find_insn.py` 的整段存在理由）。
3. **工具失败不是关于目标的发现。** 任何"这个库没有符号 / 这个 dex 没有引用"的结论，先要在**已知有**
   的输入上跑一次同一条命令（阳性对照），否则它只是"我的命令没读到"（P25、P33）。

## 选型：装工具 vs 换工具，成本怎么算

| 情形 | 便宜的选 | 为什么另一条更贵 |
|---|---|---|
| 要在 arm64 上读懂一个函数 | 装一个 arm64 反编译器（一次性成本，之后每次都用） | 手工读汇编：每次都要重来，且容易读错边界 |
| 要回答"谁引用了这个字符串" | 索引式查询（`droidasc`/`ddc findrefs`） | 导出全树再 `grep`：先付一次导出成本，之后每个问题再付一次 |
| 要回答"这个方法在运行时的值" | 一次 hook 或一次 RPC 调用 | 反复读静态代码推测：结论永远是 `inferred` |
| 只需要一个常量 | `dex_strings.py --find` | 起一整套动态环境：引入的变量比答案多 |

**这张表不是"永远选左边"**：判断标准是"这个问题会被问几次"。问一次就够的，用最轻的；问十次的，
先花十分钟把工具装好。

`SKILL.md` 只保留五条**义务**（用索引器定位、缺工具就装、先说缺口、先用已交付脚本、按层选工具）
和"先跑 `doctor.py`"这一句；本篇与两个子篇承载"具体是哪件工具、怎么装、装完怎么验、装完还是不对

## 记录模板（工具链快照）

```
host:        <os/arch>  python <v>  java <v or none>
present:     <tool=version> 列表（只记本任务用到的）
blocked:     <capability>  missing=<atom>  next=<command>
installed:   <tool> <version>  from <source>  verified_by=<command + 输出行>
off_path:    <tool> found at <path>  (not on PATH)
not_used:    <tool> 因为 <reason>（写下来，防止下次重新评估）
```

最后一行最容易被省略，也最省时间：它把"我考虑过但没用"变成一条记录，下次不用再想一遍。

## 任务类型 → 最小工具集（少装一件就少一个变量）

| 任务 | 必须有的 | 有更好 | 明确不需要 |
|---|---|---|---|
| 判有没有壳、壳是哪家 | dex 读取（`dexutil.py`）+ 字符串表（`dex_strings.py`） | 一个能看 `Application` 的反编译器 | 动态注入、内核模块 |
| 改几字节并让 `verify` 通过 | `dex_find_insn.py` + `dex_patch_bytes.py` + `dexutil.py` | `dex_classdiff.py`（证外科性） | Frida、Ghidra |
| 重打包签名安装 | `repack.py` + `apksigner` + `zipalign` + 真机 | `apk_diff.py`（证改动范围） | 反编译器 |
| 定位一个业务类 | 索引器（字符串/类型/方法 → 引用点） | `jadx` 只用于**读**已定位的类 | 全树导出 |
| native 死亡归因 | `native_crash.py` + tombstone 路径 | arm64 反汇编器 | `repack.py`（先别改） |
| Dart AOT | 快照前端口（aotopsy/blutter）+ `dart_pprefs.py`/`dart_disasm.py` | capstone 交叉验证 | Android 侧动态工具 |

**用法**：先把"必须有的"这一列变成 `doctor.py` 的输出对照，缺哪件就补哪件；"有更好"一列在结论需要
跨验时才装。**不要在第一步就把"明确不需要"的装上** —— 每多一个工具，你的环境变量就多一个。

## 假阴性的三个来源（本域最贵的工具问题）

**① 命令读不到输入。** 典型：`grep` 一个 `.dex` 二进制（永不命中，因为字符串不是明文行）、
对一个压缩过的 APK 直接搜字符串（`resources.arsc` 与 dex 都在 zip 里，明文可能被 deflate）。
判据：先在**已知有**的样本上跑同一条命令。动作：解压/解包后再搜，或用 `dex_strings.py`。

**② 解码器提前停。** 典型：ELF 用 section header 走一个被去掉节头的库（P36）、dex 走到损坏的
`code_item` 就中断（P33）。判据：输出里有没有"提前结束"的痕迹（行数明显少于预期、`walk stopped early`）。
动作：换 PT_LOAD / 换解码路径，并把"提前停"当成程序缺陷而不是目标特征。

**③ 语言/编码不匹配。** 典型：在 UTF-16LE 的快照里搜 UTF-8（返回零，然后得出"字符串被加密"）。
判据：同一字符串用两种编码各搜一次。动作：两种都试，并记下是哪一种命中。

三条的共同点：**它们都产生"干净的空结果"**。所以本域的一条硬规矩是——
"没有" 这个结论必须由一次**阳性对照**支撑，否则它只是"我的工具没找到"。

## 装完之后的三步验证

装一件工具的正确收尾不是"命令能跑"，而是：

```bash
# 【占位符】把 <...> 换成你的真实路径/端口/参数后再执行
# 1) 版本 + 来源（写进记录）
<tool> --version

# 2) 在一份你已经有答案的输入上跑一次（阳性对照）
<tool> <known-good-input> | head -20

# 3) 在一份你应该拿不到答案的输入上跑一次（阴性对照）
<tool> <empty-or-mismatched-input> | head -5
```

通过长什么样：第一步有版本号；第二步的输出与你已知的答案一致；第三步给出**空结果或明确报错**，
而不是"看起来也正常"。第二步缺失，是"工具装错了但我不知道"；第三步缺失，是"工具对任何输入都给
一个看似合理的答案"——后者更危险，因为它的输出会被当成证据。

## 一次索引 vs 十次 grep 的算术

设一个"谁引用了这个字符串"的问题，在导出的 smali 树上 `grep` 需要 20 秒（含 IO 抖动），索引器
回答一次是 0.3 秒，建立索引一次 60 秒。则：

| 问题数 | 纯 grep | 建索引 + 查询 |
|---|---|---|
| 1 | 20 s | 60 s |
| 3 | 60 s | 61 s |
| 10 | 200 s | 63 s |
| 30 | 600 s | 69 s |

这张表的用途是**让"要不要装"变成一个可算的决定**：脱壳后的定位阶段通常有 10 个以上的"谁引用"问题，
所以索引器在第三次就已经回本。反过来，只有一个问题的一次性任务，`grep` 是对的。

## 什么时候不该继续扩工具链

- **答案已经够用。** 你要的是"这一步能不能过"，而不是一份该库的完整符号表。
- **补的是"更强的同类工具"。** 已经有一个能给出 `observed` 结果的工具时，换更强的只会换掉基线。
- **要补的层在最上面（内核/框架）。** 先确认下面的层真的到顶了；否则你会在最贵的一层上解决一个
  本来在下面就能解决的问题（`kernel-and-environment-hardening.md` 的"何时升级是错的"）。
- **工具会改变目标。** 任何"注入/改包才能用"的工具，都会让观察对象不再是原包；需要对照组才成立。

## 命令块 B：一份可粘贴的工具链快照

```bash
# 逐件问版本；缺的那件会打印 "MISSING"，而不是静默跳过
for t in jadx apktool apksigner zipalign keytool d8 baksmali smali frida adb python3; do
  v=$(command -v "$t" 2>/dev/null) || { echo "$t MISSING"; continue; }
  printf '%-10s %s
' "$t" "$v"
done

# 设备侧（root）也要一份：ROM 自带工具与主机不是一回事
adb shell 'for t in toybox magisk su; do printf "%-8s %s
" "$t" "$(command -v $t 2>/dev/null || echo MISSING)"; done'
```

通过的样子：每行都是"名字 + 路径"，没有一行是 `MISSING`（除了你真的不需要的那几件 —— 那时它应该
出现在记录的 `not_used` 行里，并带原因）。

## 三个"工具在，但结果错"的具体例子

| 现象 | 真正的原因 | 判据 |
|---|---|---|
| `apksigner verify` 说通过，装上去却被拒 | 只验了你选的 scheme；设备按自己的 `minSdk` / API 级别挑方案（P13） | 加 `--print-certs` 与 `--min-sdk-version`，两者一起看 |
| `nm`/`readelf` 找不到 `Java_*`，于是结论"没有 JNI" | 动态注册 + `-fvisibility=hidden`，符号本来就不在表里 | 看 `JNI_OnLoad` 是否存在、dex 的 native 方法数与符号数是否 1:1 |
| 反编译器能开、也能导出 Java，但类名全是 `a.b.c` | R8 之后本来就没有语义名，不是工具坏了 | 用索引器按字符串/调用形状定位，别按名字找 |

三个例子的共同结构：**工具成功执行了，但它回答的不是你问的问题**。判据永远在"输入的属性"上
（方案、注册方式、混淆程度），不在工具是否报错。

## 版本漂移：同一命令，两版两种答案

这个域的工具输出**不是稳定接口**：反编译器的控制流重建、提取器支持的快照格式、签名器默认方案都在变。
因此"我上次跑出来是这样"不能作为证据，除非版本一致。

| 工具类 | 会随版本变的东西 | 记录方式 |
|---|---|---|
| 反编译器 | 生成的伪代码结构、内联决策、失败时的输出形态 | 版本 + 一次已知输入的输出片段 |
| 快照/字节码提取器 | 支持的格式标签（arm64 packed vs 32 位记录）、字符串表布局 | 版本 + 命中的格式（写进记录，见 `dart-aot.md`） |
| 签名器 | 默认启用的 scheme、对 `minSdk` 的推断 | `--print-certs` 输出 + `minSdk` |
| Frida | 桥接 API、`overload` 行为、设备端与客户端必须同版本 | 两侧版本字符串 |

**操作规则**：结论里出现"工具给出的结构"时，同时写下版本；换版本后若结论变了，**先假定版本差异**，
在旧版本上复跑一次再决定它是不是目标的差异。这一条是 `evidence-summary.md` 里"工具跑了 ≠ 工具对了"的
具体落地方式。

## 边界：本页不回答的问题

- **"这个工具的原理"** —— 本页只管"哪件、怎么调、怎么验"；原理去对应技法页（如 `dex-patching.md`）。
- **"从哪下载"** —— 子篇 1 有来源化清单；本页不重复链接，链接会烂而清单不会。
- **"某能力为什么 BLOCKED"** —— 以 `capabilities.py <id> --verbose` 的输出为准，不以猜测为准。
- **"该不该用商业工具"** —— 判断标准是"它能不能给出可交叉验证的输出"，不是授权与价格。
- **"某个脚本的参数"** —— 以 `--help` 为准（本页只写稳定用法）；`doctor.py --scripts` 会告诉你它在这台机器上能不能跑。
- **"装不上怎么办"** —— 先按子篇 1 的安装路径试一次；仍不行时，把"缺什么"写进记录，不要改成"这个目标做不了"。
- **"两篇子篇的边界"** —— Tier 0–2 与"要不要装"在子篇 1；Tier 3–4、签名、off-PATH、离线与记录在子篇 2。

> 本页与两个子篇的分工是**稳定性**：本页只写不随版本变的东西（顺序、判据、成本算术），
> 子篇写会变的东西（具体命令、安装路径、陷阱）。因此本页的命令都尽量短，且都能在
> `doctor.py` 的输出里找到对应项 —— 这样"文档与工具不一致"这件事本身是可以被检查的。
