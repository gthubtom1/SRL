# 模板 · final（交付与验收）

**这份模板用来干什么**：把「做完了」变成「能证明做完了」。上游闸只认两样东西：
**功能**是否全通，**验收**是否有可跑的判据。所以本模板先固定验收清单（每条一眼可判真伪），
再要求逐条贴实测输出；凡是没跑过的条目，一律标「未跑」，不许用「应该可以」代替。

## 占位符约定

- `{{case}}`：案例目录名
- `{{deliverable}}`：交付物路径（仓库相对）
- `{{cmd}}`：验收命令
- `{{rc}}`：退出码

| 编号 | 路径 | 类型 | 说明 |
| :-- | :-- | :-- | :-- |
| D-1 | `{{deliverable}}` | 成品 / 补丁 / 脚本 | {{value}} |
| D-2 | `{{deliverable}}` | 证据 / 日志 | {{value}} |

分档写清楚（原件与改件分开摆，别混在一个目录里）：

- 原件：`{{value}}`（只读留存，含哈希）
- 改件：`{{value}}`（改了什么、改在哪个位点）

## 2. 功能验收（全通才算交付）

| 编号 | 功能点 | 进入路径 | 判据 | 结果 |
| :-- | :-- | :-- | :-- | :-- |
| F-1 | 进主界面 | {{value}} | 窗口出现且无报错弹窗 | 未跑 |
| F-2 | 核心功能 | {{value}} | 输出/落盘结果与预期一致 | 未跑 |
| F-3 | 边界功能 | {{value}} | 报错信息与原来一致 | 未跑 |

功能面的诚实口径：

- 「能启动」不等于「功能可用」：至少跑通一条主链路
- 「页面在」不等于「数据对」：要看到真实输出
- 任一条为「未跑」，整体结论写 `partial`，不写 `done`

## 3. 验收清单（逐条打勾，勾不了就写原因）

- [ ] A1 原件哈希已记录，改件哈希与原件不同
- [ ] A2 验收命令能一条跑完：`{{cmd}}` → rc=`{{rc}}`
- [ ] A3 无环境变量 / 缺凭据时的行为仍与预期一致（拒绝路径可达）
- [ ] A4 合法输入时行为正确，输出行与预期逐字相同
- [ ] A5 非法输入时行为正确，退出码非 0 且提示语一致
- [ ] A6 三条路径（合法 / 非法 / 缺失）实测输出都已贴进回执
- [ ] A7 回归：原目标的其它功能未被连带破坏
- [ ] A8 残迹：残留的调试钩子 / 临时文件 / 日志已清
- [ ] A9 文档：README 与案例元数据口径一致（路径为仓库相对）
- [ ] A10 门禁：`Tool/scripts/preflight.py` 跑完全绿
