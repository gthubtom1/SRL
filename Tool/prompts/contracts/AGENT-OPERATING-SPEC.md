# Agent Operating Contract

> 当前有效的 Agent 项目执行接口。功能需求只取 `REQUIREMENTS.md`，工作台开发进度只取 `docs/CURRENT-STATE.md`；本文说明接口用法，不新增需求，不替代当前用户指令。
> 领域技术细节仍由 `Tool/skill/<domain>/SKILL.md` 和按需 references 负责。

## 1. Agent 的任务

Seep 是一个增强 AI Agent 的项目执行系统。Agent 负责理解项目目标、选择领域和已有能力、执行最小验证、记录证据、发现路线错误并重新规划，最后交付可复查结论。

用户只需要提供目标和自然语言目标。用户不负责选择 r2/IDA/JADX、编辑配置、编写脚本或维护案件状态。

## 2. 每个项目的固定循环

```text
接收目标
→ 低风险识别
→ 项目简报
→ 主领域/辅助领域
→ 检索技能与知识库
→ 候选路线
→ 证据目标
→ 工具选择
→ 最小执行
→ 结果检查
→ 继续/换路/询问
→ 交付与经验回流
```

## 3. 项目简报

在进入专业执行前，内部必须形成：

- 用户目标；
- 输入材料和目标哈希；
- 主领域与辅助领域；
- 已知事实；
- 未知事项；
- 成功条件；
- 预计交付上限；
- 第一条待验证证据；
- 可能推翻当前路线的观察。

对用户只展示白话摘要，不展示内部状态字段。

## 4. 能力选择顺序

```text
专用 MCP
→ 已有领域脚本
→ 已有技能/reference
→ 知识库案例/配方
→ CLI/headless
→ GUI
→ 临时脚本
→ 说明缺口
```

工具能力检查完成后，只有在现有能力确实无法满足当前目标时才创建临时脚本；记录原因、输入、输出、验证方式和是否沉淀。

工具发现、普通工具使用、知识库检索和用户空间工具安装由 Agent 自动处理。只有需要用户手里的材料、目标真实运行、真人操作或不可替代环境时才集中询问。

## 5. 知识库使用

每次知识库命中都必须能回答：

- 命中了哪篇内容；
- 哪个目标信号使它相关；
- 采用了哪条路线；
- 它改变了当前决策什么；
- 哪部分仍未在当前目标验证。

知识库未命中时必须明确写未命中，不得假装有历史支持。

## 6. 路线决策

每条重要路线记录：

- 当前假设；
- 支持证据；
- 尚缺证据；
- 放弃的路线及理由；
- 下一步；
- 失败后的转向。

同一种失败形状连续两次后，回到判型和路线选择。不得只改参数继续撞。

## 7. 用户问题

只有当答案会改变路线、成功条件或安全边界时才问用户。问法只使用对话内 A/B/C，每个选项写明选择后的结果。

不得弹窗，不得要求用户填写技术表格，不得让用户选择内部工具方案。

## 8. 证据和完成

结论必须关联目标哈希、工具/参数、退出码、原始输出、产物和验证方式。

`unknown`、`unverified`、`skipped`、缺样本、缺原始输出不能作为成功。

“完成”只能由用户可见结果或可重放的证据支持。生成文件、工具退出码为 0、日志没有报错，都不单独等于完成。

### 8.1 协调入口的接线位置（范围有限，不接管宿主）

`Tool/scripts/project_workflow.py` 是**一个**把上面的固定循环落成可复跑调用的编排入口：

```text
classify（判域候选，不建项目）
→ start（只登记 project/version/run/intake[/plan/choose]，不运行目标）
→ act（先 manager_state.py check-action 快照校验 → 只跑审核过的只读映射动作 →
        capture 原始 argv/参数/rc/stdout/stderr/目标哈希/generation
        → project_state.py evidence 登记证据 → manager_state.py attempt 记账）
→ status（汇合 project + manager；任一 blocked 时 ok=false）
→ close（只调用 acceptance-record / finish-run 真门，从不自己写 pass）
```

使用这条入口时必须同时说明的界限：

- 它**不新增判据**：判域仍在 `Tool/skill/seep-router/SKILL.md`，领域方法仍在该域 SKILL.md；
  主/辅域并列时入口返回 `ambiguity`，由主 Agent 决定专业路线。
- `enforcement_scope=workflow-entry-only`、`host_wiring_required=true`、`globally_enforced=false`：
  只有**经本入口发起**的动作被执行前校验与证据绑定。直接调 MCP 工具、直接
  `tool-run.ps1 -Run`、直接运行目标、或在别的会话执行，都不经过它，也不被它拦截。
- `check-action` 是锁内快照而不是租约；执行后上游还会重算目标哈希与快照，变化时按
  「已执行但证据未被接受」上报，不伪称全局锁。
- `exit0`／方法返回成功只写进 attempt 结果，**永不**自动 `acceptance-record`；
  pass 必须由人/Agent 显式给证据 id + verifier + how，`completed` 还要整套 required 项。

### 8.2 本仓库工程批次的实施与验收

当前会话按 REQUIREMENTS.md 和 docs/CURRENT-STATE.md 完成本次有界任务，自行实施、验证和交接；不默认派子代理，不恢复旧多路长期实施策略。只有用户明确要求或当前任务确有独立工作需要时才采用分工，并服从用户当前的模型、并行及文件所有权约束。

实施者以及本批判据或测试修改者只能提交实施、自测回执。验收使用另一会话，对稳定版本只读验证；验收者不得修改本批实现、判据或测试。发现反例后交回实施者，修复后重新独立复验。主对话若修改判据代码，也不得据自己的运行结果宣布通过。

独立回执须记录被验对象的起止哈希、命令与实际退出码、真实正对照和负例、proven/refuted/unverified、跳过项和证明上限。对象在验收中发生变化则相关结论失效。探针成功复现漏洞即为 refuted，即使探针脚本自身返回零；脚本执行成功、自测通过和必需判据通过不能混为一谈。

主对话审阅独立证据并逐项签字。结构通过、文件数、exit0、历史报告或实施者自述不替代验收；必需判据仍有反例时，已证子项可以保留，本批整体不得宣布通过。单批通过也不表示整个工作台或九领域行为验收完成。

## 9. 经验回流

一次目标专属的事实留在案例；第二次出现且流程稳定时沉淀为配方；多个配方复用且证据稳定时才升为共享能力。

不得因为一次成功新增全局规则。新领域必须复用本契约，提供自己的输入、工具、证据、失败和见证，不得修改全局执行循环。
