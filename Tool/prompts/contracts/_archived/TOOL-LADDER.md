# TOOL-LADDER —— 工具获取阶梯（"有工具却没用上"的根治）

> 由来：2026-10-23 实测。`tool-run.ps1` 1.3 秒把 x64dbg 起成 READY、9094 在听，
> 但会话里 `ALL_TOOLS` **没有 `mcp__x64dbg`** → 模型没有工具可调 → 手搓了 5 个一次性调试器脚本。
> 当时的表现是**静默**：它没说自己缺工具，也没求助，直接绕过。
>
> 这不是 x64dbg 一个工具的问题，是**所有工具**的问题。所以做成阶梯，不是补丁。

---

## 1. 四阶梯（顺序固定，每级都有判据）

```
L0 探活 ──在？──► L1 启动 ──起？──► L2 连上 ──通？──► L3 装 ──装？──► L4 求助
   │              │              │             │              │
   └ 已连 → 直接用  └ 起不来 → L3  └ 连不上 → L3  └ 装不上 → L4  └ 停下问人
```

| 级 | 动作 | 通过判据（**必须是可观测的**，不是"我觉得可以"） |
| :-- | :-- | :-- |
| **L0 探活** | 查这个工具此刻是否已经可用 | MCP 型：端口在听 **且** `tools/list` 返回 ≥1 个工具<br>CLI 型：`where <exe>` 命中 **且** 能跑一条无害命令拿到预期输出 |
| **L1 启动** | 用 `tool-run.ps1 -Tool <id>`（唯一启动入口） | 返回 `status: READY` |
| **L2 连上** | 确认 MCP 已注册进当前会话 | **在 `ALL_TOOLS` 里能看到 `mcp__<server>`**（不是"端口通"，不是"进程在"） |
| **L3 装** | 缺工具时给安装计划 | 报出：装什么 / 多大 / 从哪下 / 要不要管理员 / 有没有替代品；**等用户确认再装** |
| **L4 求助** | 前四级都不通 | 发 ASK 卡，写清：**要哪个工具 / 卡在哪一级 / 试过什么 / 备选是什么 / 不给我工具会怎样** |

### 关键一条

**"端口在听"不等于"工具可用"。** L2 的唯一判据是**工具出现在 `ALL_TOOLS` 里**。
本次事故就是拿 L0 的"端口通"当成了 L2 的"连上了"。

---

## 2. 手搓 vs 用工具：判据（不是"永远优先工具"）

手搓脚本有时候确实更好。但必须是**算过的选择**，不是**够不着工具的替代**。

| 场景 | 选择 | 理由 |
| :-- | :-- | :-- |
| 工具可用，且它就是这个活的标准手段 | **用工具** | 成熟工具处理边界情况、留证据、可复现 |
| 工具可用，但只差一个小操作（例：批量改名 200 个函数） | **用工具 + 薄脚本** | 工具做主体，脚本做胶水 |
| 工具不可用，但脚本 3 行能出结果，且**只读、无副作用** | **手搓可以** | 成本明显更低 |
| 工具不可用，需要"附加/注入/改内存/长时间运行" | **必须先走 L1–L4** | 这类手搓脚本本身就是检测面，且容易把自己写崩（实测：`ctypes` 报错 3 次、GBK 崩 3 次） |
| 工具可用，但手搓能拿到工具拿不到的信息 | **手搓，且记录"为什么不走工具"** | 这属于决策，要留痕 |
| 同一形状手搓失败 2 次 | **停下**，回 L4 | 继续写第 3 个脚本 = 返工 |

**判定顺序**：先问"工具能不能干"→ 能就问"要不要加胶水"→ 不能就走 L1–L4 → L4 也不通才允许手搓，且必须在 `decisions.md` 写一段"为什么手搓"。

---

## 3. 静默是违规（这一条最重要）

以下三种情况**都属于必须停下来求助**：

1. 想要的工具**启动不了 / 连不上 / 装不上**；
2. 工具**能用但结果明显不对**（返回空、报错、超时两次）；
3. 为了绕开工具限制，需要**改本机环境**（装驱动、改网络、装证书、装服务）。

求助格式（对话内 A/B/C，不用弹窗）：

```
【需要你选】我想用 <工具> 做 <事>，但卡在 <L1/L2/L3>：<一句话现象>
A 我帮你启动/安装（我给你命令）
B 换 <替代工具/替代路线>
C 你继续用脚本兜底（我接受风险）
直接回 A / B / C
```

**不许出现的行为**：工具连不上就当作"这个工具不存在"，然后默默写脚本继续跑。
本次 48 分钟就是这一条——用户全程不知道它缺工具。

## 4. 每次会话要留下的工具台账

`case/tool-ledger.jsonl`，一行一个工具：

```json
{"tool":"x64dbg","l0":"alive","l1":"READY(1.3s)","l2":"IN_TOOLS(80)","l3":"n/a","l4":"n/a","ts":"..."}
{"tool":"ghidra","l0":"missing","l1":"fail","l2":"-","l3":"plan: 装 Ghidra 12.1.4 / 400MB / 官方 zip","l4":"asked: 要不要装？","ts":"..."}
```

**用途**：主对话每节回访时先看这张表——"你要用的工具，L2 过了吗？"
没过就说明这一节的结论是"够不着工具的产物"，可信度要打折。

---

## 5. 为什么这条要写进契约而不是提示词

因为"优先用工具"这句话我们已经写了两年，实测执行率是 **0 次**（48 分钟里 x64dbg 调用 0 次）。

机制落点：

| 落点 | 管什么 |
| :-- | :-- |
| `Tool/scripts/tool-acquire.py` | **执行**四阶梯，输出结构化结论（可直接被模型消费） |
| `case/tool-ledger.jsonl` | **留痕**，让"够不着工具"这件事可见 |
| `00-triage` / `00-analysis` 阶段契约 | 阶段开工第一步先跑 `tool-acquire` 报出"这一阶段要用什么工具、通不通" |
| 主对话回访四问 | 追加一问：**"你要用的工具 L2 过了吗？"** |
| behavior gate | 断言"缺工具时会发 ASK，而不是静默降级" |

## 6. 子代理的能力与护栏：实测结论（2026-10-23，修正版）

### 6.1 我先前的结论是错的，纠正如下

我曾根据黑盒测试得出"扩展在子代理里不加载"。**错了。**
真相是：**我写的 frontmatter 键拼法不被引擎识别**（我写 camelCase，引擎只认 snake_case），
而界面上那两个勾选（加载技能 / 加载扩展）才是真正的开关。

**UI 保存后文件里长这样（照这个写就对了）**：

```yaml
load_skills: true
load_extensions: true
skills: true
extensions: true
codemode: 'on'
mcp: 'on'
```

### 6.2 打开扩展后，cmd-guard 在子代理里确实生效（实测）

| 测什么 | 结果 |
| :-- | :-- |
| 长命令（10 段） | 出现 `[cmd-guard 提示 · 串了 10 段]` + `已自动注入 timeout=30` → **扩展加载了** |
| 加网卡 IP（带 -WhatIf） | **被拦下**，并给出 Frida / net-rollback 替代建议 |
| `Get-ChildItem C:\ -Recurse -Depth 1` | 没拦 —— **这是对的**：盘根正则要求路径 token 停在盘尾，该命令不算盘根扫描 |

### 6.3 但有一个真实的二选一（宿主限制，必须记住）

实测对照（同一个 profile 只改两个开关）：

| `load_extensions` | `tools:` 收窄是否生效 | cmd-guard 是否生效 |
| :-: | :-: | :-: |
| **false** | ✅ 生效（只剩列出那几个） | ❌ 不生效 |
| **true** | ❌ **不生效（全部内建工具都能用）** | ✅ 生效 |

也就是说：**要护栏就失去最小权限，要最小权限就失去护栏。**
（已验证：`load_extensions: false` + `tools: read,bash,grep,find,ls` → 子代理只剩这五个，无 write/edit；
　但同一次测试里 `[cmd-guard` 一个字都没出现。）

### 6.4 于是四份 profile 这样分工（已落地并逐个实测）

| profile | load_extensions | tools | 取舍理由 |
| :-- | :-: | :-- | :-- |
| `seep-stage`（要干活） | **true** | 全部（含 bash） | 它必须能干活，**护栏优先** |
| `seep-forensics`（取证） | **true** | 全部（含 bash） | 要跑 dump/抓包，**护栏优先** |
| `seep-stage-shell`（例外） | **true** | 全部（含 bash） | 同上，仅主对话显式指定时用 |
| `seep-verify`（验证） | **false** | `read, grep, find, ls` | **最小权限优先**：不能写产物来让判据通过；判据命令由主对话（带护栏）跑，输出丢给它判 |

**实测确认**：`seep-verify` 现在工具清单 = `read, grep, find, ls`，**没有 write / edit / bash**。

> 这是一个真实的工程取舍，不是 bug：
> **验证器最怕的是自己篡改产物**（所以收窄工具有价值），
> **执行器最怕的是改坏系统**（所以护栏有价值）。两者优先级不同，所以配置不同。

### 6.5 这条给以后的规矩

1. **新建子代理不要手写 frontmatter**，先在界面里勾选 → 保存 → 再 `cat` 文件照拄它的格式（少踩一次拼写坑）。
2. **一个 profile 只能选一边**：要护栏（`load_extensions: true`，全工具）或要最小权限（`false`，工具可控）。不要假设两者兼得。
3. 往 `DECISION-LOOP.md` §8 里“子代理能力面”写的任何断言，都必须先实测工具清单，不能照配置声明写。
