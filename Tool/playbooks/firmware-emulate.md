# 固件仿真 / rehosting 失败归因
- 触发词：固件仿真、rehosting、QEMU、FirmAE、启动失败、kernel panic、服务不通
- 输入（用户提供）：`<firmware.bin 或 rootfs>`、`<设备型号>`、`<架构/端序>`、`<允许的仿真网络>`、`<目标服务端口>`；范围由用户提供的 scope 决定。
- 用到的能力（capability id）：`tool:binwalk` `repo:case_state` `repo:fw-triage` `repo:fw-repro` `repo:fw-accept` `repo:probe_api` `repo:env-ledger` `repo:kb-query` `repo:seep-start`
- 步骤：1) `python Tool/scripts/case_state.py init --case work/<case> --target <TARGET>` → rc=0；2) `python Tool/skill/firmware-iot/scripts/fw-triage.py --file <FW> --json --out-dir work/<case>/fw` → rc=0，先定容器、架构、端序、init 线索；3) `python Tool/skill/firmware-iot/scripts/fw-repro.py --file <FW> --out-dir work/<case>/fw --json` → rc=0，拿到 rootfs 与推荐的 qemu 命令行；4) 启动仿真并保存 `work/<case>/emulate.log`，把“内核到 init / init 到服务 / 服务到端口”三段结果分别 `python Tool/scripts/case_state.py claim --case work/<case> --id E1/E2/E3 --text "<阶段结论>"`，再用 `prove --id E1 --evidence work/<case>/emulate.log` → rc=0；5) 服务面：`python Tool/skill/apkseep/scripts/probe_api.py --base http://127.0.0.1:<PORT> --path / --no-proxy` → rc=0；同一时刻记录进程、监听端口与业务响应，写入 `work/<case>/service.json`；6) 环境副作用先记账：`python Tool/skill/softseep/scripts/env-ledger.py record --case work/<case> --action "启动 qemu 网络" --before down --after up --restore "netsh interface set interface <name> admin=disable"` → rc=0，收尾 `check` → rc=0；7) `python Tool/skill/firmware-iot/scripts/fw-accept.py --case <case> --json` → rc=0，最后 `python Tool/scripts/preflight.py --fast` → rc=0。
- 判据（可机检）：`emulate.log` 出现 init 或 shell 提示；`service.json` 同时有 `pid`、`listen`、`response_code`；`probe_api` rc=0 且响应体非空；`env-ledger check` rc=0；`fw-accept` rc=0。
- 失败判据 + 换路：kernel panic → 核对架构/端序/机器 ID，换内核或 DTB；init 起不来 → 补 `/dev`、NVRAM、看门狗桩；服务进程在但端口 502/空响应 → 补 Web 根与配置，转真机只读验证；全盘加密 → 回 `firmware-extract` 找解密点；仿真网络不可达 → 改 user-mode 网络或 hostfwd 并记录。
- 交付物：`work/<case>/fw/`、`emulate.log`、`service.json`、`emulate.sh`、`env-changes.jsonl`、`failure-attribution.md`（内核/init/服务/网络四段）。
